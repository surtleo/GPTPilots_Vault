    with path.open("rb") as f:
        head = f.read(8)          # 파일 맨 앞 8바이트만 읽음

추출된 markdown에서 검색에 방해되는 잡음(목차, 반복되는 머리글/꼬리말, 쓸데없는 공백)을 제거해 순수 본문만 남기기.

```python
normalized = unicodedata.normalize("NFC", text)   # 한글 자모 조합 형태 통일
normalized = normalized.replace("\r\n", "\n")     # 윈도우식 줄바꿈 정리

```

#### NFC 정규화가 필요한 이유

한글은 유니코드에서 “가”를 표현하는 방법이 2가지인데,  
완성현 한글자 와 자음+모음으로 가능하다. 2개는 다른 문자로 취급되기 때문에 필요하다

#### 목차 제거가 까다로운 이유

잘못 지울 수 있기 때문에 두가지 안전 장치를 사용

- 위치제한 : 문서 앞부분만 검사
- 줄 전체 구조 매칭 : “제목 + 점(3개이상) + 쪽번호”로 줄 전체가 정확히 그 형태여야만 지움

지워진 목차의 제목들은 그냥 버리지 않고 `toc_titles`로 따로 챙깁니다 — 왜냐하면 다음 단계(청킹)에서 "이 제목이 목차에 있던 진짜 섹션 제목이구나"라고 판단할 힌트로 재사용하기 때문입니다

(`build_index.py`에서 `toc_titles=cleaned["toc_titles"]`로 넘겨주는 부분, 이전에 봤던 `chunk.py`의 `promote_pseudo_headers`와 연결됩니다).  
바

#### **반복 헤더/푸터 제거** (clean.py:83-102)

"◯◯공단 제안요청서" 같은 문구가 매 페이지 상단에 반복해서 찍힙니다. 이건 위치가 아니라 **빈도**로 잡습니다:

return counts[stripped] >= CLEAN_HF_MIN_REPEATS and len(stripped) <= CLEAN_HF_MAX_LEN

같은 줄이 5번(`CLEAN_HF_MIN_REPEATS`) 이상 반복되고 60자(`CLEAN_HF_MAX_LEN`) 이하로 짧으면 "이건 머리글/꼬리말이지 본문이 아니다"라고 판단합니다. 단, 표 행(`|`)이나 markdown 헤더(`#`)는 절대 건드리지 않습니다.

### B. **PII 마스킹 — mask_pii.py**

**목표**: 문서에 담당 공무원 실명·전화번호·이메일이 있을 수 있는데, 이게 Chroma·OpenAI API·LangSmith로 나가면 안 됩니다 (개인정보 유출). 그래서 **삭제가 아니라 `[담당자]`, `[전화번호]`, `[이메일]` 같은 토큰으로 치환**합니다 (문장 구조는 유지해야 검색·답변 품질이 안 떨어지니까).

세 가지를 마스킹합니다:

#### **전화번호** (mask_pii.py:27):

```python
PHONE_RE = re.compile(r"(?<![\d-])\d{2,3}\s*-\s*\d{3,4}\s*-\s*\d{4}(?![\d-])")
```

`(?<![\d-])`와 `(?![\d-])`는 "앞뒤에 숫자나 하이픈이 더 있으면 매칭 안 함"이라는 뜻입니다. 왜? "2024-1234-5678" 같은 **공고번호**가 우연히 전화번호 패턴처럼 보일 수 있어서, 그 앞뒤가 끊겨 있는(진짜 독립된 전화번호인) 경우만 잡습니다.

#### **실명**

이게 제일 정교합니다. 무작정 "한글 3글자"를 이름으로 보면 "보안팀장", "제안서" 같은 일반명사까지 다 지워버립니다. 그래서:

- 성씨 리스트(`_SURNAMES`, 김이박최정... 50여 개)로 시작하는 한글 3글자만 "이름 후보"로 취급 (mask_pii.py:42)
- 그중에서도 스톱워드(`_STOPWORDS`) — "성과", "조달", "한국" 같은 성씨로 시작하지만 사람 이름이 아닌 흔한 단어들 — 는 제외
- **"직함+이름" / "이름+직함" 인접 패턴만** 치환 대상으로 삼습니다: "사무관 홍길동", "홍길동 주무관", "담당자: 홍길동" 처럼 직함이 근처에 있어야 확신을 가지고 지웁니다. 그냥 문장 중에 나오는 한글 3글자는 안 건드립니다.

#### **표 셀 단위 마스킹** (mask_pii.py:135-161)

RFP에는 담당자 연락처가 표로 정리된 경우가 많습니다 (직함 | 이름 | 전화번호 형태). 그래서 "직함 셀 바로 옆 칸"이나 "직함 헤더 열 아래 칸"에 있는 이름 셀도 따로 찾아서 지웁니다.

**주석에 나온 트레이드오프**: 2글자 이름(외자 성 등)이나 4글자 복성 이름은 놓칠 수 있다고 스스로 인정하고 있습니다 — 완벽한 마스킹보다 "확실한 것만 정확히 지우고, 애매한 건 `diff 검수`(`uv run python -m src.ingest.mask_pii`로 전후 비교 샘플 출력)로 사람이 확인"하는 실용적 접근입니다.

2. 질문과 관련 있는 부분만 찾아야 하는데, 문서 전체를 한 덩어리로 임베딩하면 "이 문서 전체가 질문과 얼마나 비슷한가"만 알 수 있지, "어느 부분이 비슷한가"는 알 수 없습니다

### **A. 의사-헤더 승격 (`promote_pseudo_headers`)**

**문제**: hwp 문서 95건이 markdown 헤더(`#`, `##`)가 하나도 없이 뽑혔습니다. 하지만 문서 안에는 "Ⅱ. 제안요청 내용", "2.1 관리적 보안" 같은 번호 체계로 된 사실상의 제목이 있습니다. 이걸 인식 못하면 문서 전체가 "구조 없는 텍스트 덩어리"가 되어 섹션 정보를 잃어버립니다.

그래서 정규식 패턴들로 번호 체계 줄을 markdown 헤더로 "승격"시킵니다 (chunk.py:41-47):

```python
(re.compile(r"^[ⅠⅡⅢⅣⅤⅥⅦⅧⅨⅩⅪⅫ]+\s*[.．)]?\s+\S"), 1),   # Ⅱ. 제안요청 내용 → h1
(re.compile(r"^제\s*\d+\s*장(?:\s+\S|$)"), 1),                    # 제2장 사업 개요 → h1
(re.compile(r"^\d{1,2}(?:\s*[.．]\s*\d{1,2}){1,3}\s*[.．]?\s+\S"), 3),  # 2.1 관리적 보안 → h3
(re.compile(r"^[□■◦○●◇◆]\s+\S"), 3),                           # □ 개요 → h3
```

"2.1"(다단 번호)을 "2."(단일 번호)보다 **먼저** 검사하도록 순서를 정해뒀습니다 — 정규식 리스트를 순서대로 시도하기 때문에, 순서가 바뀌면 "2.1 관리적 보안"이 "2." 패턴에 먼저 걸려 레벨을 잘못 매길 수 있습니다.

동시에 오탐 방지 장치 두 개가 있습니다 (chunk.py:56-63):

```python
def _pseudo_header_level(line: str) -> int | None:
    if len(line) > PSEUDO_HEADER_MAX_LEN or _SENTENCE_END_RE.search(line):
        return None   # 40자 넘거나, "...해야 한다." 처럼 문장으로 끝나면 제목이 아니다
```

"1. 사업자는 다음 서류를 제출해야 한다." 같은 **본문 리스트 항목**이 번호로 시작한다고 제목으로 잘못 승격되는 걸 막습니다.

이미 markdown 헤더가 있는 문서(대부분 pdf)는 이 로직을 아예 건너뜁니다 (chunk.py:73-74):

### C. 표는 따로 처리 (`_iter_blocks`, `_is_valid_table`, `_split_table`)

각 섹션 텍스트 안에서 `|`로 시작하는 줄들(표)과 일반 텍스트를 구분합니다 (chunk.py:130-142).

표는 일반 텍스트와 다르게 취급해야 하는 이유: 표를 중간에서 뚝 자르면 "금액 | 100,000,000원" 같은 행이 헤더 없이 떨어져 나가 의미를 잃습니다.

**단, 모든 표가 다 정상은 아닙니다** — hwp/pdf 파서가 셀 병합된 표를 markdown으로 바꾸면 행마다 열 개수가 안 맞는 "깨진 표"가 나옵니다. 그래서 검증을 합니다 (chunk.py:145-150):

```python
def _is_valid_table(block: str) -> bool:
    rows = [line for line in block.split("\n") if line.strip()]
    return len({len(row.strip().strip("|").split("|")) for row in rows}) == 1
```

모든 행의 열 개수가 똑같은 `set`으로 만들었을 때 원소가 1개뿐이면(=다 같으면) 유효한 표입니다.

깨진 표는 그냥 평문으로 취급해서 아래 ④번 일반 분할 경로로 흘려보냅니다 (앞서 얘기했던 pdf `plain` 엔진 결과물이 여기서도 같은 신세가 됩니다).

큰 표는 chunk.py:153-172에서 **헤더 행을 반복**하며 여러 청크로 쪼갭니다 — 표를 둘로 나눠도 각 조각이 "이 열이 뭘 의미하는지" 헤더를 갖고 있어야 하기 때문입니다.

- 더 자세한 설명
    
    ## ① `_iter_blocks` — "표 줄"과 "일반 줄"을 그룹으로 나누기
    
    이런 섹션 텍스트가 있다고 합시다:
    
    ```
    이 사업의 예산은 다음과 같다.
    | 항목 | 금액 |
    | --- | --- |
    | 인건비 | 100,000,000 |
    | 재료비 | 50,000,000 |
    이상 예산 내역이다.
    ```
    
    `_iter_blocks`는 줄마다 `|`로 시작하는지(`is_pipe`)를 검사하면서, **같은 종류(표 or 일반)가 연속되는 동안은 하나로 묶고, 종류가 바뀌는 순간 지금까지 묶은 걸 하나의 블록으로 내보냅니다**:
    
    ```python
    buf: list[str] = []
    buf_is_pipe = False
    for line in text.split("\n"):
        is_pipe = line.lstrip().startswith("|")
        if buf and is_pipe != buf_is_pipe:   # 종류가 바뀌었다 → 지금까지 묶은거 방출
            yield buf_is_pipe, "\n".join(buf)
            buf = []
        buf_is_pipe = is_pipe
        buf.append(line)
    ```
    
    위 예시를 넣으면 결과는 **3개 블록**으로 나뉩니다:
    
    ```
    블록1 (일반): "이 사업의 예산은 다음과 같다."
    블록2 (표)  : "| 항목 | 금액 |\n| --- | --- |\n| 인건비 | 100,000,000 |\n| 재료비 | 50,000,000 |"
    블록3 (일반): "이상 예산 내역이다."
    ```
    
    즉, 이 함수는 아직 "표가 진짜 표인지"는 안 따집니다 — 그냥 **겉모양(`|`로 시작하나 안 하나)만 보고 분류**만 합니다. 표인지 아닌지 판단은 다음 단계인 `_is_valid_table`이 합니다.
    
    ## ② `_is_valid_table` — "진짜 표"인지 검증
    
    markdown 표는 원래 모든 행의 칸(열) 개수가 같아야 정상입니다. 그런데 **셀 병합**이 있는 원본 hwp 표를 markdown으로 변환하면, 병합된 칸이 사라지거나 뒤 칸들이 밀려서 행마다 칸 개수가 달라지는 경우가 생깁니다. 예를 들어:
    
    ```
    | 항목   | 금액        | 비고     |
    | ---   | ---        | ---     |
    | 인건비  | 100,000,000 |
    | 재료비  | 50,000,000  | 3개월 사용 | 추가승인필요 |
    ```
    
    → 원본 hwp 표에서 2번째 행("인건비")이 "비고" 칸과 옆 칸이 합쳐져 있었다면, 변환 과정에서 칸이 하나 없어지고, 4번째 행("재료비")은 반대로 칸이 하나 더 생기는 식으로 **행마다 칸 개수가 들쭉날쭉**해집니다.
    
    `_is_valid_table`은 이걸 숫자로 잡아냅니다:
    
    ```python
    def _is_valid_table(block: str) -> bool:
        rows = [line for line in block.split("\n") if line.strip()]
        return len({len(row.strip().strip("|").split("|")) for row in rows}) == 1
    ```
    
    한 줄씩 계산해보면:
    
    - `"| 항목 | 금액 | 비고 |"` → 앞뒤 `|` 떼고 `|`로 쪼개면 → `[" 항목 ", " 금액 ", " 비고 "]` → **길이 3**
    - `"| --- | --- | --- |"` → **길이 3**
    - `"| 인건비 | 100,000,000 |"` → **길이 2** ← 칸 하나 부족!
    - `"| 재료비 | 50,000,000 | 3개월 사용 | 추가승인필요 |"` → **길이 4** ← 칸 하나 초과!
    
    이 4개 길이를 `{3, 3, 2, 4}`로 집합(set)에 넣으면 원소가 `{2, 3, 4}` 3개가 됩니다. `len(...) == 1`이 아니므로 **"깨진 표"로 판정** → 표 취급을 포기하고 그냥 일반 텍스트처럼 `RecursiveCharacterTextSplitter`로 흘려보냅니다 (칸이 안 맞으니 표로 살리는 것보다 차라리 문장으로 자르는 게 안전하다는 판단).
    
    반대로 아까 첫 번째 예시(항목/금액 2칸짜리, 모든 행이 정확히 2칸)는 모든 길이가 `{2}` 하나뿐이므로 **유효한 표**로 인정됩니다.
    
    ## ③ `_split_table` — 큰 표를 헤더 반복하며 자르기
    
    표가 유효하다고 판단됐는데, 행이 너무 많아서(500자 초과) 한 청크에 다 못 담으면 어떻게 할까요? 그냥 중간에서 자르면 두 번째 조각은 "이 칸이 뭘 뜻하는지" 제목을 잃어버립니다. 그래서 **첫 조각에도, 둘째 조각에도 헤더 행을 복사해서 넣습니다**.
    
    예시로, 아래처럼 20행짜리 큰 표가 있고 500자를 넘긴다고 합시다:
    
    ```
    | 항목 | 금액 |
    | --- | --- |
    | 인건비 | 100,000,000 |
    | 재료비 | 50,000,000 |
    | 여비   | 10,000,000 |
    ... (총 20행)
    ```
    
    코드 흐름:
    
    ```python
    header_end = 2 if _TABLE_SEPARATOR_RE.match(rows[1]) else 1   # "| --- | --- |" 줄이 있으면 헤더는 2줄(제목+구분선)
    header, body = rows[:header_end], rows[header_end:]            # header=["| 항목 | 금액 |", "| --- | --- |"], body=나머지 18행
    
    group = []
    group_len = header_len   # 매 조각을 시작할 때 항상 헤더 길이부터 카운트 시작
    for row in body:
        if group and group_len + len(row) + 1 > CHUNK_SIZE:   # 지금 담고 있는 조각이 꽉 찼으면
            pieces.append("\n".join(header + group))            # 헤더 + 지금까지 모은 행 = 청크 하나 확정
            group, group_len = [], header_len                   # 새 조각 시작 — 다시 헤더부터 카운트
        group.append(row)
        group_len += len(row) + 1
    ```
    

### ④ 일반 텍스트는 2차 분할 (`RecursiveCharacterTextSplitter`)

표가 아닌 부분은 문자 수 기준(500자, `CHUNK_SIZE`)으로 자릅니다:

```python
splitter = RecursiveCharacterTextSplitter(
    chunk_size=CHUNK_SIZE,
    chunk_overlap=int(CHUNK_SIZE * CHUNK_OVERLAP_RATIO),  # 500 * 0.12 ≈ 60자
    separators=list(CHUNK_SEPARATORS),  # ["\n\n", "\n", ". ", " ", ""]
)
```

`overlap`(겹침)이 있는 이유: 딱 500자에서 뚝 자르면 문장 중간이 끊길 수 있습니다. 앞 청크의 끝 60자를 다음 청크 앞에도 겹쳐 넣어서, 청크 경계에서 문맥이 잘리는 걸 완화합니다. `separators`는 "먼저 문단(`\n\n`) 단위로 자르고, 안 되면 줄(`\n`), 안 되면 문장(`.` ), 안 되면 단어, 정 안 되면 그냥 글자 단위로"라는 **우선순위**입니다.

### ⑤ 헤더만 있고 본문 없는 조각은 다음 청크에 합침

섹션을 나누다 보면 "## 3. 사업 기간" 이라는 제목만 있고 바로 다음 섹션 헤더로 넘어가는 경우가 생길 수 있습니다 (본문이 다른 조각으로 분리됨). 이런 "헤더뿐인 조각"을 그대로 두면 의미 없는 청크가 되니, 다음 조각과 합칩니다 (chunk.py:230-242):

```python
if not is_table and _is_header_only(piece):
    carry = f"{carry}\n{piece}" if carry else piece   # 잠깐 들고 있다가
    continue
if carry:
    piece = f"{carry}\n{piece}"   # 다음 조각 앞에 붙임
```

### ⑥ E5 토큰 한도 재검증 (`_fit_token_limit`)

문자 수(500자)로는 500자여도, 실제 임베딩 모델의 **토큰** 수(512 초과 여부)는 다를 수 있습니다(한글은 토큰화 특성상 글자당 토큰 소모가 다름). 그래서 최종적으로 실제 토크나이저로 토큰 수를 세서, 512(`E5_MAX_TOKENS`)를 넘으면 **반으로 쪼개기를 재귀적으로 반복**합니다 (chunk.py:180-195):

```python
mid = len(text) // 2
return _fit_token_limit(text[:mid], ...) + _fit_token_limit(text[mid:], ...)
```

10번(`MAX_SPLIT_DEPTH`) 재귀해도 안 줄면 그냥 글자 단위로 강제로 잘라버립니다 — 무한루프 방지용 최후 수단입니다.

### 최종 산출물

`chunk_doc()`이 반환하는 청크 하나는 이렇게 생겼습니다:

```python
{
    "chunk_id": "◯◯공단_사업::0004",
    "text": "실제 저장·표시용 원문",
    "embed_text": "passage: [사업명: ... / 발주기관: ... / 섹션: ...]\n실제 저장·표시용 원문",
    "metadata": {"doc_id": "...", "is_table": False, "섹션": "...", "사업명": "...", ...}
}
```

`text`(저장·화면 출력용)와 `embed_text`(임베딩 계산용, `passage:` 접두어 + 사업명/발주기관/섹션 라벨 포함)를 **분리해서 갖고 있는 게 포인트**입니다 — 임베딩 검색 성능을 위해 추가한 접두어/라벨이 실제 답변 생성이나 화면 출력에는 불필요한 잡음이 되니까요.

```
청크1: "| 항목 | 금액 |\n| --- | --- |\n(1~7행)"
청크2: "| 항목 | 금액 |\n| --- | --- |\n(8~14행)"   ← 헤더가 또 복사됨
청크3: "| 항목 | 금액 |\n| --- | --- |\n(15~18행)"  ← 여기도 복사됨
```

**핵심은 `group_len = header_len`으로 매번 리셋하는 부분**입니다 — 새 조각을 시작할 때마다 "이 조각은 헤더 길이만큼은 이미 차 있다"고 치고 카운트하기 때문에, 각 조각이 실제로 500자를 넘지 않으면서도 헤더를 포함하게 됩니다. 이렇게 하면 나중에 검색에서 "청크3"만 딱 찾아져도, 그 안에 "항목/금액"이라는 열 이름이 같이 있어서 "이 숫자가 뭘 뜻하는지" LLM이 알 수 있습니다.

# 4단계: 임베딩 + 벡터DB 저장 — build_index.py

앞의 추출·클리닝·마스킹·청킹이 끝나면, 이제 청크들을 **숫자 벡터로 바꿔서(임베딩) 검색 가능한 데이터베이스(Chroma)에 넣는** 마지막 오프라인 단계입니다.

### ① 임베딩이 정확히 뭘 하는 건가

`e5_embed()` (build_index.py:45-50):

```python
def e5_embed(texts: list[str]) -> list[list[float]]:
    model = _get_model()
    return model.encode(
        texts, batch_size=EMBED_BATCH_SIZE, normalize_embeddings=True, show_progress_bar=False
    ).tolist()
```

텍스트를 넣으면 숫자 배열(벡터, 여기선 384차원)이 나옵니다. 예를 들어 "보안 요구사항"이라는 텍스트가 `[0.02, -0.15, 0.31, ...]` 같은 숫자 384개짜리 배열로 변환됩니다. **의미가 비슷한 문장은 이 숫자 배열끼리 거리가 가깝게** 나오도록 미리 학습된 모델(`intfloat/multilingual-e5-small`)이 이 변환을 해줍니다.

`normalize_embeddings=True`가 중요합니다 — 벡터의 길이(크기)를 항상 1로 통일합니다. 왜? 그래야 "방향"(의미)만으로 비교할 수 있어서, 코사인 유사도(cosine similarity, 두 벡터의 각도) 계산이 단순해집니다. Chroma 설정에서도 이걸 맞춰줍니다:

```python
client.get_or_create_collection(name=name, metadata={"hnsw:space": "cosine"})
```

**`passage:`/`query:` 접두어 규칙** — E5 모델은 "저장할 문서"와 "검색할 질문"을 구분해서 학습됐습니다. 그래서:

- 청크를 저장할 때는 `"passage: [사업명: ... / 섹션: ...]\n실제내용"` (청킹 단계에서 만든 `embed_text`)
- 질문을 검색할 때는 `"query: 보안 요구사항 알려줘"`

이 접두어를 안 붙이면 코드가 에러 나는 게 아니라 **그냥 조용히 검색 품질이 떨어집니다** — 그래서 코드 주석에 "누락 시 조용한 품질 하락"이라고 경고가 적혀 있는 겁니다. 이런 종류의 버그는 테스트로 안 잡히면 발견하기 정말 어렵습니다.

### ② `build_index()` — 전체를 하나로 잇는 함수

build_index.py:93-135를 보면 지금까지 배운 클리닝·마스킹·청킹이 여기서 순서대로 호출됩니다:

```python
for doc in docs:
    cleaned = clean_doc(doc["markdown"])
    masked = mask_basic(cleaned["text"])
    all_chunks.extend(chunk_doc(doc["doc_id"], masked, doc["meta"], ...))

collection = get_collection(persist_dir=persist_dir)
for start in range(0, len(all_chunks), EMBED_BATCH_SIZE):    # 64개씩 배치로
    batch = all_chunks[start : start + EMBED_BATCH_SIZE]
    collection.upsert(
        ids=[c["chunk_id"] for c in batch],
        embeddings=embed_fn([c["embed_text"] for c in batch]),   # embed_text(prefix 포함)를 임베딩
        documents=[c["text"] for c in batch],                     # text(원문)는 그대로 저장
        metadatas=[c["metadata"] for c in batch],
    )
```

**한 번에 다 임베딩하지 않고 64개씩(`EMBED_BATCH_SIZE`) 나눠서 처리**하는 이유는 메모리 문제입니다 — 수천 개 청크를 한꺼번에 모델에 넣으면 GPU/CPU 메모리가 터질 수 있어서 배치로 나눕니다.

`collection.upsert()`에서 4가지를 같이 저장합니다:

- `ids`: 청크 고유 ID (`"doc_id::0004"` 형태)
- `embeddings`: 방금 계산한 벡터 (검색용)
- `documents`: 사람이 읽는 원문 (검색 결과로 보여줄 것)
- `metadatas`: 사업명·발주기관·섹션 등 (필터링·출처 표기용)

### ③ 왜 컬렉션이 2개인가 — `chunks` vs `doc_cards`

`load_index_inputs()`(build_index.py:65-90)를 보면:

```python
excluded = {e["doc_id"] for e in json.loads(ocr_path.read_text(...))}  # OCR 대기(추출 실패) 문서
...
if doc["doc_id"] in excluded:
    continue   # chunks 컬렉션에는 이 문서를 아예 안 넣음
```

반면 `load_doc_cards_inputs()`(build_index.py:142-146)는:

```python
meta_all = json.loads((extracted_dir / "meta.json").read_text(...))
return list(meta_all.values())   # 100건 전부 — 추출 실패한 문서도 포함
```

**의도**: 추출이 실패한 문서(예: 타임아웃으로 텍스트를 못 뽑은 1건)는 본문 검색은 불가능하지만, 최소한 **"사업명이 뭐고 어느 기관이 발주했는지"** 정도는 CSV 메타데이터로 알고 있습니다. 그래서:

- `chunks` 컬렉션 = 본문 검색용 (실패 문서 제외, 99건)
- `doc_cards` 컬렉션 = 문서 카드 검색용, 100건 전부 (탐색형 질문 "교육 관련 사업 뭐 있어?"에 후보로 제시하거나, 실패 문서를 물어보면 "본문은 없지만 이런 사업입니다"라고 답하는 용도)

이게 라우터의 `meta_only` 경로([[router.py](http://router.py)]에서 봤던 "청크 0개 → 메타만 제공")와 직접 연결됩니다.

### ④ 종료 게이트 — `check_index_gate`

인덱싱이 끝나면 마지막으로 "이상하게 빠진 문서는 없는지" 자동 검사합니다 (build_index.py:196-212):

```python
cards_only = card_ids - chunk_ids     # doc_cards엔 있는데 chunks엔 없는 문서
chunks_only = chunk_ids - card_ids    # 반대 경우 (이건 있으면 안 됨 — 버그)
return {
    "passed": not chunks_only and cards_only == set(expected_missing),
    ...
}
```

`cards_only`(카드는 있는데 본문은 없는 문서)가 딱 "추출 실패로 미리 알고 있던 문서 목록"(`expected_missing`)과 **정확히 일치**해야 통과합니다. 만약 예상치 못한 문서가 하나라도 더 빠져 있으면 — 예를 들어 임베딩 도중 에러가 나서 조용히 누락됐다면 — 이 게이트가 실패로 잡아내고 `src/pipeline.py`의 `PipelineError`로 파이프라인을 중단시킵니다.

### ⑤ 검색은 어떻게 하나 — `query_index` (다음 단계로 넘어가는 다리)

```python
def query_index(question, k=5, where=None, ...):
    result = collection.query(
        query_embeddings=embed_fn([E5_QUERY_PREFIX + question]),  # "query: " 접두어!
        n_results=k,
        where=where,   # {"doc_id": "..."} 필터
        include=["documents", "metadatas", "distances"],
    )
```

질문 텍스트에 `query:` 접두어를 붙여 임베딩하고, Chroma가 저장된 수천 개 청크 벡터 중 **코사인 거리가 가장 가까운 k개(기본 5개)**를 찾아줍니다. `where` 파라미터로 "이 doc_id 안에서만 찾아라"는 필터도 걸 수 있습니다 — 이게 바로 다음 단계인 `retrieve.py`에서 쓰이는 함수입니다.

# 5단계: 온라인 쿼리 파이프라인

지금까지는 전부 "미리 준비하는" 단계였고, 이제부터는 **사용자가 질문을 칠 때마다** 실행되는 코드입니다. 진입점은 `src/app.py`의 `answer_once()`(app.py:82-126)이고, 그 안에서 4개 파일이 순서대로 협력합니다: `router.py` → (`retrieve.py` + `generate.py`).

```python
decision = route_fn(question, active_doc_id=state.active_doc_id)   # 1. 라우팅
...
if decision.route in ("direct_meta", "meta_only"): ...              # LLM 무호출 경로
elif decision.route == "clarify": ...
elif decision.route == "explore": ...
else:  # retrieval
    hits = retrieve_fn(question, doc_id=decision.doc_id)             # 2. 검색

```

### ① 라우터의 핵심 — `_match()`: "어떤 문서 얘기인지" 찾아내기

이게 이 프로젝트에서 가장 정교한 부분입니다. 예를 들어 코퍼스에 이런 문서 2개가 있다고 합시다 (합성 예시):

- doc A: 사업명 "서울교통공사 통합관제시스템 구축", 발주기관 "서울교통공사"
- doc B: 사업명 "부산교통공사 스마트카드 고도화", 발주기관 "부산교통공사"

사용자가 "서울교통공사 사업 보안 요구사항 알려줘"라고 물으면:

**후보 이름 목록 만들기** — `_candidate_names()`(router.py:218-241)가 매칭 대상이 될 이름들을 모읍니다: 각 문서의 사업명, 기관별로 묶은 발주기관명, org_dictionary의 수동 별칭들. (지역 축약형은 따로 2군으로 분리 — 나중에 설명.)

**fuzzy 점수 매기기** — `fuzz.partial_ratio(name, question)`으로 질문 문장 안에 그 이름이 얼마나 비슷하게 들어있는지 점수(0~100)를 매깁니다:

```python
scored = [(fuzz.partial_ratio(name, question), name, docs, False) for name, docs in names]
```

"서울교통공사"는 질문 문장에 그대로 포함되어 있으니 거의 100점, "부산교통공사"는 겹치는 글자가 적어 낮은 점수가 나옵니다.

**80점 미만은 버림** ([router.py:275](http://router.py:275)):

```python
scored = sorted((s for s in scored if s[0] >= FUZZY_MATCH_THRESHOLD), key=lambda s: -s[0])
```

`FUZZY_MATCH_THRESHOLD = 80`. 이 임계값 밑이면 "그 문서를 말한다고 확신 못함"으로 처리합니다.

**1등과 2등이 너무 붙어있으면 반문** (router.py:289-307):

```python
if top_score - score >= FUZZY_TIE_MARGIN:   # 5점 이상 차이나면 안전 → break
    break
```

1등이 92점, 2등이 89점이면 차이가 5점 미만이라 "둘 중 뭘 말하는 건지 애매하다"고 보고 `clarify`(반문) 경로로 보냅니다. 이게 왜 필요하냐면, 애매한데 그냥 1등만 믿고 진행하면 **틀린 문서로 확신에 찬 답**을 만들어낼 위험이 있기 때문입니다 — 차라리 "어느 문서 말씀이신가요?"라고 되묻는 게 안전합니다.

**부분 언급도 잡는 트릭 — 고유 토큰** (router.py:244-255): 만약 질문이 "관제시스템 사업 보안 어때"처럼 기관명 없이 사업명 일부만 말하면 `partial_ratio`가 낮게 나올 수 있습니다. 그래서 코퍼스 전체에서 **딱 한 문서에만 등장하는 단어**("관제시스템"이 doc A에만 있다면)를 별도로 매칭 후보에 넣습니다:

```python
def _distinctive_tokens(names) -> dict[str, str]:
    ...
    return {tok: next(iter(ds)) for tok, ds in token_docs.items() if len(ds) == 1}
```

단, "시스템", "사업", "구축" 같은 흔한 단어는 `TOKEN_STOPWORDS`로 걸러서 오매칭을 막습니다 (여러 문서에 다 나오는 단어라 식별력이 없으니까).

**흥미로운 안전장치**: 고유 토큰 하나만으로 문서가 확정됐는데(`via_token=True`) 동시에 직답 질문("예산 얼마야")이면, 라우터는 그 확신을 **일부러 낮춰서 반문으로 보냅니다** (router.py:451-456):

```python
if field_name and via_token:
    return RouteDecision(route="clarify", ..., reason="고유 토큰 단독 매칭 — 직답 단정 금지, 후보 확인 반문")
```

이유: retrieval 경로는 틀려도 LLM이 "이 컨텍스트에 없다"고 자기교정할 여지가 있지만, `direct_meta`는 CSV 값을 무조건 확정해서 답해버리므로 **틀리면 그대로 권위 있는 오답**이 됩니다. 그래서 확신이 약한 매칭(토큰 단독)일 때는 더 위험한 직답 경로를 막는 겁니다.

### ② 직답 분기 — `_direct_field()` / `_direct_answer()`

문서가 특정됐으면, LLM을 부르지도 않고 CSV에서 바로 답할지 판단합니다 (router.py:334-342):

```python
DIRECT_PATTERNS = {"금액": ("얼마", "금액이", "금액은", "예산은", "예산이"), "마감일": ("언제까지", "마감일")}
EVIDENCE_WORDS = ("근거", "기준", "산출", "내역")

def _direct_field(question):
    if any(w in question for w in EVIDENCE_WORDS):
        return None   # "예산 산출 근거"는 직답 아님 — retrieval로
    ...
    for field_name, patterns in DIRECT_PATTERNS.items():
        if any(p in question for p in patterns):
            return field_name
```

"이 사업 예산 얼마야?" → `금액` 필드로 직답. 하지만 "예산 산출 근거가 뭐야?"처럼 `EVIDENCE_WORDS`가 같이 있으면 — 숫자 하나만 던지면 안 되고 본문 근거가 필요한 질문이니 — 강제로 `retrieval`로 돌립니다. "기간이랑 예산은?"처럼 복합 질문도 `_COMPOUND_DIRECT_RE`로 걸러서 retrieval로 보냅니다 (직답은 필드 하나만 답할 수 있어서 나머지 질문이 누락되니까).

### ③ 검색 — `retrieve.py`

문서가 확정되고 직답도 아니면 진짜 검색을 합니다:

```python
def retrieve(question, k=5, doc_id=None, ...):
    where = {"doc_id": doc_id} if doc_id else None
    return query_index(question, k=k, where=where)
```

앞서 4단계에서 본 `query_index`를 그대로 재사용하되, **`doc_id` 필터를 강제로 겁니다** — 다른 문서 청크가 섞여 들어오는 걸 원천 차단합니다. 만약 필터링 후 결과가 0개면, app.py:114-115에서 필터를 풀고 전체 검색하는 게 아니라 그냥 "근거를 찾지 못했다"고 고정 응답합니다 — 엉뚱한 문서 내용을 가져와 답하는 걸 막는 장치입니다.

찾은 결과는 `format_context()`(retrieve.py:29-37)로 LLM에 넣을 텍스트로 조립됩니다:

```python
label = md.get("사업명") or md.get("doc_id", "미상")
blocks.append(f"[출처: {label} / {section}]\n{h['text']}")
```

### ④ 생성 — `generate.py`

시스템 프롬프트(generate.py:25-33)가 환각 방지 규칙을 최우선으로 못박습니다:

```
1. 답은 반드시 제공된 컨텍스트에 근거한다. 컨텍스트에 없는 내용은
"제공된 문서에서 확인되지 않습니다"라고 답한다.
2. 근거 사용 시 출처를 표기한다: (출처: {사업명}, {섹션}).
```

`build_messages()`(generate.py:93-100)가 최근 6턴 히스토리 + 이번 컨텍스트/질문을 합쳐 GPT-5-mini에 보낼 메시지를 만들고, `_call_with_retry()`(generate.py:106-138)가 429(rate limit)/5xx 에러 시 지수 백오프(2초→4초→8초)로 최대 3번 재시도합니다.

재밌는 예외처리 하나: gpt-5 계열은 "reasoning 토큰"이 답변 토큰 예산 안에 포함되는데, 가끔 reasoning만으로 예산을 다 써버려서 **답변이 텅 빈 채로 옵니다** (generate.py:165-172):

```python
if not answer.strip() and response.choices[0].finish_reason == "length":
    response = _call_with_retry(client, messages, max_completion_tokens=GENERATION_MAX_COMPLETION_TOKENS * 2)
```

이럴 때 예산을 2배로 늘려서 한 번 더 시도합니다.

### ⑤ 비용 추적 — `TokenLedger`

모든 호출마다 `ledger.add(response.usage)`로 토큰 수를 누적하고, 매 호출 전에 `ledger.check_limit()`으로 세션 누적 비용이 $2를 넘었으면 `CostLimitExceeded`를 던져서 세션을 강제 종료시킵니다 — API 요금이 통제 불능으로 새는 걸 막는 안전장치입니다.

switched = state.active_doc_id is not None and doc_id != state.active_doc_id
