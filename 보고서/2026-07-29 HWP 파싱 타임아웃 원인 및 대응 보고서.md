# HWP 파싱 타임아웃 원인 및 대응 보고서

> 대상: 케빈랩 주식회사 「평택시 강소형 스마트시티 AI 기반의 영상감시 시스템」 HWP 파일 1건  
> 작성일: 2026-07-29  
> 목적: 특정 HWP가 추출 작업을 멈추게 하는 이유를 팀 전체가 이해하고, 새 RFP가 추가되어도 같은 문제가 반복되지 않도록 대응 방향을 정한다.

## 1. 한 줄 결론

케빈랩 파일이 깨진 것으로 단정할 근거는 없다. 파일은 한글(Hancom)에서 정상적으로 열리고 PDF로 바꾼 뒤에는 본문 추출도 성공했다. 문제는 현재 사용 중인 외부 HWP 파서가 문서 안의 특정 짧은 제어 문자열을 만났을 때 **다음 위치로 이동하지 못해 같은 위치를 계속 읽는 것**이다. 즉, 문서 자체보다 파서의 예외 처리 부족이 직접 원인이다.

## 2. 지금까지 확인한 사실

| 항목 | 확인 결과 | 의미 |
| --- | --- | --- |
| 전체 원본 100건 재추출 | 99건 성공, 케빈랩 1건만 600초 타임아웃 | 일반적인 HWP 추출 경로는 대부분 동작한다. |
| 케빈랩 파일 열기 | Hancom에서 정상적으로 열림 | 파일이 곧바로 손상 파일이라는 뜻은 아니다. |
| 케빈랩 PDF 본문 추출 | 성공, 약 68,553자 추출 | 문서의 실제 본문 텍스트는 읽어 낼 수 있다. |
| HWP 파일 읽기/레코드 분해 | 정상 완료 | 파일 인식, 암호화 확인, 기본 레코드 분해 단계가 원인은 아니다. |
| 멈추는 지점 | 하이퍼링크 텍스트를 미리 찾는 단계 | 문서 전체 본문을 만드는 핵심 단계 이전의 보조 탐색에서 멈춘다. |
| 문제 바이트 | 문단 내부의 `03 00 0d 00` | 이 짧은 데이터에서 파서의 위치 이동이 멈춘다. |

## 3. 먼저 알아둘 말: 바이트, `03 00`, 제어 문자열

### 바이트는 문서 안의 아주 작은 숫자 조각이다

컴퓨터는 HWP 문서를 글자 그대로 저장하지 않고, 수많은 숫자 조각으로 저장한다. 숫자 하나가 보통 1바이트다. 개발자는 이 숫자를 보기 쉽게 16진수로 적는다.

```text
03 00 0d 00
```

위 표기는 문자 `0`, `3`이 아니라 네 개의 숫자 조각이다.

### `03 00`은 “특별한 표시가 시작됨”으로 읽힌다

현재 파서는 두 바이트를 묶어 읽는다. HWP는 작은 자리부터 저장하는 방식(리틀 엔디언)을 쓰기 때문에 `03 00`은 숫자 `0x0003`, 즉 값 3으로 해석된다.

쉽게 비유하면 본문에는 다음 두 종류가 섞여 있다.

```text
일반 글자:  "사업 기간은 6개월입니다"
특별 표시:  "여기부터 링크/필드/표 같은 특수 기능에 대한 안내입니다"
```

`0x0003`은 현재 파서가 두 번째 종류, 즉 **제어 문자열(control)** 의 시작 신호로 취급하는 값이다. 제어 문자열은 눈에 보이는 글자보다 “링크 시작”, “링크 끝”, “표”, “그림”처럼 문서 구조를 알려 주는 표지판에 가깝다.

### 제어 ID는 “어느 특별 표시끼리 한 쌍인지” 구분하는 번호다

하이퍼링크를 예로 들면, 파서는 링크 시작과 링크 끝을 서로 연결해야 한다. 이때 제어 ID는 “이 시작과 이 끝은 같은 링크입니다”라고 연결하는 번호 역할을 한다.

```text
링크 시작 [번호 27]  ────────────────  링크 끝 [번호 27]
```

중요한 점은, **제어 ID가 실제 HWP 명세에서 항상 4바이트인지, `0x0003`에 2바이트 ID 형식도 존재하는지는 아직 공식 명세로 확인하지 못했다**는 것이다. 아래 원인 설명은 현재 설치된 파서가 어떻게 동작하는지에 대한 확인 결과다.

## 4. 실제로 왜 멈췄나

현재 외부 라이브러리 `hwp_hwpx_parser`는 `0x0003`을 만나면 다음처럼 처리한다.

```text
1. 03 00을 제어 문자열 시작으로 본다.
2. 그 뒤 4바이트를 제어 ID라고 가정한다.
3. 총 6바이트(시작 2바이트 + ID 4바이트)를 읽은 뒤 다음 위치로 이동한다.
```

그런데 케빈랩의 해당 문단 끝에는 다음 네 바이트만 남아 있다.

```text
03 00 0d 00
^^^^^ ^^^^^
시작  뒤에 남은 데이터는 2바이트뿐
```

현재 파서는 4바이트 ID가 없다는 사실은 알아차린다. 하지만 그 경우에 다음 둘 중 아무것도 하지 않는다.

- 문단 탐색을 안전하게 끝내기
- 최소한 다음 바이트 위치로 이동하기

그래서 같은 위치의 `03 00`을 계속 읽는다. 책을 읽다가 모르는 표시를 만났는데, 페이지를 넘기지도 않고 같은 줄만 계속 보는 상황과 같다. 이 때문에 추출 프로세스가 끝나지 않아 600초 뒤 타임아웃이 발생했다.

```text
정상:  읽음 → 위치 이동 → 다음 데이터 읽음 → 끝
현재:  03 00 읽음 → ID 길이 부족 → 위치 이동 없음 → 03 00 다시 읽음 → 반복
```

## 5. 이것이 “케빈랩만의 문제”가 아닌 이유

새 RFP가 계속 들어오면 다음과 같은 문서는 언제든 추가될 수 있다.

- 서로 다른 한글 프로그램/버전으로 만들어진 HWP
- 문서 끝부분에 특수 필드, 링크, 주석, 표 제어 정보가 있는 HWP
- 명세상 허용되는 짧은 제어 형식이 있는 HWP
- 일부 제어 정보가 비정상적으로 끝났지만 본문은 정상인 HWP

따라서 파일명으로 케빈랩만 예외 처리하면 다음 유사 문서에서 다시 타임아웃이 난다. 필요한 것은 “케빈랩 예외”가 아니라 **어떤 입력도 파서를 무한 반복시키지 않는 일반 규칙**이다.

## 6. 해결 방법: 명세 확인 결과에 따른 두 갈래

### 경우 A. 명세상 `0x0003` 뒤에는 항상 4바이트 제어 ID가 와야 한다

이 경우 `03 00 0d 00`은 문단 끝의 불완전하거나 파서가 해석하지 못하는 제어 정보다.

처리 방향:

1. ID 4바이트가 부족하면 경고를 기록한다.
2. 해당 문단의 **하이퍼링크 사전 탐색만 종료**한다.
3. 문서 전체 본문 및 뒤의 다른 문단 추출은 계속한다.
4. 결과에 `partial_extract` 또는 경고 정보를 남긴다.

장점은 타임아웃을 막으면서 대부분의 본문을 살릴 수 있다는 점이다. 이 하이퍼링크 탐색은 본문 전체를 만드는 주 경로가 아니라 보조 단계이므로, 링크 표시 일부가 빠질 가능성은 있어도 문서 전체를 포기할 이유는 없다.

### 경우 B. 명세상 `0x0003` 뒤에 2바이트 제어 ID가 오는 별도 형식이 있다

이 경우 케빈랩 데이터는 정상 형식일 가능성이 있다. 단순히 건너뛰면 안 되고, 그 형식을 정식으로 파싱해야 한다.

처리 방향:

1. 명세가 정한 구분 조건으로 4바이트 ID 형식과 2바이트 ID 형식을 구분한다.
2. 2바이트 형식이면 `03 00 + 0d 00`을 하나의 완전한 제어 문자열로 읽는다.
3. 해당 ID가 링크 시작/끝/다른 제어 중 무엇을 의미하는지 명세대로 처리한다.
4. 읽은 길이만큼 반드시 위치를 이동한다.

주의: “남은 바이트가 2개면 일단 2바이트 ID로 읽자”는 방식은 위험하다. 정상 4바이트 형식의 데이터가 우연히 잘렸을 때 가짜 ID를 만들 수 있기 때문이다. 반드시 명세상 구분 규칙이 있어야 한다.

## 7. 권장 대응안

### 1단계: 무한 루프 방지부터 적용

명세 확인 여부와 관계없이, 파서는 한 번 반복할 때마다 반드시 위치가 앞으로 이동하거나 현재 문단 처리를 끝내야 한다. 이는 어떤 문서가 들어와도 전체 추출 작업이 멈추지 않게 하는 최소 안전장치다.

### 2단계: HWP 명세 및 라이브러리 구현 확인

- `0x0003`의 정확한 의미와 뒤따르는 데이터 길이를 공식 HWP 명세로 확인한다.
- 현재 라이브러리의 다른 제어 문자열 처리 방식과 비교한다.
- 2바이트 제어 ID 형식이 확인되면 별도 문법 분기를 구현한다.

### 3단계: 회귀 테스트 추가

실제 원본 RFP 파일 전체를 테스트에 넣지 않고, 아래처럼 최소 재현 데이터를 만든다.

```text
정상 4바이트 ID 제어 문자열
명세상 정상인 2바이트 ID 제어 문자열(존재한다면)
문단 끝에서 잘린 03 00 데이터
```

테스트 기준은 다음과 같다.

- 무한 루프/타임아웃이 없어야 한다.
- 정상 형식은 정확히 파싱되어야 한다.
- 알 수 없는 짧은 형식은 경고와 함께 안전하게 종료되어야 한다.
- 다른 99개 문서의 추출 결과가 깨지지 않아야 한다.

## 8. 팀 의사결정이 필요한 사항

| 결정 항목 | 이유 |
| --- | --- |
| HWP 명세 확인 담당 | 2바이트 ID 형식의 존재 여부에 따라 정답 구현이 달라진다. |
| 외부 라이브러리 수정 방식 | `.venv`를 직접 고치면 배포/VM에서 사라진다. 포크, 버전 고정, 업스트림 수정 제안 등 팀 방식이 필요하다. |
| 부분 추출 문서의 서비스 정책 | 본문 일부만 추출된 문서를 추천/질문에서 어떻게 표시할지 정해야 한다. |

## 9. 팀 공유용 요약

> 케빈랩 HWP는 열리지 않는 파일이 아니라, 현재 HWP 파서가 특정 제어 문자열을 만났을 때 다음 위치로 이동하지 못해 무한 반복에 빠지는 사례입니다. 새 RFP에서도 유사 사례가 나올 수 있으므로 케빈랩 파일만 예외 처리하면 안 됩니다. 우선 모든 제어 문자열 처리에서 “반드시 전진하거나 종료한다”는 안전장치를 넣고, `0x0003` 뒤 2바이트 제어 ID 형식의 존재 여부는 HWP 명세를 확인한 뒤 정식 파싱 분기를 결정하는 것이 권장 방향입니다.

## 부록: 조사 범위와 한계

- 이 보고서는 현재 프로젝트의 실행 결과와 설치된 `hwp_hwpx_parser` 코드 동작을 기준으로 작성했다.
- `03 00 0d 00`이 실제로 정상적인 2바이트 ID 형식인지, 또는 불완전한 제어 정보인지는 아직 공식 HWP 명세로 확정하지 않았다.
- 따라서 현재 단계에서 확정할 수 있는 것은 “이 데이터에서 현재 파서가 무한 반복한다”는 사실이며, 2바이트 형식을 구현할지는 명세 확인 후 결정해야 한다.
