HWP 파싱 타임아웃
원인 및 대응 보고서

케빈랩 HWP 1건의 추출 실패를 분석하고, 새 RFP가 계속 유입되는 환경에서 같은 문제가 재발하지 않도록 대응 방향을 제안합니다.

작성일 2026. 07. 29. 대상 케빈랩 주식회사 RFP HWP 범위 원인 분석 및 대응 방향

01 결론부터

케빈랩 HWP는 “열리지 않는 깨진 파일”로 단정할 수 없습니다. 한글(Hancom)에서 정상적으로 열리고, PDF로 바꾼 뒤에는 본문 약 68,553자도 추출됐습니다. 직접적인 문제는 현재 HWP 파서가 특정 짧은 제어 문자열에서 다음 위치로 이동하지 못해 같은 데이터만 반복해서 읽는 것입니다.

결론

케빈랩만 파일명으로 예외 처리하지 말고, 어떤 새 RFP가 들어와도 파서가 멈추지 않도록 “반드시 전진하거나 안전하게 종료한다”는 공통 규칙을 적용해야 합니다.

02 확인된 사실

전체 재추출 결과 99 / 100 99건 성공, 케빈랩 1건만 600초 타임아웃
원본 문서 상태 정상 열림 Hancom에서 문서 내용을 확인할 수 있음
PDF 본문 추출 68,553자 PDF 변환본에서 본문 텍스트 추출 성공
확정된 범위: HWP를 읽기 시작하고 내부 레코드를 나누는 단계는 완료됩니다. 멈추는 곳은 “하이퍼링크 관련 텍스트를 미리 찾는 보조 단계”입니다.

03 03 00 0d 00는 무엇인가

HWP 파일 내부는 글자만 저장된 텍스트 파일이 아닙니다. 글자, 표, 그림, 링크처럼 문서 구조를 표현하기 위한 많은 숫자 조각이 들어 있습니다. 개발자는 이 숫자를 보기 쉽게 16진수로 표시합니다.

03 00 0d 00

문제 위치에서 남아 있던 네 개의 바이트. 문자 “03”이 아니라 컴퓨터가 읽는 숫자 네 조각입니다.

바이트(byte)

컴퓨터가 문서를 저장하는 아주 작은 숫자 단위입니다. 위 값은 바이트 네 개를 16진수로 적은 것입니다.

03 00 → 0x0003

현재 파서는 이 두 바이트를 묶어 값 3으로 읽고, “특별한 문서 구조가 시작된다”는 신호로 취급합니다. HWP는 작은 자리부터 저장하므로 03 00 순서입니다.

제어 문자열(control)

눈에 보이는 본문 글자가 아니라 링크, 필드, 표 같은 문서 구조를 알려 주는 표지판입니다.

제어 ID(control ID)

예를 들어 링크의 시작과 끝을 연결하기 위한 번호입니다. “이 시작과 이 끝은 같은 링크”라고 묶는 식별자 역할을 합니다.

링크 시작 [제어 ID 27]  ────────────────  링크 끝 [제어 ID 27]
중요: 0x0003 뒤에 실제로 항상 4바이트 ID가 오는지, 2바이트 ID인 별도 형식도 있는지는 아직 공식 HWP 명세로 확정하지 않았습니다. 아래 원인은 “현재 설치된 파서가 어떻게 동작하는가”에 대한 확인 결과입니다.

04 실제로 왜 600초 동안 멈췄나

현재 외부 라이브러리는 0x0003을 만나면 “뒤에 제어 ID 4바이트가 더 있다”고 가정합니다. 즉, 제어 시작 2바이트와 ID 4바이트를 합쳐 최소 6바이트가 필요하다고 봅니다.

STEP 0103 00 발견특별한 제어 문자열의 시작으로 판단
STEP 02뒤 4바이트 ID 필요총 6바이트를 읽으려 함
STEP 03실제 남은 값은 2바이트0d 00만 남아 있어 조건 불충족
STEP 04위치 이동이 없음같은 03 00을 다시 읽으며 무한 반복

비유하면 책을 읽다가 모르는 표식을 만났는데, 페이지를 넘기거나 다음 문장으로 가지 않고 같은 줄만 계속 읽는 상황입니다. 타임아웃은 문서 분석이 오래 걸려서가 아니라 이 반복이 끝나지 않아서 발생했습니다.

05 왜 케빈랩만 예외 처리하면 안 되나

앞으로 들어올 수 있는 문서재발 가능성
다른 한글 프로그램·버전에서 작성된 HWP같은 제어 문자열이 다른 방식으로 저장될 수 있습니다.
문서 끝에 링크·필드·주석·표 정보가 있는 HWP짧거나 예상하지 못한 제어 정보가 나올 수 있습니다.
본문은 정상인데 일부 구조 정보가 불완전한 HWP본문까지 포기할 필요는 없지만 파서가 멈출 수 있습니다.

따라서: 파일명에 “케빈랩”이 들어가면 다른 방식으로 처리하는 예외는 다음 문서에서 다시 실패합니다. 입력 파일과 무관하게 동작하는 안전 규칙이 필요합니다.

06 명세 확인 결과에 따른 해결 방법

경우 A. 4바이트 ID만 정상 형식인 경우

남은 2바이트는 불완전하거나 현재 파서가 모르는 제어 정보입니다.

  • 경고를 기록합니다.
  • 현재 문단의 하이퍼링크 사전 탐색만 끝냅니다.
  • 나머지 본문 추출은 계속합니다.
  • 결과를 부분 추출 상태로 표시합니다.

경우 B. 2바이트 ID 별도 형식이 있는 경우

03 00 0d 00은 정상적인 완성 데이터일 수 있습니다.

  • 명세의 구분 조건으로 2·4바이트 형식을 나눕니다.
  • 2바이트 ID를 정식으로 읽고 의미를 처리합니다.
  • 읽은 길이만큼 위치를 앞으로 이동합니다.
  • 이 형식을 회귀 테스트에 추가합니다.
피해야 할 방법: “남은 바이트가 2개면 무조건 2바이트 ID로 읽자”는 방식입니다. 원래 4바이트여야 할 데이터가 우연히 끝에서 잘린 경우, 존재하지 않는 ID를 만들어 낼 수 있습니다. 2바이트 형식은 명세상 구분 규칙이 확인됐을 때만 처리해야 합니다.

07 권장 실행 순서

명세 확인 전에도 할 수 있는 안전 조치와, 명세 확인 후 해야 할 정확한 파싱을 분리합니다.

  1. 무한 반복 방지모든 제어 문자열 처리에서 한 번 반복할 때마다 위치가 전진하거나, 현재 문단 처리를 끝내도록 보장합니다.
  2. HWP 명세 확인0x0003의 정확한 의미와 뒤따르는 ID 길이, 2바이트 형식의 존재 여부를 공식 명세로 확인합니다.
  3. 정식 분기 구현명세상 2바이트 형식이 있으면 별도 분기로 처리하고, 없으면 경고와 함께 안전하게 보조 탐색을 종료합니다.
  4. 회귀 테스트 추가정상 4바이트 형식, 정상 2바이트 형식(존재 시), 문단 끝의 짧은 제어 데이터를 최소 재현 테스트로 고정합니다.
  5. 서비스 상태 구분정상 추출, 부분 추출, 파서 오류, 타임아웃을 구분해 추천·질문 단계에서 근거 없는 답변을 막습니다.

08 팀에 공유할 한 문장

회의·메신저용 요약

“케빈랩 HWP는 파일 자체가 깨진 사례라기보다, 현재 파서가 특정 제어 문자열을 만났을 때 위치를 전진시키지 않아 무한 반복에 빠지는 사례입니다. 새 RFP에서도 유사 문서가 들어올 수 있으므로 파일별 예외 대신, 파서가 항상 전진하거나 안전하게 종료하도록 만들고, 2바이트 제어 ID 형식의 존재 여부는 HWP 명세 확인 후 정식 지원 여부를 결정해야 합니다.”

조사 기준: 프로젝트의 실제 재추출 결과, 케빈랩 HWP/PDF 추출 결과, 설치된 hwp_hwpx_parser의 실행 흐름.  |  이 문서는 원인 공유와 의사결정을 위한 보고서이며, HWP 명세 미확인 부분을 확정 사실로 취급하지 않습니다.
