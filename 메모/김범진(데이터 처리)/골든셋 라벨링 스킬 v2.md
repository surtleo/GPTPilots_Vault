# 골든셋 라벨링 스킬 v2

> 사람 없이 정답 청크를 라벨링하는 에이전트용 지시서. **검증 라운드 2 진행 중.**
> 검증 절차 → [[골든셋 200문항 확장 계획]] · 라운드 기록 → [[골든셋 라벨링 스킬 검증 기록]] · v1 → [[골든셋 라벨링 스킬 v1]]

**v1에서 바뀐 핵심**: R2를 반전했다. v1은 "최소 집합"을 지시했는데 사람은 근거를 담은 청크를
전부 넣었다. 이 오지시 하나로 16문항이 틀렸다. v2는 **포괄 수집**이다.

## 네가 하는 일

질문 하나마다 **후보 청크 30~40개**와 **기준답변**이 주어진다.
후보 중에서 **기준답변의 근거가 되는 청크를 전부** 골라 `chunk_id` 목록으로 낸다.

근거가 하나도 없으면 **빈 목록**을 낸다. 이건 실패가 아니라 정답일 수 있다.

## 이 골든셋이 쓰이는 곳 — 이걸 알아야 판단이 선다

너의 라벨은 **검색 엔진 성능 측정**에 쓰인다.
"검색이 이 질문에 대해 **찾아냈어야 할 청크 목록**"이 곧 정답이다.

그래서 판단의 기준선은 이거다.

> **검색이 이 청크를 가져왔다면, 답변에 도움이 됐을까?**

됐으면 정답이다. 같은 사실을 담은 청크가 셋이면 **셋 다 정답**이다.
검색이 그중 아무거나 가져와도 답변이 되기 때문이다.

## 절차

### 1단계 — 기준답변에서 검증할 사실을 뽑는다

기준답변을 읽고 **확인해야 할 사실 조각**을 나열한다. 이게 채점표가 된다.

```
기준답변: "사업기간은 계약일로부터 3개월이며, 안정화기간 1개월이 포함된다."
    → 사실 ①  사업기간 = 계약일로부터 3개월
    → 사실 ②  안정화기간 1개월 포함
```

### 2단계 — 후보 전체를 훑으며 사실을 담은 청크를 표시한다

**반드시 후보를 처음부터 끝까지 다 읽어라.** 상위 몇 개만 보고 끊지 마라.
각 사실마다 그것을 담은 청크 번호를 전부 적는다.

### 3단계 — 표시된 청크를 전부 고른다

**최소 집합을 만들려 하지 마라.** 사실을 담고 있으면 전부 정답이다.

### 4단계 — R1~R9 체크리스트로 걸러낸다

## 반드시 지킬 규칙

### R1. 다른 문서의 청크는 절대 고르지 않는다

후보에는 **다른 사업의 청크가 섞여 있다.** 검색에 문서 필터가 없기 때문이다.

각 후보의 `doc_id`가 `target_doc_id`와 **정확히 같은지** 확인하고, 다르면 내용이 아무리
그럴듯해도 버린다. 예외 없다.

> 사람이 라벨링했을 때 이 오류가 3건 나왔다. 화면에 문서명이 없어서다.
> 너는 `doc_id`가 보이므로 변명의 여지가 없다.

### R2. 같은 사실이 여러 청크에 있으면 전부 고른다 ★

**이게 v1에서 가장 크게 틀렸던 규칙이다.** v1은 "최소 집합"을 지시했는데 반대였다.

RFP는 같은 사실을 여러 곳에 반복 기재한다. 구조적으로 그렇다.

| 중복 유형 | 예 |
|---|---|
| 사업개요 ↔ 제안요청 개요 | 같은 문장이 앞뒤로 두 번 |
| 과업내용 ↔ 요구사항 명세(SFR/ECR) | 서술형과 요구사항 표에 각각 |
| 요구사항 총괄표 ↔ 상세 요구사항 | 고유번호↔명칭 매핑이 두 벌 |
| 평가 기준표 ↔ 등급별 평점표 | 배점이 두 벌 |

**이 경우 전부 고른다.** 검색이 어느 쪽을 가져와도 답이 되기 때문이다.
"어느 쪽이 더 정확한가"를 고민하지 마라 — 그건 이 작업이 답할 질문이 아니다.

단, **사실을 담지 않은 청크는 여전히 배제한다.** 중복이라고 무조건 넣는 게 아니라,
"이 청크만 읽고 그 사실을 알 수 있는가"를 각각 판단해서 통과한 것만 넣는다.

### R3. 다만 개수 채우기는 금지다

R2는 "근거가 있으면 다 넣어라"이지 "많이 넣어라"가 아니다.

- 사실을 **부분적으로만 스치는** 청크는 넣지 마라 (예: 사업명만 같고 내용은 무관)
- "2개쯤 있어야 할 것 같다"는 이유로 추가하지 마라
- 근거가 되는 청크가 1개면 1개, 0개면 0개다

골든셋에 틀린 정답이 들어가면 이후 모든 실험이 오염된다.
**빠뜨린 정답 하나보다 잘못 넣은 정답 하나가 3배 해롭다.**

경계선: 그 청크를 검색 결과로 받은 사람이 **"이건 답이 아니네"라고 할 것 같으면** 빼라.

### R4. 서식·보일러플레이트에 흩어진 사실은 상한 3개 ★

발주기관·사업명 같은 사실은 계약 서식(접수증·인감계·서약서 등)에 **열 군데씩** 나온다.
이건 R2의 의미 있는 중복이 아니라 잡음이다.

같은 사실을 담은 청크가 **4개를 넘으면**, 그중 **질문 문구에 가장 가까운 3개**만 고른다.

```
질문: "발주 기관은 어디인가요?"
  ::0239  "인천광역시에서 발주하는『도시계획위원회…』"   ← '발주' 일치, 우선
  ::0225  "인천광역시에서 시행하는『도시계획위원회…』"   ← 차선
  ::0235  "인천광역시에서 시행하는『도시계획위원회…』"   ← 차선
  (그 외 서식 7개는 제외)
```

우선순위: ① 질문의 핵심어와 표현이 일치 → ② 본문 절(사업개요·과업내용) → ③ 부록 서식

### R5. 기준답변의 사실 일부만 후보에 있으면, 있는 것만 고른다 ★

후보는 검색 결과라서 **기준답변의 근거를 다 담지 못할 수 있다.**

이때 **빈 목록을 내지 마라.** 후보에 있는 사실을 담은 청크는 고르고,
`reason`에 **어떤 사실의 근거가 없었는지 반드시 명시**한다.

```json
{"gold_chunk_ids":["문서::0006","문서::0007"],
 "reason":"사실①(IRB 업무)은 ::0006, 사실②(동물실험)은 ::0007에 있다. 사실③(연구비카드·전자세금계산서 연계)의 근거는 후보 40개 어디에도 없다.",
 "confidence":"보통"}
```

빈 목록은 **어떤 사실의 근거도 후보에 없을 때만** 낸다.

> 사람이 이 규칙이 없어서 실제로 틀렸다. 사실 셋 중 둘의 근거가 후보에 있었는데
> 나머지 하나가 없다는 이유로 "정답 없음"으로 넘겨버렸다.

### R6. 표기가 달라도 같은 값이면 정답이다

문서와 기준답변이 **다른 표기법**을 쓰는 일이 흔하다. 숫자를 정규화해서 비교하라.

| 기준답변 | 문서 표기 | 판정 |
|---|---|---|
| `40,000,000원` | `40,000천원` | **같음 — 정답** |
| `3.8억원` | `380,000,000원` | 같음 |
| `제2019-69호` | `행정안전부고시 제2019-69호` | 같음 |
| `210일` | `7개월` | 다름 — 근거 부족 |

단위(천원·백만원·억원)를 원 단위로 환산한 뒤 비교한다.

### R7. 글자가 깨져 있어도 내용으로 판단하라

hwp 추출 오류로 청크 머리에 이런 문자가 붙는 경우가 있다.

```
楴䵴楴䵴4. 제안요청 내용
 3) 사업금액 : 40,000천원(부가세 포함)
```

`楴` `䵴` `䛄` `䱴` `䖴` 같은 한자 비슷한 문자는 **파싱 쓰레기**다. 무시하고 나머지를 읽어라.
이것 때문에 사람이 정답을 놓친 사례가 있다.

마크다운 표가 파이프와 빈 칸투성이라 읽기 어려워도 **답이 그 안에 있으면 정답이다.**
서식이 아니라 내용으로 판단하라.

```
|  |  |  |
| --- | --- | --- |
|  | 소형 쉘터형 : 50대 |  |      ← 읽기 나쁘지만 정답임
```

### R8. 정답이 인접 청크로 쪼개졌으면 둘 다 골라라

500자 경계가 표 중간을 자르는 일이 잦다. `::0059`와 `::0060`처럼 **번호가 연속인 청크**가
하나의 표에서 갈라져 나온 것이면, 기준답변의 사실이 양쪽에 나뉘어 있는지 확인하라.

```
::0059  | 요구사항 고유번호 | ECR-002 |  ← 번호는 여기
::0060  세부내용 … 소형 쉘터형 : 50대 …   ← 내용은 여기
```

한쪽만으로 사실이 성립하지 않으면 **둘 다** 고른다.

**단, 표가 5조각 이상으로 쪼개진 경우** 사실을 담은 조각만 고른다.
예: 요구사항 건수 표가 ::0030~::0034로 쪼개졌고 질문이 "총합"이면,
합계 행이 있는 ::0034만 고른다. 나머지 조각은 그 사실을 담지 않는다.

### R9. 거의 똑같은 청크는 식별자로 가려라

같은 양식의 표가 여러 벌 있는 문서에서는, 잘린 뒤 조각들이 **글자가 거의 같아진다.**

```
후보 25  냉각 FAN(최소 2개이상) … 서지보호기 2P 40kA …   ← 어느 타입인지 안 적혀 있음
후보 26  냉각 FAN(최소 2개이상) … 서지보호기 2P 40kA …
후보 27  냉각 FAN(최소 2개이상) … 서지보호기 2P 40kA …
```

`섹션` 필드와 `chunk_id` 순번을 보고, **식별자를 담은 앞 조각**이 후보에 있는지 확인하라.
있으면 그것으로 어느 타입인지 특정한다.

**특정이 불가능하면 추측하지 말고 고르지 마라.** 넷 중 하나를 찍는 것은 R3 위반이다.
이건 R2의 "전부 고르기" 대상이 아니다 — 셋 중 둘은 **다른 사실**(다른 타입)을 담고 있기 때문이다.

### R10. 기준답변에 없는 내용이 담겼다고 배제하지는 마라

청크는 대개 기준답변보다 길다. 기준답변의 사실을 **담고 있으면** 정답이고,
그 외에 다른 내용이 더 있는 것은 문제가 아니다.

## 유형별 추가 지침

| 유형 | 지침 |
|---|---|
| `단일세부` | 기본 절차 그대로 |
| `후속` | `선행_턴`의 대명사("그 사업")를 선행 질문의 대상으로 치환한 뒤 판단한다. **채점표는 `expected`의 사실만이다** — 선행 턴의 답까지 덮을 필요는 없다 |
| `직답` | 본문에 값이 있으면 그것을 담은 청크를 고른다(R4 상한 적용). 금액·마감일이 `data_list.csv` 메타에만 있고 **본문에 없으면 빈 목록** |
| `탐색비교` | `대상_doc_id`가 리스트다. **문서마다 근거를 따로** 고르고 합친다. R1은 "목록에 있는 문서면 허용"으로 완화 |
| `모른다` | 근거가 없어야 정상이다. 빈 목록이 기대값. 그럴듯한 청크를 찾아 넣지 마라 |
| `반문` | 대상 문서 자체가 없다. 항상 빈 목록 |

## 출력 형식

문항마다 JSON 한 줄(JSONL):

```json
{"qid":"기존:af85ee75","gold_chunk_ids":["문서::0005","문서::0010"],"facts":["사업기간=계약일로부터 3개월","안정화기간 1개월 포함"],"reason":"::0005(사업개요)와 ::0010(구축일정)이 같은 사실을 각각 담고 있어 R2에 따라 둘 다 선택","uncovered":[],"confidence":"높음"}
```

| 필드 | 내용 |
|---|---|
| `qid` | 입력 그대로 |
| `gold_chunk_ids` | 고른 청크의 `chunk_id`. **후보에 있는 것만.** 없으면 `[]` |
| `facts` | 1단계에서 뽑은 사실 조각 |
| `reason` | 왜 이 조합인가. 적용한 규칙 번호를 함께 적어라 |
| `uncovered` | 후보에 근거가 없던 사실 (R5). 없으면 `[]` |
| `confidence` | `높음` / `보통` / `낮음` — 애매하면 솔직히 낮음 |

## 제출 전 자가 점검

문항마다 확인한다.

- [ ] 후보를 **처음부터 끝까지** 읽었는가 (2단계)
- [ ] 같은 사실을 담은 다른 청크를 빠뜨리지 않았는가 (R2) ← **v1의 최대 실패 지점**
- [ ] 고른 청크의 `doc_id`가 전부 `target_doc_id`와 같은가 (R1)
- [ ] 고른 청크 하나하나가, 그것만 읽어도 어떤 사실을 알려주는가 (R3)
- [ ] 같은 사실 청크가 4개 넘는데 상한을 안 걸었는가 (R4)
- [ ] 사실 일부만 있는데 빈 목록으로 내지 않았는가 (R5)
- [ ] `chunk_id`를 지어내지 않았는가 — 전부 후보 목록에 있는가
- [ ] 빈 목록으로 낸 문항은, 정말 후보 전체를 다 읽고 없다고 판단한 것인가
