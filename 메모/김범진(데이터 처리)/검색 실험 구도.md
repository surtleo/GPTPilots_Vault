# 검색 실험 구도

BM25 하이브리드와 크로스인코더 리랭커를 **넣을지 말지 판단하기 위한** 실험 설계 + 측정 계획.
평가 문항 전수는 [[검색 실험 골든셋 40문항]], 구조도는 [[검색 품질 개선 (BM25·리랭커)]], 여기까지 온 경위는 [[검색 개선 이력]].

핵심 전제 한 줄: **좋아 보이니까 넣는 게 아니라, 미리 정한 숫자를 넘겨야 넣는다.**

---

## 1. 왜 실험을 다시 설계했나

Plans 6.1에서 이미 6개 변형을 비교했는데 **`hit@5`가 전부 1.000**이었다. 검색을 바꿔도 숫자가 안 움직이니 무엇이 나은지 판단이 불가능.

원인은 지표가 **문서 단위**라는 것. 청킹이 모든 청크 앞에 `사업명+발주기관`을 붙이기 때문에 어떤 청크가 뽑히든 "정답 문서에서 뽑혔다"는 항상 참이 된다. 즉 지표가 검색기가 아니라 청킹 접두어를 재고 있었다.

> 그래서 실험 코드보다 **지표를 먼저** 새로 만들었다. 지표가 변별을 못 하면 그 뒤 실험은 전부 무의미하다.

---

## 2. 무엇을 비교하나

### 2-1. 뼈대는 2×2 전수 (사전등록)

BM25와 리랭커는 서로 독립적인 축이라, 하나씩 켜보는 게 아니라 **4칸을 전부** 돈다. 그래야 "둘 다 켜야만 좋아지는지 / 하나만으로 충분한지"가 갈린다.

| | 리랭커 OFF | 리랭커 ON |
|---|---|---|
| **BM25 OFF** | `A_dense` — 베이스라인 | `C_rerank` |
| **BM25 ON** | `B_hybrid` | `D_hybrid_rerank` |

### 2-2. 라벨링 뒤 3개를 더 붙였다 (탐색)

라벨링 실패 4건을 실측해보니 **원안 4변형만으로는 답이 안 나오는 질문**이 두 개 생겼다.

| 실측 | 원안이 답 못 하는 질문 |
|---|---|
| 전체 질문으로 넣으면 160위, 핵심어만 넣으면 2위 (4건 모두 1~4위) | BM25가 나쁜 건가, **우리가 질문을 잘못 넣은 건가**? |
| 정답이 dense 23·35·94위에 있는데 후보 top-20에서 잘림 | 알고리즘 문제인가, **후보 깊이 설정 문제**인가? |
| 정답이 표면 dense 중앙값 10위(진입 70%), 줄글이면 4위(87%). BM25는 표에서 대등 | **하이브리드 이득이 표 문항에서만** 날 가능성 |

### 2-3. 최종 변형 목록

| 변형 | BM25 | 리랭커 | 후보 K | 쿼리 | 성격 |
|---|---|---|---|---|---|
| **A_dense** | ✗ | ✗ | 20 | 원문 | 베이스라인 |
| **B_hybrid** | ✓ | ✗ | 20 | 원문 | 사전등록 |
| **C_rerank** | ✗ | ✓ | 20 | 원문 | 사전등록 |
| **D_hybrid_rerank** | ✓ | ✓ | 20 | 원문 | 사전등록 |
| **B′_kw** | ✓ | ✗ | 20 | **핵심어** | 탐색 |
| **E_deep** | ✗ | ✓ | **40** | 원문 | 탐색 |
| **F_all** | ✓ | ✓ | **40** | **핵심어** | 탐색 |

- **핵심어 쿼리** = BM25에 넣기 전 질문에서 저IDF 토큰을 걸러낸다. dense 쿼리는 원문 그대로 둔다(임베딩은 문맥이 있어야 함).
- 후보 K는 `RERANK_CANDIDATE_K`. 최종 반환은 모든 변형이 top-5로 동일.
- 전 변형이 **같은 프로세스에서 config 플래그만 토글**해서 돈다. 인덱스·질문·정답이 동일하므로 차이는 오직 검색 경로에서만 온다.

> **사전등록 vs 탐색은 섞지 않는다.**
> A~D는 결과를 보기 전에 승격 기준까지 정해뒀다. B′·E·F는 라벨링 진단을 본 **뒤에** 추가했다.
> 따라서 **승격 판정은 A~D로만** 하고, B′·E·F는 "다음에 뭘 고칠지"를 정하는 참고 자료로만 쓴다.
> 이 구분을 흐리면 결과를 보고 기준을 만든 셈이 되어 실험이 무의미해진다.

### 2-4. 리랭커 모델은 별도 축 (탐색)

한국어 전용 리랭커가 다국어 모델보다 나은지도 봐야 한다. 단 이걸 위 표에 곱하면 변형이 14개가 되므로 **별도 축으로 뺀다.**

가능한 이유: **리랭커 모델 비교는 후보를 고정한 채 점수만 다시 매기면 된다.** 검색 단계를 다시 돌 필요가 없다.

```
검색(dense/BM25) 1회 → 후보 20개 확정   ← 모델 바꿔도 불변
        ↓ 이 20개를 모델별로 재배열해서 MRR 비교
문항 35 × 후보 20 = 모델당 700쌍
```

A~F 중 가장 좋은 후보 구성 위에서, 두 모델만 스윕한다.

| 모델 | 용량 | 최대 길이 | 라이선스 | 역할 |
|---|---|---|---|---|
| `BAAI/bge-reranker-v2-m3` | 2.27 GB | 8194 | Apache-2.0 | 기준선 (현행) |
| `upskyy/ko-reranker-8k` | 2.27 GB | 8194 | Apache-2.0 | 한국어 파인튜닝본 |

**이 둘로 좁힌 이유** — ko-reranker-8k는 모델 카드상 **v2-m3를 한국어 데이터(ko-wiki-reranking)로 파인튜닝한 것**이다. 구조·토크나이저·최대 길이가 전부 동일하므로 **변수가 "한국어 파인튜닝" 하나뿐**인 통제된 비교가 된다. 코드는 `RERANK_MODEL` 상수 한 줄만 바뀐다.

탈락:

| 모델 | 탈락 사유 |
|---|---|
| `Dongjin-kr/ko-reranker` | 최대 길이 **514** → `parent_text` 경로를 막는다 (아래) |
| `BAAI/bge-reranker-base` | 512 + v2-m3보다 낮은 성능. 비교 가치 없음 |
| `jinaai/jina-reranker-v2-base-multilingual` | **CC-BY-NC(비상업)** |

### 512 제한이 왜 탈락 사유인가 — 실측

리랭커에 넣는 텍스트의 토큰 길이 (XLM-R 토크나이저 기준):

| 리랭커 입력 | 중앙값 | p90 | 512 초과 |
|---|---|---|---|
| **청크 본문** (현행) | 148 | 276 | **0%** |
| **`parent_text`** (표 전문, 개선 후보) | 454 | 1,527 | **46%** |

지금 입력이라면 512 모델도 무해하다. 그러나 **표 전문을 넣는 개선을 하면 절반이 잘린다** — 표는 앞부분만 남고 뒤가 날아가는데, 실패 사례 상당수가 표 문항이다. 그 길을 막지 않으려면 8k 모델이어야 한다.

### 모델 교체 판정 기준 (사전 확정)

> 동일 후보 위에서 **MRR@10 +0.03 이상**이면 교체. 미만이면 `bge-reranker-v2-m3` 유지.

이것도 라벨링 결과를 본 뒤 추가한 축이므로 **A~D 승격 판정에는 넣지 않는다.**

### 왜 RRF인가
코사인 유사도(0~1)와 BM25 점수(상한 없음)는 스케일이 달라 그냥 더할 수 없다. RRF는 **점수를 버리고 순위만** 쓴다.

```
score(청크) = Σ  1 / (60 + 그 검색기에서의 순위)
```

정규화 파라미터를 튜닝할 필요가 없어서, "융합 방식을 잘못 맞춰서 졌다"는 변명이 안 나온다.

## 3. 무엇으로 재나 — 순위 민감 지표

| 지표 | 보는 것 | 왜 필요 |
|---|---|---|
| **MRR@10** | 첫 정답이 몇 등에 있나 (`1/등수`) | **주 지표.** 1등↔3등 차이를 잡는다 |
| **nDCG@10** | 정답 여러 개가 위쪽에 몰렸나 | 정답 2개 이상인 문항이 22개 |
| **Recall@5** | 실제 쓰이는 top-5 안에 몇 개 들어왔나 | 생성이 받는 컨텍스트의 실질 품질 |
| `hit@5` | (기존) 정답 문서가 뽑혔나 | **회귀 감시용으로만** — 1.0에서 안 떨어지는지 |

구현: `src/eval/ir_metrics.py`. 순수 함수 + stdlib만, 외부 의존 없음.

## 4. 무엇에 대고 재나

### 라벨링한 문항 40개 → 측정 대상 35개

| | 수 | |
|---|---|---|
| 라벨링 전수 | 40 | 기존 30 · 어휘형 10 |
| − 검색 미검출 | 4 | 정답 근거가 후보 풀 밖 |
| − 검색 대상 아님 | 1 | 문서에 근거 자체가 없음 |
| **측정 대상** | **35** | **기존 26 · 어휘형 9** |

정답 청크 72개, 문항당 평균 2.1개. 인덱스는 `data/chroma_v2` (30,002청크, 표 헤더 승격 반영본).

**어휘형 10문항을 따로 만든 이유** — BM25가 이기라고 만든 게 아니라, **BM25가 이겨야 정상인 구간이 실제로 있는지** 확인하려고. 고유번호(SFR-03)·법령 조항·정확한 기관명처럼 임베딩이 뭉개기 쉬운 표층 문자열을 묻는 질문들이다. 여기서도 BM25가 못 이기면 도입 근거가 없다.

### 보고는 두 축으로 분할한다

| 축 | 분할 | 왜 |
|---|---|---|
| 문항 출처 | 전체 35 / 기존 26 / 어휘형 9 | 어휘형만 좋아지고 기존이 나빠지는 건 개선이 아니라 트레이드오프. 합쳐 평균 내면 그게 숨는다 |
| **정답 소재** | **표 정답 / 줄글 정답** | dense는 표에서 약하고(중앙값 10위·진입 70%) 줄글에서 강하다(4위·87%). BM25는 표에서 대등. 하이브리드 효과가 표 문항에서 갈릴 것으로 예상 |

추가로 **중복 청크 문항 19개를 뺀 재계산**을 함께 낸다. 그 문항들은 정답과 오답의 텍스트가 거의 같아 리랭커가 구분할 근거가 없고, 점수 차이가 운에서 나온다.

## 5. 정답은 어떻게 정하나 — TREC 풀링

정답 청크를 사람이 처음부터 찾는 건 30,000개 중에서 고르는 일이라 불가능. 대신 **두 검색기가 건진 것만 후보로 놓고** 그중에서 고른다.

```
후보 = dense top-20  ∪  BM25 top-20     → 문항당 30~40개, 총 1,438개
```

실측 후보 분포 (`data/rerank_pool.jsonl`, 재인덱싱 후):

| | 후보 수 |
|---|---|
| dense만 찾음 | 638 |
| BM25만 찾음 | 638 |
| 둘 다 찾음 | 162 |

**겹침이 11%밖에 안 된다.** → BM25가 dense가 못 보던 청크를 실제로 건져 올리고 있다 = **실험에 변별력이 있다.**

### 라벨링 3단계 (사람 부담 최소화)
1. 기계가 기준답변과 청크 본문의 **내용어 겹침**으로 후보를 점수화 → 상위 3개를 제안
2. 사람은 **엔터로 승인하거나 번호로 수정**만
3. 애매한 건 `v<번호>`로 전문을 펼쳐 확인

겹침 점수는 **질문이 아니라 기준답변**에 대고 잰다. 질문에 대고 재면 BM25가 찾기 쉬운 청크가 정답으로 뽑히는 **자기충족 편향**이 생긴다.

실제 라벨링에서 드러난 문제와 교훈은 [[검색 실험 골든셋 40문항]], 그 원인이 된 데이터 손상은 [[인덱스 데이터 손상 진단]].

## 6. 언제 채택하나 — 승격 기준 (측정 전 확정, 변경 없음)

> 변형이 베이스라인 A 대비
> **① 전체 문항 MRR@10 +0.05 이상** 개선하고
> **② 기존 문항 hit@5 = 1.0 유지**하면 → 프로덕션 반영 (config 플래그 ON)
>
> 하나라도 미달 → **미채택으로 기록**, 코드는 플래그 OFF로 남김
> 여러 변형이 통과하고 MRR 차이가 **0.02 이내면 더 단순한 쪽** (A < B,C < D)

**결과를 보기 전에 못 박은 이유** — 숫자를 본 뒤에 기준을 정하면 어떤 결과든 "성공"으로 해석할 수 있다. +0.03이 나왔을 때 "그래도 개선이니까"라고 말하지 않기 위한 사전 구속.

**더 단순한 쪽 우대**는 리랭커가 공짜가 아니기 때문. 568M 모델을 매 질의마다 20개 청크에 돌리는 비용·지연·GPU 메모리를, 0.02 차이로는 정당화할 수 없다.

## 7. 실행 순서

### 1단계 — GPU 없이 지금 (로컬 CPU)

`A` · `B` · `B′`. 리랭커가 없어 CPU로 돈다. **BM25의 순수 효과와 쿼리 처리의 효과를 먼저** 확인한다.

판단 갈림길:
- `B′ ≫ B` → 문제는 BM25가 아니라 **쿼리 처리**였다. 알고리즘 교체(BGE-M3 등) 불필요
- `B′ ≈ B ≈ A` → BM25 자체가 이 코퍼스에서 힘을 못 쓴다. 대안 검토 대상

### 2단계 — GPU 확보 후 (VM L4)

`C` · `D` · `E` · `F`. 리랭커 1,600~3,200회 추론. CUDA fp16, **맥 MPS 경로는 쓰지 않는다** — 로컬과 VM의 수치가 갈리면 비교 자체가 무너진다.

**선결 과제**: VM 디스크가 96G 중 1.7G만 남아 모델을 하나도 못 받는다. 두 모델이면 **4.5GB** 필요. 디스크 확보가 먼저다. 차선책은 맥 CPU 측정(20~40분).

### 2-5단계 — 리랭커 모델 스윕

2단계에서 가장 좋았던 후보 구성을 고정하고, `bge-reranker-v2-m3` ↔ `upskyy/ko-reranker-8k` 만 갈아끼워 700쌍씩 재채점한다. 검색을 다시 안 돌아 몇 분이면 끝난다.

### 3단계 — 결과 해석

| 관측 | 해석 | 다음 행동 |
|---|---|---|
| E ≫ C | 병목은 알고리즘이 아니라 **후보 깊이** | `RERANK_CANDIDATE_K` 상향 (설정 한 줄) |
| B′ ≫ B | 병목은 **쿼리 처리** | 저IDF 필터를 프로덕션에 반영 |
| F ≈ D | 추가 조치의 효과 없음 | 원안 판정대로 진행 |
| ko-8k > m3 +0.03 | 한국어 파인튜닝이 유효 | `RERANK_MODEL` 교체 |
| 전부 A와 비슷 | 순위 문제가 아님 | **인제스트(표 처리)로 투자 전환** |

| 모델 스윕 | 고정 후보를 재채점하는 경로. `RERANK_MODEL`을 인자로 받게 | 소 |

플래그 기본값은 계속 OFF. 측정 스크립트가 변형별로 토글할 뿐 프로덕션 동작은 안 바뀐다.

## 9. 비용

**OpenAI 호출 0건.** 임베딩(로컬 e5)·BM25·리랭커 전부 로컬 모델이라 팀 키 $20 한도와 무관.

## 10. 이 실험이 답하지 못하는 것

세 가지는 결과 보고서에 반드시 함께 적는다.

1. **풀링의 태생적 한계** — 두 검색기 어느 쪽도 못 건진 청크는 영원히 정답이 될 수 없다. 실제 Recall은 여기서 재는 값보다 낮다.
2. **BM25는 승격만 시킬 수 있다** — BM25만 찾은 청크는 본문을 안 들고 있어 리랭킹 대상에서 빠진다. 즉 BM25의 기여는 "dense가 이미 본 청크를 위로 올리는 것"까지다. 진짜 신규 청크를 넣으려면 Chroma 왕복이 한 번 더 필요한데 v1 범위 밖.
3. **답변 품질은 안 잰다** — 이 실험은 검색 순위만 본다. 검색이 좋아져도 생성이 좋아진다는 보장은 없다(별도 골든셋 평가 몫).

---

## 11. 보류 — spec 이탈 안건

`spec.md`/ADR-006이 임베딩을 `multilingual-e5-small`로 고정하고 있다. BGE-M3(dense+sparse+multi-vector 통합)로 교체하면 e5와 BM25를 한 모델로 대체할 수 있고 한국어 성능도 낫지만:

- 30,002청크 재인덱싱 + **라벨 전량 재생성** 필요
- 모델 2.2GB (VM 디스크 문제와 동일)
- 임베딩·sparse·인덱스가 한꺼번에 바뀌어 **무엇 때문에 좋아졌는지 구분 불가**

→ **1단계 결과를 보고 결정한다.** `B′`가 잘 나오면 굳이 바꿀 이유가 없다.
