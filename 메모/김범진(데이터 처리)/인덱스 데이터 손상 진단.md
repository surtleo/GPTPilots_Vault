# 인덱스 데이터 손상 진단

`data/chroma_v2` (30,002청크 / 99문서, 표 헤더 승격 반영본) 전수 측정.
검색 실험([[검색 실험 골든셋 40문항]]) 라벨링 중 관찰된 이상을 코퍼스 전체로 확대해 센 것이다.

## 왜 이 문서가 필요한가

검색 실험에서 나온 실패 원인 중 **검색 알고리즘 문제는 1건**(긴 질문이 희귀어를 희석)뿐이고 나머지는 전부 **인제스트 단계**에서 생긴 손상이었다.

```
[인제스트]                                       [검색]
hwp/pdf → 텍스트 추출 → 클리닝 → 청킹 → 임베딩 → | → dense · BM25 · 리랭커
                  ↑ 여기서 망가진 것                  ↑ 우리가 실험하는 곳
```

인제스트에서 망가진 데이터는 **검색 알고리즘을 바꿔도 안 고쳐진다.** 이미 그 상태로 인덱스에 들어가 있기 때문이다.

## 전수 측정 결과

| 항목 | 건수 | 전체 대비 | 심각도 |
|---|---|---|---|
| **요구사항 청크에 고유번호 없음** | 3,252 | 10.8% (요구사항 청크의 **31%**) | 높음 |
| 거의 동일한 청크 | 6,712 (2,120그룹) | 22.4% | 중간 |
| 정보량 없는 짧은 청크 (<40자) | 3,002 | 10.0% | 중간 |
| 빈 셀이 절반 넘는 표 | 2,221 | 7.4% (표 청크의 12%) | 중간 |
| 섹션 경로 누락 | 1,437 | 4.8% | 중간 |
| 표 머리(구분행) 없는 조각 | 859 | 2.9% (표 청크의 5%) | 높음 |
| **hwp 파싱 깨짐 문자** | 345 | 1.1% (**57개 문서**) | 높음 |

정규화 상태는 양호: NFC 미정규화 청크 **0건**.

---

## 1. 요구사항 고유번호 유실 — 31% (가장 큰 손상)

요구사항 표는 세로형 키-값 구조다. 500자에서 자르면 **고유번호 행이 앞 청크에 남고 내용만 뒤 청크로** 넘어간다.

```
::0059  | 요구사항 고유번호 | ECR-002 |
        | 요구사항 명칭 | 버스정보안내단말기(BIT) 소형 |
        | 세부내용 | ○ 도입장비 수량 ▹ 소형 쉘터형 : 50대 …      ← 여기서 끊김
::0060  물(지지대 혹은 브라켓) 포함 도장 : 옥외용 분체도장 …        ← "구조"의 "물"부터 시작
```

**영향**
- `"SFR-009 요구사항이 뭐야?"` 같은 질문에서 내용 청크가 검색되지 않는다
- 검색된 청크에 번호가 없어 인용·출처 표기가 부정확해진다
- 라벨링 중 "고유번호로 찾은 청크에 답이 안 보인다"의 직접 원인

**대응** — 잘린 조각마다 표 머리(고유번호·명칭 행)를 다시 붙인다. 규칙 변환이라 LLM 불필요.

## 2. 거의 동일한 청크 — 22.4%

앞 120자가 같은 청크가 2,120그룹 6,712개. **최대 80개**가 한 그룹이다.

같은 양식의 표(장비 사양·요구사항 상세)가 여러 벌 있고 뒤 조각에 식별자가 없어서 생긴다. 1번 문제와 뿌리가 같다.

> **현재 검색 실험에는 영향 없음.** 실측 결과 정답이 중복 무리에만 있는 문항은 0건이고, 중복은 대부분 오답 쪽에 몰려 있다. 다만 문서가 늘면 터질 수 있어 감시 대상이다. 상세는 [[검색 실험 골든셋 40문항]] 교훈 B-1.

## 3. hwp 파싱 깨짐 — 345청크 / 57개 문서

```
楴䵴楴䵴4. 제안요청 내용
 가. 제안요청 개요
 3) 사업금액 : 40,000천원(부가세 포함)
```

`楴`·`䵴`·`䪌` 같은 CJK 통합한자가 청크 머리에 섞인다. hwp 바이너리 파싱에서 제어 바이트를 문자로 잘못 해석한 것으로 보인다.

**영향** — 라벨링 중 사람이 정답 청크를 못 알아보고 건너뛴 실제 사례가 있다(EIP3.0 사업금액 문항). 임베딩에도 노이즈로 들어간다.

**대응** — 클리닝 단계에서 해당 유니코드 영역 제거. 정규식 한 줄이면 되고 **한국어 RFP 본문에 이 영역 문자가 정상적으로 등장할 일은 없다.**

## 4. 정보량 없는 짧은 청크 — 10.0%

40자 미만이 3,002개. 표 조각·빈 줄·제목 단독 등이다. 검색 결과 자리를 차지하면서 답에 기여하지 않는다.

**대응** — 인접 청크에 병합하거나 인덱싱에서 제외.

## 5. 빈 셀 과다 표 — 표 청크의 12%

병합셀을 빈칸으로 패딩한 결과, 셀의 절반 이상이 빈 표가 2,221개다.

```
|  |  |  |
| --- | --- | --- |
|  | 2024년 ｢벤처확인종합관리시스템…｣ |  |
|  |  |  |
```

**영향** — 임베딩에 파이프·구분선만 잔뜩 들어가 의미 신호가 희석된다. dense가 표에서 약한(정답이 표일 때 중앙값 10위 vs 줄글 4위) 원인 중 하나로 추정.

**대응** — 빈 셀 압축 또는 표를 행 단위 문장으로 변환. 후자는 검색 품질 개선에도 직접 기여한다.

## 6. 섹션 경로 누락 — 4.8%

`섹션` 메타가 없는 청크 1,437개. 출처 표기가 `chunk_id`로 대체돼 사람이 읽을 수 없다.

## 7. 가운뎃점 유니코드 변종 — 5종 공존

| 문자 | 코드 | 청크 수 |
|---|---|---|
| `·` | U+00B7 | 4,149 |
| `․` | U+2024 | 1,699 |
| `‧` | U+2027 | 558 |
| `∙` | U+2219 | 92 |
| `・` | U+30FB | 51 |

`사회적 책임·성실성`과 `사회적 책임∙성실성`이 **다른 문자열**이라 BM25 정확 매칭이 깨진다. NFC 정규화로는 안 잡히고(측정: NFC 미정규화 0건) 별도 치환이 필요하다.

**대응** — 클리닝 단계에서 가운뎃점 계열을 한 문자로 통일.

## 대응 우선순위

| 순위 | 작업 | 난이도 | 기대 효과 |
|---|---|---|---|
| 1 | **표 머리 반복 삽입** | 중 | 고유번호 유실 31% + 중복 청크 22% 동시 해결 |
| 2 | **hwp 깨짐 문자 제거** | 하 | 345청크, 정규식 한 줄 |
| 3 | **가운뎃점 통일** | 하 | BM25 정확 매칭 복구 |
| 4 | 표 행 단위 문장화 | 중 | dense의 표 약세 개선 (실측 10위 vs 4위) |
| 5 | 짧은 청크 병합·제외 | 하 | 검색 결과 자리 낭비 감소 |

2·3번은 **오늘 안에 가능하고 재인덱싱만 하면 된다.** 1·4번은 청킹 로직 변경이라 설계가 필요하다.

## 주의 — 재인덱싱은 라벨을 무효화한다

청크 ID가 `{doc_id}::{순번}`이라 청킹이 바뀌면 전부 달라진다. 지금 라벨(35문항)이 무효가 되므로 **검색 실험 측정을 먼저 끝낸 뒤** 진행해야 한다.

권장 순서:
```
1. 4변형 측정 → 베이스라인 확보          ← 현재 여기
2. 인제스트 수정 → 재인덱싱 → 재라벨링
3. 재측정 → "검색 개선 vs 데이터 개선" 비교
```

이러면 **"알고리즘에 투자할까, 데이터에 투자할까"**가 숫자로 갈린다.
