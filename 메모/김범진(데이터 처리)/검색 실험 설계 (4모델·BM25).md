## 0. 읽기 전에 — 이 실험이 뭐냐

### 한 문장

> 질문을 던졌을 때 **정답이 적힌 문단을 몇 등으로 찾아오는가**를 재고,
> 지금 쓰는 **임베딩**을 바꿀 값어치가 있는지 판정한다.
> 이전 판과 다른 점은 두 가지다 — **문항을 164 → 251로 늘렸고, 후보에 도메인 파인튜닝 모델을 하나 더 넣었다.**

### 실제로 무슨 일이 일어나나 — 질문 하나를 끝까지 따라가기

<details open>
<summary>질문 하나가 검색 파이프라인을 통과하는 흐름</summary>

```
질문  "한영대학교 정보시스템 구축사업의 사업기간은?"
  │
  │  ① 어느 문서 얘기?          문서 100개 중 1개로 좁힌다
  ▼                             (골든셋이 정답 문서를 알려주므로 이 단계는 항상 맞다고 친다)
문서 1개  =  청크(문단) 약 300개
  │
  │  ② 그중 20개만 뽑는다        ← 이 실험이 바꾸는 곳. 임베딩 4종이 여기서 갈린다
  ▼
후보 20개  (정답이 이 안에 없으면 이후 단계가 무슨 짓을 해도 끝)
  │
  │  ③ 20개를 다시 줄세운다      ← 리랭커 R1. 이번엔 고정이다
  ▼
1등 … 20등
  │
  │  ④ 상위 5개만 LLM에게 준다
  ▼
답변

★ 채점: 정답 문단이 ③에서 몇 등이었나 → 1등이면 1.0, 2등이면 0.5, 4등이면 0.25
```

</details>

**이전 판과 달라진 것은 ②의 선수 명단뿐이다.** ①·③·④는 전부 그대로 뒀다.
그래야 성적 차이의 원인이 임베딩 하나로 좁혀진다.

### 모르면 못 읽는 단어 10개

| 단어 | 한 줄 뜻 |
|---|---|
| **청크** | 문서를 잘라 놓은 문단 하나. 검색의 최소 단위 (RFP 100개 → 30,002개) |
| **임베딩** | 문장을 숫자 벡터로 바꾸는 모델. **뜻이 비슷하면 벡터가 가깝다** → 이걸로 후보를 뽑는다 |
| **dense** | 위 임베딩(벡터)으로 하는 검색. "의미가 비슷한 것" |
| **[[크로스인코더 리랭커\|리랭커]]** | 뽑아온 후보 20개를 질문과 하나씩 붙여 보고 **다시 줄세우는** 모델. 이 실험에서는 **고정**이다 |
| **골든셋 / 정답지** | 사람(과 Claude)이 미리 판정해 둔 "이 질문의 정답은 이 청크" 목록. 채점 기준 |
| **[[MRR]]@10** | 이 실험의 **판정 지표**. 첫 정답이 몇 등인지의 평균 → 아래 눈금 참조 |
| **LoRA** | 큰 모델 전체를 다시 학습하지 않고 **작은 보조 행렬만** 얹어 튜닝하는 방식. 이번 M3가 그것 |
| **GPL** | Generative Pseudo Labeling. 정답 라벨 없이 **질문을 기계로 지어내** 도메인에 적응시키는 학습법 |
| **문서 클러스터 부트스트랩** | 재표집 단위를 문항이 아니라 **문서**로 두는 통계 보정 → §5 |
| **사전등록** | 수치를 **보기 전에** 판정 기준을 코드에 박아두는 것 → §6 |

### 숫자 읽는 눈금 — MRR 0.70이 좋은 건가

```
1.00  항상 1등          0.70 ← 지금 여기(v6 기준선)     0.50  평균 2등
0.33  평균 3등          0.10  평균 10등                 0.00  10등 안에 아예 없음
```

**0.7041** = 대충 *"질문 10개 중 6개쯤은 정답이 1등, 나머지는 2~4등쯤"*.

> [!warning] 이 0.7041을 v5의 0.7443과 비교하지 마라
> 두 숫자는 **다른 시험지**에서 나온 점수다. v6는 정답 청크가 353 → 486으로 늘었고
> 문항도 164 → 251로 바뀌었다. 절대값이 내려간 것은 성능이 떨어진 게 아니라
> **채점 대상이 달라진 것**이다. 비교는 언제나 **같은 v6 안에서의 모델 간 델타**로 한다.

### 실험 코드 읽는 법 — 이 문서 내내 나온다

| 축 | 코드 | 뜻 |
|---|---|---|
| **조작 — 임베딩** | `M0` | **e5-small** — 지금 쓰는 것 (기준선) |
| | `M1` | bge-m3 — 5배 큰 다국어 모델 |
| | `M2` | KURE-v1 — bge-m3의 한국어 튜닝판 |
| | `M3` | **gpl3** — e5-small에 LoRA-GPL을 병합한 도메인 파인튜닝판 ★ 이번에 새로 들어옴 |
| **고정 — 리랭커** | `R1` | `bge-reranker-v2-m3` — 현행. **이번엔 안 바꾼다** |
| **후보 구성** | `C` | dense 20개만. BM25 없음 — **임베딩 축의 고정값** |
| ~~고정~~ **→ 조작** | `E` `F` `G` | BM25를 섞은 세 변형. **착수 후 축을 다시 열었다** → §0-1 ② · §8-1 |
| 접미사 | `_doc` | 문서 1개 안에서만 검색 (프로덕션 경로. **모든 판정의 기준**) |
| 엔진 갈래 | `M0_exact` | M0를 **정확 계산**으로 만든 후보 캐시 |
| | `M0_fast` | M0를 Chroma **근사 탐색**으로 만든 후보 캐시 → §11 |

> **기준선 = `M0` + `R1` + `C_doc`** = 지금 돌아가는 그것. 모든 비교는 이것과 맞댄다.

## 0-1. 실험 설계 한눈에

### ① 무엇을 고정했나 — 통제 변인

**하나라도 움직이면 이전 수치와 비교할 수 없다.**

| 고정한 것 | 값 | 왜 고정하나 |
|---|---|---|
| **청크 경계** | e5 토크나이저 (`CHUNK_TOKENIZER_MODEL`) | `chunk_id`가 **문서 내 위치 기반**이라, 경계가 밀리면 정답지가 **전부 다른 청크**를 가리킨다 → §9 |
| **정답지** | 골든셋 **v6** · 300문항 준비 · **채점 성립 251** · 정답 **486** | 라벨이 늘면 점수가 오른다. 모델마다 다르면 비교가 아니다 → §3 |
| **후보 구성** | **`C_doc`** (dense 20개, BM25 없음) | v5에서 C가 이겼다. 여기서 다시 흔들면 임베딩 판정의 전제가 깨진다 → §8. ⚠️ **임베딩 축 안에서만 고정이다** — BM25는 별도 측정으로 다시 열었다 → ② · §8-1 |
| **리랭커** | **R1 `bge-reranker-v2-m3`** ON | 리랭커 OFF 값은 승격 판정에 못 쓴다 → §4 |
| **검색 범위** | 대상 문서 안 (`doc_id` 필터) | RFP 100개가 서로 닮아 안 좁히면 엉뚱한 사업이 올라온다 → §2 |
| **top-k** | 후보 20 → 리랭크 후 10 | |
| **프리픽스** | 모델 계열별 규약 (e5 계열은 `passage:`/`query:`) | 틀려도 **에러가 안 나고 성능만 떨어진다** → §10 |
| **지표** | [[MRR]]@10(판정) · [[nDCG]]@10 · Recall@5 · Recall@20 | MRR 하나만 두면 반대 방향 손해가 안 보인다 → §4 |
| **통계** | [[paired bootstrap]] 95% CI · 1만 회 · 시드 `20260729` · **문서 클러스터** | 문항 단위로 재표집하면 CI가 실제보다 좁아진다 → §5 |

### ② 무엇을 바꾸나 — 조작 변인

| 축 | 파이프라인 어디 | 바꾸는 것 | 몇 개 | 상세 |
|---|---|---|---|---|
| **임베딩** | ② 후보 뽑기 | `M0` `M1` `M2` `M3` | 4 | §7 |
| **BM25 (후보 구성)** ★ 도중 추가 | ② 후보 뽑기 | `C_doc` → `E_doc` `F_doc` `G_doc` | 3 × 4모델 | **§8-1** |

**착수 시점에는 축이 하나였다.** v5는 후보 구성·리랭커·임베딩 세 축을 3단계로 확정했고,
그 중 아래 두 층(후보 구성 = C, 리랭커 = R1)이 **현행 유지로 닫혔다.**
이 실험은 그 위에 남은 **임베딩 한 축만** 다시 여는 것으로 시작했다.

> [!warning] BM25 축은 **통제 변인이었다가 조작 변인이 됐다** — 설계 변경 경위
> 착수 시 후보 구성은 위 ①의 **통제 변인 표**에 있었다. "v5에서 C가 이겼으니 상속한다"였다.
> **그 상속을 취소한 것은 임베딩 판정 결과 자체다.**
>
> | 순서 | 무슨 일 |
> |---|---|
> | 1 | 임베딩 축 판정 — v5에서 기각됐던 M1·M2의 **CI 하한 부호가 바뀌어 통과**했다 |
> | 2 | 그 원인은 성능이 아니라 **표본 해상도**였다("164문항으로는 +0.03을 판정할 수 없다") |
> | 3 | **BM25도 같은 표본에서 기각됐다** — e5 `G_doc` +0.0222, CI 하한 −0.0184 (v5/164문항 기준) |
> | 4 | 임베딩만 다시 재고 BM25는 옛 판정을 유지하면 **우리에게 유리한 축만 다시 재는 것**이 된다 |
> | 5 | → 후보 구성 축을 **조작 변인으로 되돌려** v7 251문항으로 재측정했다 |
>
> **즉 이 변경은 새 아이디어가 아니라 일관성 요구다.** 근거를 인정한 순간 적용 범위가 따라온 것이다.
>
> ⚠️ **두 축은 서로 다른 정답지에서 쟀다** — 임베딩 축은 v6(정답 486), BM25 축은 **v7**(정답 490).
> BM25 측정을 위한 라벨링이 정답을 4건 늘렸기 때문이다(§3-5).
> **임베딩 판정을 v7 라벨로 재확인한 결과 세 승격이 소수 4자리까지 그대로였다** —
> 그래서 두 축의 결과를 나란히 읽어도 된다 → [[검색 실험 결과 (4모델·BM25)]] §12-6

> [!note] 축을 좁혔다가 다시 연 것이 이 실험의 설계 이력이다
> v5는 3 × 2 × 4 = 24조합을 3단계로 좁혔다. 이번엔 **아래 두 층을 상속**받아
> 4모델 × 1리랭커 × 1후보 = **4칸**으로 시작했다. 대신 그 4칸을 **훨씬 정밀하게** 쟀다
> (문항 251, 문서 클러스터 보정, 사전등록 규격). **넓히는 대신 깊게 판 실험**이다.
>
> 상속의 전제는 "후보 구성·리랭커 판정이 임베딩을 바꿔도 유지된다"는 가정이었고,
> **그 가정 중 BM25 쪽은 위 경위로 취소돼 실측으로 대체됐다**(4모델 × 3변형 = 12칸 추가).
> **리랭커 쪽 상속은 그대로 유지된다** — R2는 CI 상한까지 전부 음수라 표본을 늘려도 뒤집힐 여지가 없다 → §8

### ③ 무엇과 무엇을 맞대나 — 비교쌍

**같은 조건에서 딱 한 곳만 다르게 한 두 판을 맞댄다.** 그래야 차이의 원인이 하나로 좁혀진다.

| 비교 | 무엇이 달라지나 | 답하는 질문 | 용도 |
|---|---|---|---|
| **M0_exact ↔ M3** | 같은 계열·같은 크기·같은 차원에서 **도메인 학습만** | **RFP 도메인 파인튜닝이 값어치가 있나** ★ | **핵심** |
| **M0_fast ↔ M1** | 118M → 568M, 384 → 1024차원 | 모델을 키우면 나아지나 | v5 판정(6.8.9) 재확인 |
| **M0_fast ↔ M2** | 위와 같되 한국어 튜닝판 | 한국어 특화가 나은가 | v5 판정(6.8.9) 재확인 |
| M0_exact ↔ M0_fast | 후보 캐시를 만든 **검색 엔진만** | 근사 탐색이 성적에 영향을 주나 | 게이트 검증 → §11 |

> [!important] `M0 ↔ M3`가 왜 핵심인가
> M1·M2는 기준선과 **모델 크기·차원·학습 데이터·프리픽스 규약이 전부 다르다.**
> 이겨도 *"큰 덕인가, 한국어 덕인가, 학습 데이터 덕인가"*가 갈리지 않는다.
> M3는 **M0와 같은 베이스 모델에 LoRA만 얹은 것**이라, 이기면 그 원인이
> **도메인 학습 하나**로 좁혀진다. 실험 설계상 가장 깨끗한 쌍이다.

### ④ 가설과 판정 기준 — 측정 전에 정한다

> [!tip] 판정 기준을 말로 풀면
> **"기준선보다 확실히 낫고(운이 아니고), 그 차이가 바꿀 만큼 크고, 어느 유형도 망가지지 않는다"** 세 가지를 동시에 요구한다.

## 1. 왜 다시 재나 — 이전 판의 결론은 "판정 불가"에 가까웠다

이전 판(v5/164문항)은 임베딩 축을 **"현행 유지"**로 닫았다. 그런데 같은 문서에 이런 자기비판이 함께 남아 있었다.

> **승격 기준이 측정 해상도보다 낮다 — +0.03은 164문항으로 판정할 수 없다.**
> paired bootstrap 95% CI의 반폭이 전 조합에서 ±0.035~0.046으로 거의 일정했다.
> 이 해상도에서는 CI 하한 > 0을 통과하려면 점추정이 대략 **+0.036 이상**이어야 하고,
> 따라서 **+0.030~+0.036 구간은 최소 폭 기준은 넘어도 CI에서 막히는 회색지대**가 된다.

그리고 v5의 KURE가 정확히 그 회색지대에 떨어졌다 — **+0.0297, CI 하한 −0.0042.**

즉 v5의 "현행 유지"는 **"바꿔서 좋아지지 않는다"가 아니라 "좋아지는지 알 수 없다"**에 가까웠다.

| v5가 실제로 말한 것 | v5가 말하지 않은 것 |
|---|---|
| 이 표본으로는 이득이 증명되지 않는다 | 이득이 없다 |
| +0.03을 164문항으로는 판정할 수 없다 | 임베딩 교체가 무의미하다 |

v5는 **필요한 문항 수까지 계산해뒀다.**

| 잡고 싶은 차이 | 필요한 채점 문항 |
|---|---|
| **+0.03** | 약 **236** |
| +0.02 | 약 531 |

그래서 이 실험의 착수 목적은 단순하다 — **채점 성립 문항을 236 이상으로 올려 같은 기준을 다시 적용한다.**
결과는 **251문항**이 나왔다(§3). 목표를 넘겼다.

**동시에 새 후보를 하나 넣었다.** 팀에서 e5-small을 RFP 도메인에 GPL로 파인튜닝한
LoRA 어댑터가 나왔기 때문이다(§7-1). 표본을 늘리는 김에 후보도 늘리는 것이
GPU 시간 면에서 압도적으로 싸다 — 후보 캐시와 리랭킹을 한 번에 돌린다.

> [!note] 표본만 늘렸으면 더 깨끗한 실험이었다
> 표본과 후보를 동시에 바꿨으므로 **"무엇 때문에 결론이 바뀌었나"가 자동으로 갈리지 않는다.**
> 그래서 판정 후 **구간별 재판정**을 따로 돌려 원인을 분리했고,
> 그 결과가 우리에게 불리했다 → [[검색 실험 결과 (4모델·BM25)]] §7

## 2. 파이프라인 — 왜 문서를 먼저 좁히나

검색은 **2단**이다.

```
① doc_cards 컬렉션(문서 100개 요약카드)으로  어느 문서 얘기인지 특정
② 그 문서의 청크 안에서만 검색               where={"doc_id": ...}
```

이유는 **RFP 100개가 서로 너무 닮았기** 때문이다. 전부 정부 제안요청서라
*"사업기간은 계약일로부터 O개월"* 같은 문장이 100개 문서에 다 있다.
문서를 안 좁히면 벡터 유사도상 **엉뚱한 사업의 절**이 위로 올라온다.

**표기 규칙**: 접미사 **`_doc`** = 대상 문서 안에서만(**프로덕션 경로. 모든 판정의 기준**) → [[후보 캐시]]

> [!warning] 전제 — ①이 항상 맞았다고 가정한다
> 골든셋의 `대상_doc_id`를 그대로 쓴다. 실서비스에서는 라우터가 문서를 틀릴 수 있으므로
> **모든 수치는 "라우팅이 완벽할 때의 상한"**이다.
>
> 검색 성능과 라우팅 성능을 분리해 재려는 **의도된 설계**지만, **"실서비스 성능"으로 읽으면 안 된다.**

이 전제는 v5와 동일하다. 바꾸지 않은 이유도 같다 — 여기를 흔들면 v5와의 방법론 연속성이 끊어진다.

### 3-1. 왜 정답지를 4모델 기준으로 다시 만들어야 했나 ★

**여기가 이 실험에서 제일 조용히 망하기 쉬운 자리였다.**

v5 정답지는 **3모델(M0·M1·M2) 합집합 풀**에서 판정됐다. 여기에 M3를 그냥 얹으면 이렇게 된다.

```
M3만 데려온 후보  →  사람이 판정한 적이 없음  →  라벨 없음  →  채점기가 오답으로 셈
```

즉 **M3가 진짜 정답을 새로 찾아올수록 점수가 깎인다.** 잘할수록 손해를 보는 구조다.

> [!danger] 이건 이미 한 번 겪은 사고다 (6.8.8)
> v4 정답지는 **e5 후보만** 사람이 판정해서 만들어졌다.
> 그 결과 새 모델이 사용자에게 보여줄 상위 10개 중 **26~32%를 아무도 읽어본 적이 없었다.**
>
> | 조합 | 상위 10개 중 미판정 |
> |---|---|
> | e5 + R1 (당시 현행) | **0.7%** |
> | bge-m3 + R1 | **26.0%** |
> | KURE + R1 | **32.0%** |
>
> v5는 3모델 합집합 풀링으로 이 편향을 걷어냈고, 전 조합 미판정률이 **0.0%**가 됐다.
> **v6에서 M3를 넣는 순간 같은 구조의 사고가 다시 열린다.** 그래서 정답지부터 고쳤다.

### 3-2. 두 갈래로 채웠다

문항 성격이 달라 채우는 방법도 갈렸다.

| 갈래 | 대상 | 무엇을 판정했나 | 규모 |
|---|---|---|---|
| **신규 85문항** | v6에 새로 들어온 문항 | **4모델 합집합 후보 전건** | 후보 4,215개 · 문항당 평균 **49.6** |
| **기존 169문항 델타** | v5부터 있던 문항 | **M3 고유 신규 후보만** (기존 정답은 맥락으로 동봉) | M3 고유 **598건** |

**왜 기존 문항은 전건이 아니라 델타인가.** 기존 문항의 M0·M1·M2 후보는 v5에서 이미 전건 판정됐다.
다시 읽으면 비용만 들고, 더 나쁘게는 **잣대가 미세하게 달라져 기존 라벨과 어긋난다.**
그래서 **M3가 새로 데려온 후보만** 판정 대상으로 뽑았다(6.8.8에서 쓴 것과 같은 방식).

M3 고유 후보는 최종적으로 **1,020건**(신규 갈래 422 + 기존 갈래 598)이었고,
그중 정답으로 채택된 것은 **5건 = 0.49%**다.

> [!note] 이 0.49%를 어떻게 읽어야 하나 — 함정이 있다
> 이 숫자는 **"4모델 중 M3만 데려온 후보의 정답률"**이다.
> 12.7 판정이 재는 것은 **"M0 대비 M3"**다. **기준이 다르다.**

> 이 둘을 같은 얘기로 읽었다가 가설을 하나 잘못 세웠다 → [[검색 실험 결과 (4모델·BM25)]] §8

### 3-3. 라벨링 파이프라인 — 2단계, 그리고 왜 스킬을 안 바꿨나

1. **라벨러** — `.harness-mem/goldenset-skill/rounds/r8/SKILL.md` (v8, **재현율 0.863 / 정밀도 0.750**)로 원문 대조 판정

> [!important] 여기서는 **절대 정확도보다 일관성**이 중요하다
> 증분을 더 엄격한 방법으로 라벨링하면 기존 정답과 잣대가 갈려,
> M0(기존 라벨 위주)와 M3(신규 라벨 위주)가 **서로 다른 기준으로 채점**된다.
> **지금 고치려는 편향을 다른 편향으로 바꾸는 꼴**이다.
> 그래서 200문항 골든셋을 만든 바로 그 스킬·그 프롬프트를 그대로 썼다.

**검증 실측 — 2단계가 설계대로 작동했다.**

| 갈래 | 문항 | 검증 verdict | 유지 | 제거 | 추가 | 보류 |
|---|---|---|---|---|---|---|
| 신규 85문항 | 85 | 통과 77 · 수정 8 | 120 | **2** | **8** | 0 |
| 기존 169문항 델타 | 155 | 통과 155 · 수정 0 | 5 | 0 | 0 | 1 |

**제거(2)보다 추가(8)가 많다.** 이것이 라벨러 스킬 프로필(**재현율 0.863 · 정밀도 0.750**)과 방향이 맞는다 —
재현율이 높고 정밀도가 낮은 라벨러라면 검증에서 **떨어져 나가는 게 많아야** 정상처럼 보이지만,

검증자가 놓친 것을 주워 담으면 **추가가 제거보다 많아진다.** 실측이 그 방향과 일치했다.

신규 85문항의 최종 정답은 라벨러 122건 → 검증 후 **128건**이 됐다.

> [!danger] 리스트로 이었으면 조용히 틀어졌다
> 델타 판정에서 **중복 정답 2건**이 나왔다(`g200:37cd7e06::0011` · `g200:9f071cc8::0009`).
> `gold_chunk_ids`를 리스트로 append하면 같은 chunk_id가 두 번 들어가
> **그 문항의 nDCG·Recall 분모가 부풀고 채점이 에러 없이 틀어진다.**
> 집합 연산으로 합쳐 해소했다. 경위는 [[검색 실험 결과 (4모델·BM25)]] §10.

### 3-5. BM25 축을 열면서 정답지가 한 단계 더 갔다 — **v7**

BM25를 조작 변인으로 되돌리는 순간(②) **§3-1과 똑같은 구조의 사고가 다시 열렸다.**
BM25 전용 후보는 **4모델 dense 합집합 풀에 없다** — 판정된 적이 없으니 전부 오답으로 세어진다.

**실측으로 크기를 먼저 쟀다.**

| 항목 | 값 |
|---|---|
| BM25 전용 후보 | **2,819건** |
| 그중 판정 이력 없음 | **734건 = 26.0%** (기존 169문항 중 **118문항**에 걸침) |
| dense 대조군 미판정률 | M0 0.56% · M1 0.72% · M2 0.82% · M3 **0.00%** |
| 변형별 미판정률(리랭커 입력 기준) | `C_doc` 0.6% → `E_doc` 3.3% → `F_doc` 6.4% → **`G_doc` 8.6%** |

**dense는 전부 1% 미만인데 BM25만 26%다. 그리고 판정 대상 변형(`G_doc`)이 가장 큰 페널티를 받는다.**
원인은 **스코프 변경**이다 — 기존 풀의 어휘 후보는 **전역 BM25**였고(§8-2), 이번은 **문서 스코프**라
대상 문서 안에서 새로 올라온 청크가 판정 대상에 없었다.

**조치: 734건 전건 라벨링**(라벨러 8명 병렬) → **독립 검증 2명** → **정답 4건(0.54%)**, 추가·제거 0.
리드가 별도로 **자동 재현율 감사**(기준답변 변별 토큰 60% 이상을 담고도 기각된 후보 탐색)를 돌려 **0건** 확인.

| | v6 | **v7** |
|---|---|---|
| 문항 (300 / 254 / 채점 성립 251) | 동일 | **동일 — 불변** |
| 정답 청크 | 486 | **490** |
| 판정 풀 구성 | 4모델 | **4모델 + BM25(문서 스코프)** |

> [!important] 여기서도 라벨러·검증 규격을 바꾸지 않았다
> §3-3과 같은 이유다 — **증분을 더 엄격하게 라벨링하면 기존 정답과 잣대가 갈린다.**
> 다만 이번엔 갈리는 축이 모델이 아니라 **후보 구성**이다.
> BM25 전용 후보만 더 엄격하게 보면 **BM25가 구조적으로 불리해진다.**
>
> **v6 스냅샷은 불변으로 둔다**(불변 스냅샷 규약). v7은 그 위의 델타를 얹은 별도 정본이다.
> 그리고 **v7 라벨로 임베딩 판정을 재확인해도 세 승격이 소수 4자리까지 같다** —
> 신규 정답 4건이 전부 BM25 전용이라 `C_doc` 후보에 들어오지 않기 때문이다.

### 3-6. 질문 파일 — 이걸 틀리면 조용히 망한다

검색·리랭킹은 **항상 같은 질문 텍스트**를 봐야 한다.

> [!danger] 6.8.6에서 실제로 전체 측정이 무효가 됐다
> 첫 실행에서 검색은 병합본을 봤는데, 리랭킹에는 골든셋 원본을 넣었다.
> 그러면 후속 유형의 **선행 턴 병합이 빠져 검색과 재정렬이 서로 다른 질문**을 보게 된다.
> 파일 이름도 문항 수도 그럴듯해서 **에러가 나지 않는다.** 결과 숫자만 조용히 틀어진다.

**후속 유형은 선행 턴을 앞에 이어붙인 병합본**이다.

```
원본:    "그 사업의 안정화기간은?"
병합본:  "한영대학교 …사업기간은 어떻게 되나요? 그 사업의 안정화기간은?"
```

v6에서 후속 유형은 **45문항**(기존 30 + 신규 15)으로 v5의 29보다 늘었다.
그만큼 이 실수의 영향 범위도 넓어졌다.

| 실행 단계 | 틀리면 생기는 일 |
|---|---|
| 후보 캐시 생성 | 후속 질문 문맥 없이 후보를 뽑는다 |
| 리랭킹 | 검색과 재정렬이 서로 다른 질문을 본다 |
| 채점 | 정답 라벨 기준이 검색 질문과 분리된다 |

## 4. 지표

| 지표 | 무엇을 보나 | 역할 |
|---|---|---|
| **[[MRR]]@10** (리랭커 ON) | 첫 정답이 **몇 등**인가 | **판정** ★ |
| **[[nDCG]]@10** | 상위권 **전체의 질** | 회귀 감시 |
| **Recall@5** | LLM에 실제로 넘어가는 5개의 질 | 회귀 감시 |
| **Recall@20** | 정답이 후보 안에 **들어왔나** | **진단** — 임베딩 고유 실력 · 리랭커가 손댈 수 없는 상한 |

**판정은 종단(리랭커 켠) 성적으로 한다.** 그게 실제로 돌아갈 구성이기 때문이다.

> [!danger] 리랭커 OFF 값을 승격 판정에 쓰지 마라
> 12.2a에서 gpl3가 dense 단독으로 **+0.0650 [+0.0193, +0.1134]**를 냈다(v5/164문항 기준).
> 이 값은 **승격 판정이 아니다.** v5의 KURE도 dense 단독으로는 큰 격차를 냈지만
> **종단에서 +0.0297로 깎였다** — 리랭커가 그 이득의 대부분을 이미 하고 있기 때문이다.
> 이 주의사항은 `verdict_12_7.py`의 `해석_주의` 배열에 **산출물로 박아** 뒀다.

### 4-1. Recall@20을 같이 보는 이유

종단이 안 올랐을 때 **원인을 구분**하려고다.

| Recall@20 | 종단 MRR | 해석 |
|---|---|---|
| ↑ | ↑ | 더 데려왔고 성적으로 이어졌다 |
| ↑ | → | 더 데려왔는데 리랭커가 못 올렸다 → **리랭커 쪽 문제** |
| → | → | 키워도 못 찾는 문항이다 → **청킹·질의 쪽 문제** |

이 진단표는 이번 실험에서 실제로 쓰였다. gpl3의 이득이 **어디서 오는지**를 가른 것이
Recall@20과 순위 덤프였다 → [[검색 실험 결과 (4모델·BM25)]] §4·§8.

### 4-2. 판정 지표를 하나만 두면 반대 방향 손해를 못 본다

> [!warning] v5의 BM25 판정이 실제로 그랬다
> MRR@10으로는 "유의차 없음"인데 nDCG@10·Recall@5로는 **유의하게 나빴다**
> (KURE 기준 nDCG −0.0364 [−0.0622, −0.0101] · Recall@5 −0.0492 [−0.0869, −0.0126], v5/164문항 기준).
> BM25 후보가 상위 5개를 잠식해 **LLM에 넘어가는 컨텍스트를 떨어뜨린 것**이다.
> 그때는 결론이 같은 방향이라 판정이 안 바뀌었지만, 반대였다면 잘못 채택했을 것이다.
>
> **그래서 BM25를 다시 열 때는 이 검사를 판정 규격 안에 넣었다** — 채택 4번째 조건 → §8-1.
> v7에서 `E_doc` 3건(M1·M2·M3)이 실제로 그 조건에 걸렸다.

그래서 v6에서도 부수 지표 셋을 **판정 지표와 같은 부트스트랩으로 함께** 낸다.
`verdict_12_7.py`는 `--extra-metrics ndcg@10,recall@5,recall@20`을 기본값으로 갖는다.

<small>Recall@20은 채점기 기본 Recall이 `RETRIEVAL_TOP_K`(=5)라 산출물에 없다.
그래서 `--dump-ranked`가 남긴 **순위 목록에서 계산**한다. 순위는 chunk_id뿐이라 NDA에도 안전하다.
`ranked`가 없으면 **중단한다** — 조용히 0으로 채우면 모든 모델이 똑같이 0이 되어 차이가 사라진다.</small>

## 5. 통계 — 문서 클러스터 paired bootstrap

> [!note] paired bootstrap을 쓰는 이유
> 같은 251문항에서 기준선과 도전안을 나란히 비교한다.
> 문항마다 난이도가 다르므로, 단순 평균 두 개를 따로 보는 것보다 **문항별 차이**를 다시 뽑아 보는 쪽이 맞다.

251문항을 **복원추출**해 문항별 차이 `d_i = 도전점수(i) − 기준점수(i)`를 리샘플한다.
**1만 회**, 시드 `20260729` 고정. 시드는 v5와 같은 값을 유지했다 — 바꿀 이유가 없고, 바꾸면 재현 대조가 어려워진다.

**"평균이 올랐다"만으로 판정하지 않는다.** 과거에 36문항에서 +0.073이 나와 "확정"이라 적었다가
164문항에서 −0.031로 부호가 뒤집힌 적이 있다. 자세히 → [[paired bootstrap]]

### 5-1. 왜 문항 단위가 아니라 문서 단위인가 ★

**같은 문서에서 뽑은 문항들은 독립이 아니다.** 한 RFP에서 3~4문항이 나오는데,
그 문서의 청킹이 잘 됐으면 문항 셋이 같이 잘 나오고 못 됐으면 같이 못 나온다.

문항 단위로 재표집하면 **유효표본을 과대평가해 CI가 실제보다 좁아진다 — 유의성을 부풀리는 방향의 오차다.**

그래서 재표집 단위를 **문항이 아니라 문서**로 둔다.

```python
# scripts/verdict_12_7.py : build_clusters()
군집 키 = 그 문항의 첫 대상 문서(_norm_doc_id 경유)
키가 없는 문항이 하나라도 있으면  →  SystemExit로 중단
```

> [!danger] 키가 없으면 왜 중단하나
> 부트스트랩이 **키 없는 문항을 조용히 버린다.** 분모가 줄었는데 에러는 안 난다.
> 이 실험에서 반복적으로 잡힌 실패 유형(§13의 "조용히 틀리는 실패")과 정확히 같은 계열이라
> 하드페일로 막았다.

### 5-2. 군집 키를 뭘로 잡을지도 실측으로 정했다

| 키 | 군집 수 | 군집당 문항 | 왜 이걸 쓰나 / 안 쓰나 |
|---|---|---|---|
| **첫 대상 문서 (`first`)** | **95** | **2.64** | **채택.** Plans 예상치 2.96과 같은 자릿수 |
| 대상 문서 집합 (`tuple`) | 129 | 1.97 | 군집이 잘게 쪼개져 **보정 효과가 약해진다** |

**보정 효과가 약해지는 쪽을 고르면 CI가 좁아지고 유의성이 부풀려진다.**
그러니 여기서 `tuple`을 고르는 것은 자기에게 유리한 선택이 된다. `first`를 기본값으로 박았다.

### 5-3. 클러스터 보정이 실제로 일한다 — 실측

M3 ↔ M0_exact · MRR@10 · 1만 회 · seed 20260729:

| 재표집 단위 | 95% CI | 폭 |
|---|---|---|
| 문항 단위 | [+0.0121, +0.0776] | 0.0655 |
| **문서 클러스터 (first, 95군집)** | **[+0.0097, +0.0807]** | **0.0710** |
| 문서집합 클러스터 (tuple, 129군집) | [+0.0102, +0.0799] | 0.0697 |

- 클러스터 보정이 CI를 **8.4% 넓혔다.** 방향이 맞고 크기도 설계효과(문서당 2.64문항)에 부합한다
- **어느 재표집 단위를 써도 하한이 양수로 유지된다** — 판정이 재표집 방식에 민감하지 않다
- 남는 반박: **문서 클러스터가 상관의 유일한 축인가.** 같은 발주기관·같은 문서 유형의 문항도 상관이 있을 수 있다 → 미측정

## 6. 승격 기준 — 측정 전에 **코드로** 고정한다

기준선은 **M0 e5-small + R1**.

> [!important] 판정은 여기서 끝난다
> 아래 세 조건을 **모두** 통과해야 한다.
> 점추정이 좋아 보여도 95% CI가 0을 걸치면 **채택하지 않는다**.

| 조건 | 값 | 왜 이 값인가 |
|---|---|---|
| **주 기준** | 차이의 **95% 신뢰구간 하한 > 0** | 소표본 오판을 막는다 |
| **최소 폭** | 점추정 **+0.03 이상** | 재인덱싱·모델 교체를 감수할 최소선 |
| **회귀 금지** | 어떤 유형도 **−0.03 이하로 떨어지지 않을 것** | 평균이 오르며 한 유형이 망가지는 걸 막는다 |

세 조건은 v5와 **글자 하나 안 바꿨다.** 이번에 달라진 것은 기준이 아니라 **그 기준을 판정할 수 있는 표본**이다.

### 6-1. 왜 코드에 박았나 — 사전등록

```python
# scripts/verdict_12_7.py
PROMOTE_MIN_DELTA = 0.03
REGRESSION_LIMIT  = -0.03
SEED              = 20260729
N_RESAMPLES       = 10_000
```

docstring에 이유가 한 줄로 적혀 있다.

> **기준을 코드로 박는 이유: 수치를 보고 나서 기준을 고르면 어떤 결과든 정당화된다.**

`promote_verdict()`는 세 조건을 각각 bool로 내고 `all()`로 묶는다.
**판정자가 "이번엔 이 조건이 좀 애매하니까"라고 끼어들 자리가 없다.**

같은 이유로 **6.8.9 대조도 코드에 상수로 박혀 있다.**

```python
BASELINE_689 = {
    "M1": {"mean": 0.0197, "lo": None, "hi": None, "판정": "기각 (CI 0 걸침)"},
    "M2": {"mean": 0.0297, "lo": -0.0042, "hi": 0.0654, "판정": "기각 (하한 음수)"},
}
```

`compare_to_689()`가 **하한 부호가 바뀌었는지**를 자동 판정하고,
바뀌면 `재검토_필요: true`와 파생 작업(`6.8.9 되돌림 + ADR-010 신설 + spec.md §2 개정`)을 산출물에 찍는다.
**실제로 M2에서 그 플래그가 켜졌다.**

### 6-2. 회귀 검사는 유형별 평균차로 한다

```python
# per_type_deltas() — 평균이 오르며 한 유형이 망가지는 것을 여기서 잡는다
유형별 평균차(t) = mean( 도전점수(q) − 기준점수(q) )   for q in 유형 t
```

v6의 유형별 문항 수는 **단일세부 134 · 후속 45 · 탐색비교 37 · 직답 35**다.
직답 35문항은 표본이 작아 평균차의 변동이 크지만, **회귀 한계 −0.03은 CI가 아니라 점추정 기준**이라
표본 크기와 무관하게 적용된다. 이건 의도된 보수성이다 — 작은 유형에서 무너지는 것도 잡아야 하기 때문.

### 6-3. 동점 통과 시의 규칙

> 여러 구성이 통과하면 **작은 쪽**을 고른다. 인덱스 크기·질의 비용이 그만큼 낮기 때문이다.

이 규칙은 v5에서 그대로 상속했다. **이번에 실제로 발동했다** — 세 후보가 전부 통과했기 때문이다.
그런데 이번엔 규칙이 단순히 적용되지 않았다. 평균 성능·견고성·유형 안정성·모델 크기가
**서로 다른 답**을 가리켰기 때문이다.

> 축이 갈렸을 때 **무엇을 우선할지는 실측이 정하지 않는다.** 사용자가 이 규칙을 우선했다.
>
> | # | 근거 |
> |---|---|
> | 1 | **이 규칙 그대로** — gpl3는 **118M·384차원**으로 KURE(0.6B·1024)의 1/5 |
> | 2 | **유형별 최저값** gpl3 +0.0328 > KURE +0.0169 > bge −0.0100 |
> | 3 | **gpl3 단독(+0.0437) ≈ e5+BM25(+0.0430)인데 BM25 인덱스가 필요 없다** → §8-1 |
>
> 3번은 착수 시점에 없던 근거다. BM25를 조작 변인으로 되돌린 것(§0-1 ②)이
> **"e5에 BM25를 얹는 값싼 길"의 크기를 실측으로 알려줬고, 그 길이 gpl3 단독과 같은 크기였다.**
> 즉 축을 다시 연 결정이 채택 근거를 하나 만들어냈다.
>
> ⚠️ **평균·견고성 축에서는 KURE가 앞섰다는 사실은 유지된다** —
> 기존 169문항 구간에서 승격 기준을 통과한 유일한 모델은 KURE다.
> 그래서 재판정 조건을 함께 남겼다 → [[검색 실험 결과 (4모델·BM25)]] §5

## 7. 임베딩 4종

| 코드 | 모델 | 파라미터 | 차원 | 프리픽스 | 비고 |
|---|---|---|---|---|---|
| **M0** | `intfloat/multilingual-e5-small` | 118M | 384 | `query:` / `passage:` **필수** | **현행 운영** (ADR-006) |
| **M1** | `BAAI/bge-m3` | 568M | 1024 | 없음 | 대형 다국어. HF 캐시 4.3GB |
| **M2** | `nlpai-lab/KURE-v1` | 0.6B | 1024 | 없음 | bge-m3의 **한국어 튜닝판** |
| **M3** | e5-small + LoRA-GPL merged (**gpl3**) | 118M | 384 | `query:` / `passage:` **필수** | **도메인 파인튜닝** ★ 신규 |

**M1을 계속 넣어야 했다.** M2는 M1을 한국어로 추가 학습한 모델이라,
M1 없이 M2만 돌리면 이긴 이유가 갈리지 않는다. 이 구조는 v5에서 그대로 가져왔다.

| 결과 | 해석 |
|---|---|
| M0→M1 크고 M1→M2 작다 | **계열이 관건** |
| M0→M1 작고 M1→M2 크다 | **한국어 튜닝이 관건** |
| M1→M2 ≤ 0 | 한국어 튜닝 불필요 |

### 7-1. 새 후보 gpl3 — 먼저 병합 상태부터 검증했다

팀에서 e5-small을 RFP 도메인에 **GPL(Generative Pseudo Labeling)**로 파인튜닝한
LoRA 어댑터가 나왔다(`intfloat-multilingual-e5-small-LoRA-gpl3.pt`).

**받은 체크포인트를 그대로 믿지 않았다.** 어댑터가 실제로 병합됐는지, 무엇이 바뀌었는지부터 확인했다.

| 확인 항목 | 결과 | 무엇을 뜻하나 |
|---|---|---|
| state_dict 키 | **199개**, missing / unexpected **0** | 베이스 구조와 완전히 호환된다 |
| 단어 임베딩 | `(250037, 384)` — 베이스와 동일 | 어휘·차원이 안 바뀌었다 |
| 변경된 텐서 | **72개 / 12개 레이어** (어텐션 q·k·v·output, FFN intermediate·output) | 실제로 학습된 가중치가 얹혔다 |
| 임베딩 층·풀러 | **변경 없음** | → **e5의 프리픽스 규약을 그대로 써야 한다** |

**마지막 줄이 실험 설계에 직접 영향을 줬다.** 임베딩 층이 안 바뀌었다는 것은
입력 문자열 관례가 베이스와 같아야 한다는 뜻이고, 그래서 §10의 프리픽스 게이트가 M3에도 그대로 걸린다.

### 7-2. 프리픽스 여부를 실측으로 확정했다 (12.2a)

학습 시 `query:`/`passage:`를 붙였는지가 **문서로 남아 있지 않았다.** 그래서 세 조건을 다 돌렸다.
v5/164문항 · **리랭커 OFF** · dense 단독:

| 조건 | MRR@10 | nDCG@10 | Recall@20 |
|---|---|---|---|
| (a) 원본 e5 + 프리픽스 | 0.6402 | 0.5764 | 0.7608 |
| **(b) gpl3 + 프리픽스** | **0.7052** | **0.6447** | **0.8305** |
| (c) gpl3 프리픽스 없음 | 0.5219 | 0.4846 | 0.7225 |

- **(b) − (c) = +0.1833** — 프리픽스를 떼면 **원본보다도 나쁘다.** gpl3는 e5 관례를 유지한 채 학습됐다
- **(b) − (a) = +0.0650, CI [+0.0193, +0.1134]** — nDCG +0.0684 · Recall@20 +0.0697도 전부 CI 하한 > 0
- `EMBEDDING_M3_USE_E5_PREFIX = True` 확정

> [!warning] 이 +0.0650은 **승격 판정이 아니다**
> 리랭커 OFF의 dense 단독값이다. v5의 KURE도 dense 단독으로는 큰 격차를 냈지만
> 종단에서 +0.0297로 깎였다. 판정은 종단으로만 한다(§4).
> 이 주의문은 `verdict_12_7.json`의 `해석_주의`에 산출물로 박혀 있다.

<small>**재현 검증 통과** — 조건 (a)가 v5 결과 문서의 M0 실측 MRR@10 **0.6402를 소수점 넷째 자리까지 재현**했다.
dense_doc 경로가 원본과 동일함이 확인된 것이다. nDCG·Recall이 v5 문서 표와 다른 것은
**정답지 v4(310) → v5(353) 차이**이며 파이프라인 문제가 아니다.</small>

### 7-3. 핵심 비교쌍은 M0 ↔ M3 ★

| | M0 | M1 | M2 | M3 |
|---|---|---|---|---|
| 베이스 계열 | e5 | bge | bge | **e5 (M0와 동일)** |
| 파라미터 | 118M | 568M | 0.6B | **118M (동일)** |
| 차원 | 384 | 1024 | 1024 | **384 (동일)** |
| 프리픽스 규약 | e5식 | 없음 | 없음 | **e5식 (동일)** |
| M0와 다른 점 | — | 크기·계열·차원·프리픽스 | 위 + 한국어 학습 | **도메인 학습 하나** |

**M1·M2가 이겨도 이유가 안 갈린다.** 크기 덕인지, 계열 덕인지, 한국어 덕인지 셋이 뭉쳐 있다.
**M3가 이기면 이유가 하나뿐이다** — RFP 도메인 학습.

그래서 `COMPARE_PAIRS`에서 M3만 `핵심`으로 태그돼 있고, M1·M2는 `6.8.9재확인`이다.

```python
COMPARE_PAIRS = [
    ("핵심",        "M3", "M0_exact"),
    ("6.8.9재확인", "M1", "M0_fast"),
    ("6.8.9재확인", "M2", "M0_fast"),
]
```

<small>기준선이 M3에 대해서만 `M0_exact`인 이유는 §11에 있다 — M3 후보를 정확 계산으로 만들었으므로
비교 상대도 정확 계산이어야 "검색 방식 덕에 이긴 것"을 배제할 수 있다.</small>

## 8. 상속한 축 — 리랭커는 고정, 후보 구성은 **되열었다**

이번 실험은 착수 시 **아래 두 층을 v5에서 상속**했다.

| 축 | 상속한 값 | v5의 근거 (v5/164문항 기준) | 지금 상태 |
|---|---|---|---|
| **후보 구성** | **`C_doc`** — dense 20개, BM25 없음 | E·F·G 어느 것도 유의하지 않았고, G는 nDCG·Recall@5에서 **유의하게 나빴다** | ⚠️ **상속 취소 · 조작 변인으로 재측정** → §8-1 |
| **리랭커** | **R1 `bge-reranker-v2-m3`** ON | R2(한국어 튜닝판)가 세 임베딩 전부에서 −0.06~−0.07로 **유의 패배**(점수 포화) | ✅ **상속 유지** |

**두 축의 상속 근거가 다르다.** 리랭커 R2는 **CI 상한까지 전부 음수**였다 —
"운이 나빴을 수도 있다"가 아니라 확실히 진 것이라 표본을 늘려도 뒤집힐 여지가 없다.
**후보 구성은 그렇지 않았다** — e5 줄의 `G_doc`은 점추정이 **이득 쪽(+0.0222)**인데 CI가 0을 걸친,
즉 **"졌다"가 아니라 "판정이 안 섰다"**였다. 그래서 이 축만 다시 열었다 → §8-1

> [!warning] 상속은 가정이지 측정이다 — 이번에 그 차이가 실제 비용으로 나타났다
> "후보 구성·리랭커의 승자가 임베딩을 바꿔도 승자다"라는 가정 위에 서 있었고,
> **그중 후보 구성 쪽 가정은 틀렸을 수 있다는 것이 드러나 12칸을 추가로 재야 했다**(4모델 × E·F·G).
> 재보니 e5 줄에서 판정이 실제로 뒤집혔다 — **가정으로 뒀으면 못 봤을 값이다.**
>
> 여전히 안 잰 칸은 남는다 — v5의 `E·F·G × R2 × 임베딩 3` = 9칸과 같은 계열로,
> 이번에도 **`M3 × R2`는 재지 않았다.** 다만 채택 경로가 `C_doc + R1`로 닫혀 있어
> 이번 판정에는 직접 쓰이지 않는다.

### 8-1. BM25 축 — 상속을 취소하고 **v7로 재측정했다**

v5는 BM25를 미채택으로 닫았다. 그런데 그 판정에는 **임베딩 판정을 뒤집은 것과 똑같은 해상도 부족**이 있다.

| v5/164문항 기준 | 값 |
|---|---|
| e5 줄 `C_doc` → `G_doc` | **+0.0222, CI [−0.0184, +0.0642]** |
| bge-m3 | −0.0035 |
| KURE-v1 | −0.0127 |

**e5의 +0.0222는 KURE의 +0.0297과 같은 성격의 숫자다** — 점추정은 이득 쪽인데 CI가 0을 걸쳐 기각된 것.
그리고 그 KURE는 v6에서 **하한 부호가 바뀌어 통과했다.**

> [!important] 그래서 BM25도 같은 잣대로 다시 재는 것이 일관된 태도다
> "임베딩은 표본이 부족해서 판정이 안 섰다"고 인정했으면,
> **같은 표본으로 기각된 BM25에도 같은 말을 해야 한다.**
> 한쪽만 다시 재고 다른 쪽은 옛 판정을 유지하면 그것 자체가 편향이다.

**측정 규격 — 임베딩 축과 같은 잣대에 한 항을 더했다.**

| 항목 | 값 |
|---|---|
| 대상 | 임베딩 **4종 전부**(M0·M1·M2·M3) × 변형 **`E_doc`·`F_doc`·`G_doc`** = 12칸 |
| 문항 | **251문항** (v6와 동일) · 정답지는 **v7**(정답 490, §3-5) |
| 조건 | `bm25_doc`(문서 스코프) · 리랭커 R1 ON · 문서 클러스터 95군집 · 1만 회 · seed `20260729` |
| **채택 조건** | 승격 3조건 **+ ④ 부수 지표(nDCG@10·Recall@5)에 유의 음수 없음** |
| 사전등록 | `scripts/verdict_bm25_v6.py` — **수치를 보기 전에 커밋** |

> [!important] 조건이 하나 더 붙은 이유
> §4-2의 v5 실측 때문이다 — BM25는 **MRR로는 유의차 없음인데 nDCG·Recall@5로는 유의하게 나빴다.**
> 판정 지표 하나만 보면 그때 잘못 채택했을 수도 있었다.
> 그래서 이번엔 그 검사를 **판정 규격 안에 조건으로** 넣었다. (실제로 `E_doc` 3건에서 걸렸다.)

**결과 요약 — 값 정본은 [[검색 실험 결과 (4모델·BM25)]] §12다.**

| 모델 | `C_doc → G_doc` MRR@10 Δ | 95% CI | 판정 |
|---|---:|---|---|
| **M0 e5-small** | **+0.0430** | **[+0.0032, +0.0869]** | ✅ **4조건 충족** |
| M1 bge-m3 | +0.0016 | [−0.0141, +0.0182] | ❌ |
| M2 KURE-v1 | −0.0027 | [−0.0256, +0.0202] | ❌ |
| M3 gpl3 | +0.0007 | [−0.0163, +0.0202] | ❌ |

**e5 줄에서 하한 부호가 바뀌었다**(v5/164문항 기준 +0.0222 [−0.0184, +0.0642] → v7 +0.0430 [+0.0032, +0.0869]).
즉 **v5의 BM25 미채택도 "효과 없음"이 아니라 "판정 불성립"이었다** — 임베딩 축과 같은 구조다.

> [!success] 그런데 설계상의 결론은 "BM25 OFF 유지"다
> BM25의 이득은 **dense가 약할 때의 보완**이고, 승격 후보 세 모델 위에서는 남지 않는다.
> **채택 모델이 gpl3(§6-3)이므로 이 축은 켜지지 않는다.**
> 그리고 **gpl3 단독 +0.0437 ≈ e5+BM25 +0.0430**이라는 대조가 §6-3의 채택 근거 3번이 됐다.

<small>⚠️ **정정(2026-07-31)**: 여기 있던 "M0 `G_doc`의 nDCG가 v5 −0.0364 → v7 +0.0459로 부호가 뒤집혔다"는
미해결 사항은 **철회한다.** −0.0364는 M0가 아니라 **KURE의 값**이었고(v5 정본 §2-1-2가 "KURE-v1 기준"이라
명시한다), M0의 v5 부수 지표는 기록이 없어 대조 자체가 불가능하다. 사전등록 스크립트가 이 상수를
`V5_SECONDARY_M0_G`라는 이름으로 들고 있던 것이 원인이다 — 판정 로직은 이 상수를 쓰지 않으므로
채택 판정에는 영향이 없다 → [[검색 실험 결과 (4모델·BM25)]] §12-7.</small>

### 8-2. BM25는 문서를 좁혔을 때만 의미가 있다 (전제)

재측정도 **`bm25_doc`(문서 스코프)** 기준으로만 했다. 전역 BM25는 v5에서 이미 무효 처리됐다.

BM25를 전체 코퍼스에 돌리면 **사업명 토큰이 상위를 독식**한다.
RFP는 표지·머리말·각 절에 사업명이 반복돼서, 질문에 사업명이 들어가면 **그 사업의 아무 절이나** 위로 올라온다.
어떤 절이 답인지는 전혀 가려주지 못한다.

문서를 이미 좁힌 상태에서는 사업명이 **모든 후보에 똑같이** 들어 있어 변별에 기여하지 않고,
나머지 어휘(고유명사·표기·수치)로 순위가 갈린다.

<small>v5에서 이 결함으로 무효 처리된 값: `dense_doc`은 문서 안인데 구 `bm25`는 전역이라
BM25 후보 20개 중 평균 6.5개(32.6%)가 **대상 문서 밖 = 정답일 수가 없는 청크**였다.
그 측정은 하이브리드를 잰 게 아니라 **"엉뚱한 문서의 청크를 섞으면 나빠지나"**를 잰 것이었다.</small>

> [!danger] 그 스코프 변경이 **이번 미판정 편향의 직접 원인**이다
> 기존 판정 풀의 어휘 후보는 **전역 BM25**로 만들어졌다. 이번은 **문서 스코프**다.
> **대상 문서 안에서 새로 올라온 청크는 판정받은 적이 없다** → BM25 전용 후보의 **26.0%가 미판정**.
> 그대로 쟀으면 전부 오답으로 세어져 **BM25가 구조적으로 진다.**
> 조치와 실측은 §3-5에 있다. **스코프를 고치면 정답지도 따라와야 한다** — 이번에 배운 것이다.

| §9 chunk_id 동결 | 정답지가 다른 청크를 가리키는 실패 |
| §10 프리픽스 | 모델 입력 형식이 달라지는 실패 |
| §11 동일 엔진 | 검색 방식 덕에 새 모델이 이기는 실패 |
| §12 인덱스·검색 조건 | 다른 인덱스나 검색 범위를 재는 실패 |

## 9. 청크 경계를 동결한다 — chunk_id 게이트

`chunk_id`는 **문서 내 위치 기반**이다.

```python
# src/index/chunk.py:321
"chunk_id": f"{doc_id}::{len(chunks):04d}"   # 몇 번째 청크인가
```

청크 경계가 밀리면 **251문항 정답지가 통째로 다른 청크를 가리킨다.**
에러 없이 조용히 어긋나는 종류다 → [[청크와 chunk_id]]

그래서 임베딩을 바꿔도 청킹은 **항상 e5 토크나이저**(`CHUNK_TOKENIZER_MODEL`)로 한다.
안 쓰는 토크나이저로 자르는 게 이상해 보이지만 **청킹 고정이 목적**이라 이게 맞다.
bge-m3·KURE가 8192토큰을 받는다고 청크를 키우는 건 **다른 실험**이다.

**게이트 — 모델 간 chunk_id 차집합이 0건이 아니면 중단한다.**

이번 실험에서는 후보 풀 생성이 **전체 재인덱싱 없이 대상 문서 청크만** 모델별로 임베딩하는 방식이라
게이트가 더 중요해졌다. 인덱스에 없는 chunk_id가 하나라도 나오면 **드롭 하드페일**로 세웠다.

| 항목 | 결과 |
|---|---|
| 후보 풀 생성 범위 | **32문서 / 10,643청크** (신규 85문항 대상 27문서 9,323청크에서 확대) |
| 인덱스에 없는 chunk_id | **0건** |
| 드롭 | **0건** |
| pytest | **23건 통과** (청크 수 일치 / e5가 `chroma_v2`와 chunk_id 순서·거리 동일 / 중복 0건) |

<small>범위를 27문서 → 32문서로 넓힌 이유: 12.5에서 라벨을 새로 붙인 기존 문항 5건이
기존 캐시(164문항 기준)에 없어 그대로 두면 **재채점 자체가 불가능**했다.</small>

> [!danger] 왜 드롭을 하드페일로 막았나
> 이 프로젝트에서 **에러 없이 후보·라벨이 줄어드는 실패가 3건 확인**됐다(메모리 `silent-data-drop`).
> id 조회 코드는 **드롭 건수를 세야 한다.** 세지 않으면 분모가 줄어든 채로 점수가 나온다.

## 10. 프리픽스 ⚠️ 통제 항목 중 제일 위험

E5 계열(**M0·M3**)은 `passage: `/`query: `를 **반드시** 붙여야 하고 bge-m3·KURE(**M1·M2**)는 **붙이면 안 된다.**
틀려도 **에러가 안 나고 성능만 조용히 떨어진다.**

함정이 하나 더 있다 — 프리픽스 뒤에 **섹션 정보가 같이** 붙는다.

```python
# src/index/chunk.py:48
def build_passage_prefix(meta, section):
    return f"passage: [사업명: {...} / 발주기관: {...} / 섹션: {section}]\n"
```

통째로 떼면 섹션 정보까지 날아가 **새 모델만 정보를 덜 받는다.**

| 모델 | 문서 입력 | 질문 입력 |
|---|---|---|
| M0 · **M3** (e5 계열) | `passage: [사업명…/섹션…]\n` + 본문 | `query: ` + 질문 |
| M1 · M2 | `[사업명…/섹션…]\n` + 본문 | 질문 그대로 |

> [!danger] 여기서 틀리면 실험이 조용히 망한다
> 프리픽스 오류는 예외를 던지지 않는다.
> 모델별 입력 문자열을 확인하지 않으면, 새 모델이 나빠진 것이 아니라
> **새 모델만 섹션 정보를 덜 받은 상태**를 재게 된다.

### 10-1. 육안 확인 대신 **전수 복원 검사**를 썼다

v5는 "각 인덱스 첫 청크의 실제 입력 문자열을 눈으로 확인"이 게이트였다. **표본 확인이다.**

v6에서는 더 강한 검사로 바꿨다.

```
인덱싱에 실제로 들어간 입력 문자열을 되짚어 재구성
  → 그 문자열을 다시 임베딩
  → 저장된 벡터와 코사인 유사도를 전건 비교
```

| 지표 | 값 |
|---|---|
| `embed_text_복원_cos` min | **0.9999999** |
| mean | **1.0** |

**코사인이 1.0이면 입력 문자열이 바이트 단위로 같다는 전수 증명이다.**
표본 육안 확인보다 강하다 — 첫 청크만 맞고 중간이 틀린 경우를 잡을 수 있다.

## 11. 동일 엔진 — 검색 방식 덕에 이기지 않게 한다

> [!danger] 세 임베딩이 **같은 엔진**을 써야 한다 (v5의 게이트 문구)
> Chroma는 `doc_id` 필터를 걸어도 전수 비교가 아니라 **근사 탐색**이라,
> 정확 계산과 대조하니 v5/164문항 중 **9문항(5.5%)**에서 상위 20이 달랐다.
> 기존 M0 캐시는 근사 산출물이므로 새 모델만 정확 계산으로 만들면
> **새 모델이 임베딩 성능이 아니라 검색 방식 덕에 유리해진다.**

v6에서는 M1·M2·M3 후보를 **numpy 정확 계산**으로 만들었다.
그래서 M0도 **정확 계산 버전(`M0_exact`)을 한 벌 더** 만들어 M3의 비교 상대로 삼았다.

| 캐시 | 만든 방법 | 누구의 비교 상대인가 |
|---|---|---|
| `M0_fast` | Chroma 근사 탐색 (기존 캐시 계보) | M1 · M2 (6.8.9 재확인이라 그때와 같은 조건 유지) |
| `M0_exact` | numpy 정확 계산 | **M3** (핵심 비교쌍 — 엔진을 맞춘다) |

### 11-1. 결과적으로 이 게이트는 종단에서 무의미했다 — 그러나 사전에는 알 수 없었다

| 비교 | 종단 MRR@10 차이 |
|---|---|
| `M0_exact` ↔ `M0_fast` | **0.000000** (251문항 전건) |

후보 집합이 다른 문항이 있었지만, **교체된 청크가 전부 비정답이고 상위권 밖**이었다.
리랭커가 후보 20개를 전량 재정렬하므로 dense 엔진 차이가 종단 지표에 남지 않는다.

> [!note] 그래도 두 벌 만든 것이 낭비는 아니다
> **§11의 게이트는 dense 단독 측정에서만 구속력이 있고, 리랭커 종단에서는 씻긴다** —
> 이것이 이번 실험이 새로 알아낸 사실이다.
> 그런데 **그 사실은 측정으로만 알 수 있었다.** 사전에는 "유리한 편향이 생길 위험"을 배제할 수 없었다.
> 게이트를 안 걸고 나중에 "씻겼을 것"이라 말하는 것과, 걸고 나서 "씻겼다"고 말하는 것은 다르다.
>
> 경위는 [[검색 실험 결과 (4모델·BM25)]] §9.

## 13. 이 실험이 경계하는 실패 유형

이 프로젝트에서 잡힌 사고를 늘어놓으면 **전부 같은 종류**다.

| 사고 | 왜 안 보였나 |
|---|---|
| 틀린 인덱스 | 양쪽에 같은 chunk_id가 있어 에러가 안 난다 |
| 질문 파일 어긋남 | 파일 이름이 그럴듯하고 문항 수도 맞다 |
| 정답지 편향 | 라벨이 없으면 그냥 오답으로 세어진다 |
| BM25 스코프 불일치 | 후보 개수는 정확히 20개다 |
| **정답지에 새 모델 미반영 (이번에 막은 것)** | **M3 고유 후보가 전부 오답으로 세어진다** |
| **병합 시 중복 chunk_id (이번에 잡은 것)** | **분모만 조용히 부푼다** |
| **정답지에 새 후보 구성 미반영 (이번에 막은 것)** | **BM25 전용 후보의 26.0%가 오답으로 세어진다** → §3-5 |

**공통점: 실패가 예외를 던지지 않고 숫자로만 나타난다.**
그래서 이 실험은 조건마다 게이트를 붙이고, 게이트 실패를 **하드페일**로 만들었다.
