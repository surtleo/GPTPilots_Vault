# BM25 하이브리드 실험

> dense 단독 검색에 BM25(어휘 검색)를 섞으면 정답 순위가 오르는지 검증한 기록.
> 구도 → [[검색 실험 구도]] · 평가셋 → [[검색 실험 골든셋 40문항]] · 이력 → [[검색 개선 이력]]
>
> **결론이 두 번 바뀐 기록이다. 순서대로 읽을 것.**
> 1차(전체 코퍼스): +0.002 → 기각
> **2차(문서 한정): +0.073 → 승격 기준 통과.** 조건 하나 바꿨더니 뒤집혔다
> **핵심: 프로덕션 코드가 BM25를 정확히 거꾸로 켜고 있다** (§7)

---

## 1. 왜 했나

우리 검색은 **dense 단독**이다. 질문과 청크를 각각 벡터로 만들어 **뜻이 가까운 것**을 찾는다.
임베딩은 로컬 `intfloat/multilingual-e5-small` (ADR-006).

그 ADR에 트레이드오프가 이렇게 적혀 있었다:

> 대형 임베딩 모델 대비 **한국어 고유명사·표 검색 품질 한계** → 메타데이터 필터·프리픽스 주입·**(백로그) BM25 하이브리드로 보완**

즉 BM25 도입 근거는 처음부터 **"표와 고유명사에서 dense가 약할 것"**이라는 예상이었다.

**우리 코퍼스에서 이게 중요한 이유**: 인덱스 30,002청크 중 **63.3%가 표 청크**다.
RFP의 핵심 정보(배점표, 요구사항 목록, 장비 규격, 제출서류)가 거의 다 표 안에 있다.

**희석 가설**: 표 청크는 `| 항목 | 값 | 비고 |` 형태로 셀 수십 개가 한 청크에 들어간다.
512토큰 벡터 하나에 그게 다 뭉개지므로 `CDR-003`, `ISO 4373` 같은 **핵심 토큰 하나의 신호가 희석**된다.
BM25는 그 글자가 있으면 바로 점수를 준다 → 그래서 BM25가 이 구간을 메워줄 것이라고 봤다.

## 2. 가설

| # | 가설 | 참이면 기대되는 것 |
|---|---|---|
| H1 | dense는 표 안의 고유번호·코드를 잘 못 찾는다 | 어휘형 질문에서 dense 재현율이 낮다 |
| H2 | BM25가 그 구간을 메운다 | 같은 질문에서 BM25가 dense가 놓친 청크를 잡는다 |
| **H3** | **둘을 합치면 정답 순위가 올라간다** | **하이브리드 MRR@10 > dense MRR@10** |

H3이 본 가설. H1·H2는 그 이유를 설명하는 하위 가설.

### 왜 "찾았냐"가 아니라 "몇 등이냐"인가

6.1 실측에서 기존 골든셋 `hit@5`가 **1.000으로 포화**됐다. 정답이 상위 5개 안에 들어오는지만 보면
전부 만점이라 변형 간 차이가 안 보인다. 그래서 **순위 민감 지표**를 주 지표로 쓴다.

- **MRR@10** — 첫 정답이 몇 등인가 (1등=1.0, 5등=0.2). 실전에서 상위 5개만 LLM에 주므로 등수가 곧 성능
- **nDCG@10** — 정답이 여러 개일 때 위쪽에 몰릴수록 높음

## 3. 방법

### 3.1 비교 대상

| 변형 | 구성 | 역할 |
|---|---|---|
| **A_dense** | 현행 프로덕션 | 베이스라인 |
| **B_hybrid** | dense + BM25를 RRF로 융합 | **이 실험의 본체** |
| C_rerank | dense + 크로스인코더 재배열 | 별도 관심사 (GPU 필요) |
| D_hybrid_rerank | 둘 다 | 상호작용 |

### 3.2 합치는 방식 — RRF

두 검색기의 **점수**는 척도가 달라 직접 못 섞는다(dense는 코사인 유사도, BM25는 무한대로 열린 점수).
그래서 **등수만** 쓴다.

```
점수(청크) = Σ  1 / (60 + 그 검색기에서의 등수)
```

`60`은 원논문 권장값(`RRF_K`). 상위권 격차를 완만하게 만들어 한 검색기의 1등이 다른 검색기의
합의를 짓밟지 못하게 한다. **가중치 튜닝이 필요 없다는 게 RRF를 고른 이유.**

### 3.3 BM25 구현

| 요소 | 내용 |
|---|---|
| 토큰화 | `kiwipiepy` 형태소 분석 — 조사를 떼어야 "제안서를/제안서의"가 같은 토큰이 됨 |
| 랭커 | `rank_bm25.BM25Okapi` 기본값 (k1=1.5, b=0.75) |
| 토큰 캐시 | `data/bm25_tokens.json` (31MB), 코퍼스 지문 불일치 시 자동 재생성 |
| 실패 처리 | 예외 시 빈 목록 → dense 단독 강등 (spec §12) |
| 프로덕션 | `RETRIEVAL_USE_BM25 = False` — 꺼져 있음 |

### 3.4 평가셋

| 항목 | 내용 |
|---|---|
| 정답 라벨 | `data/rerank_labels.jsonl` — **사람이 직접 라벨링한 40문항** |
| 구성 | 기존 30 + 어휘형 10 |
| 빈 정답 | 4건 제외 (어느 변형도 득점 불가) |
| **가용** | **36문항** (기존 28 + 어휘형 8) |
| 후보 풀 | 문항당 34후보, `dense ∪ BM25` 합집합에서 사람이 선별 → **어느 쪽에도 편향 없음** |

**어휘형이 BM25의 승부처.** 전부 표 안의 고유 코드·번호를 묻는다 —
`CDR-003`(요구사항 번호), `ISO 4373`(기자재 표), CC인증 등급, 평가 배점, 행안부고시 번호, KS 규격.

### 3.5 실행 환경 — 함정 하나

> **`CHROMA_DIR_OVERRIDE=data/chroma_v2` 없이 돌리면 결과가 전부 틀린다.**

`chunk_id`는 위치 기반(`doc_id::순번`)이라 인덱스가 다르면 같은 id에 다른 본문이 들어간다.

| 인덱스 | 청크 | gold **id** 매칭 | gold **본문** 일치 |
|---|---|---|---|
| `data/chroma` (기본값) | 28,293 | 56/56 (100%) | **0/56 (0%)** |
| `data/chroma_v2` | 30,002 | 56/56 (100%) | **56/56 (100%)** |

id가 100% 맞아서 **에러 없이 조용히 돌고 본문만 전부 다르다.** 가장 위험한 실패 모드.
VM `/srv/GPTPilot/chroma`는 `chroma_v2`와 동일 확인(30,002청크, 라벨 본문 56/56).

### 3.6 승격 기준 (측정 전 확정 — 결과 보고 바꾸지 않는다)

> A_dense 대비 **전체 MRR@10 +0.05 이상** AND **기존 문항 hit@5 = 1.0 유지** → 프로덕션 ON
> 하나라도 미달이면 **미채택**으로 기록하고 플래그는 OFF로 남긴다.

## 4. 실험 전에 발견한 구조적 문제 — 융합 결과 폐기

`bm25_rank()`는 **`chunk_id` 목록만** 돌려준다. 본문도 메타데이터도 안 딸려온다.
합칠 때 코드가 dense 결과 사전을 기준으로 거른다:

```python
# src/query/retrieve.py:63
fused = rrf_fuse([dense_ids, bm25_ids])
ranked_ids = [cid for cid in fused if cid in by_id]   # ← BM25만 찾은 건 탈락
```

**인덱스에 표가 없어서가 아니다.** BM25는 답을 찾았는데 본문을 안 들고 와서, 뒷단(리랭커·지표 계산)에
못 넘기니까 명단에서 지우는 것이다.

해법은 이미 레포에 있다 — `scripts/make_rerank_labels.py:148`에서 라벨 만들 때 쓴 방식:
> BM25만 찾은 청크는 dense 결과에 본문이 없으므로 **Chroma에서 id로 직접 조회해 채운다**

그래서 **세 가지를 비교**했다:

| 이름 | 내용 | 차이가 말해주는 것 |
|---|---|---|
| `dense` | 현행 프로덕션 | 베이스라인 |
| `융합_현행` | BM25 섞되 dense 후보 밖 폐기 | (− dense) = **순위 재배열 이득** |
| `융합_수정` | BM25 섞고 폐기 안 함 | (− 융합_현행) = **청크 발굴 이득** |

## 6. 가설 판정 (1차 — 전체 코퍼스 조건)

| 가설 | 판정 | 근거 |
|---|---|---|
| H1 dense가 표에서 약하다 | **기각** | 어휘형에서 dense 9/10 적중, BM25는 5/10. `ISO 4373`·CC인증·배점 등 BM25가 이길 거라 본 문항에서 **BM25가 오히려 못 찾음** |
| H2 BM25가 구멍을 메운다 | **거의 기각** | 8문항 중 1건(CDR-003)만 해당 |
| H3 합치면 순위가 오른다 | **기각** | +0.002. 기준의 1/25 |

### 왜 안 오르나 — 상쇄

BM25가 **크게 돕는 사례**와 **크게 해치는 사례**가 섞여서 평균이 제자리다.

| 개선 | 악화 |
|---|---|
| HDIMS 6등 → **1등** | 한영대 사업기간 4등 → **10등** |
| KUSF 2등 → **1등** | 울산 BIT 제어부 20등 → **25등** |
| 봉화군 GIS 6등 → 2등 | 네팔 ISO 1등 → **3등** |

### 융합 폐기 수정은 오히려 손해

어휘형에서 `융합_현행 0.771` → `융합_수정 0.754`로 **내려간다**.
BM25만 찾은 무관한 청크가 상위로 끼어들어 정답을 밀어내기 때문(네팔 1→3, DDoS 3,4→5,7).
**고칠 이유가 사라졌다.**

## 6.5 재검증 — 실험 조건이 잘못돼 있었다

### 무엇이 잘못됐나

`run_rerank_experiments.py` 주석에 이렇게 적혀 있었다:

> `doc_id` 필터는 끈다 — 필터를 켜면 **항상 1.0이라 변형 간 차이가 사라진다**

**측정 편의를 위해 실전 조건을 바꿨다.** 지표가 포화된다는 건 그 조건에서 검색이 잘 된다는 뜻이지
조건을 버리라는 뜻이 아니다. 포화를 피하려면 더 어려운 문항이나 더 민감한 지표를 써야 하고,
조건 자체를 실전과 다르게 바꾸면 그 실험은 실전에 대해 아무 말도 못 한다.

### 토큰화 진단 — 여기는 멀쩡했다

먼저 kiwi 토큰화를 의심했는데 아니었다. `DDoS`, `CC`, `ISO`, `등급` 전부 온전히 살아 있다.
하이픈 분해도, 표 마크업 오염도 없었다.

**네팔 ISO 4373** — 정답 청크가 59등이었던 이유:

| | 내용 | 매칭 |
|---|---|---|
| 질문 토큰 | `네팔·수자원·관리·정보·화·사업·Pilot·시스템·구축·용역` + `수문·관측·기자재·ISO·표준` | 28개 |
| 정답 청크 (255자) | `\| 관련요구사항 \| ISO 4373, ISO 11655 \|` | **6개** → 59등 |
| BM25 1등 | 같은 문서 `## 1. 과업개요 / 용역명: 네팔 수자원관리 정보화사업 Pilot...` | 사업명 10토큰 |

**DDoS CC인증** — 정답 청크 518등. 1등은 *다른 문서*의 `\| 요구사항 분류 \| 보안 요구사항 \|`.

### BM25 단독 MRR — 조건별 (36문항)

| 조건 | MRR |
|---|---|
| A. 전체 코퍼스 (1차 실험 조건) | 0.349 |
| **B. 문서 한정** | **0.533** (+0.184) |
| C. 사업명 토큰 제거 | **0.126** (−0.223) |

### 메커니즘 — 사업명 토큰이 두 일을 겸한다

C가 붕괴한 게 핵심 단서다. "사업명이 정답을 잡아먹는다"는 단순한 설명은 **틀렸다.**

| 역할 | 효과 |
|---|---|
| 올바른 **문서**로 좁히기 | **필수** — 없으면 99개 문서에서 엉뚱한 청크가 올라옴 (C 붕괴) |
| 문서 안에서 **청크** 고르기 | **방해** — 개요·표지가 정답 표를 밀어냄 (네팔 1등이 과업개요) |

한 신호가 두 일을 겸하는데 방향이 반대라 상쇄된다.
**문서를 외부에서 좁혀주면 첫 역할이 필요 없어지고 충돌이 풀린다.**

## 7. 2차 결과 — 문서 한정 조건 (본 결론)

| 방식 | 전체 36 | 어휘형 8 | 기존 28 |

| dense 단독 | 0.577 | 0.750 | 0.527 |
| BM25 단독 | 0.532 | 0.701 | 0.484 |
| **하이브리드** | **0.650** | **0.854** | **0.591** |
| **Δ vs dense** | **+0.073** | **+0.104** | **+0.064** |

```
승격 기준        +0.050  ██████████████████████████
전체 코퍼스(1차) +0.002  █
문서 한정 (2차)  +0.073  ██████████████████████████████████████
```

**승격 기준 +0.05 통과.** 어휘형·기존 두 구간이 각각 단독으로도 넘는다.

같은 BM25, 같은 RRF, 같은 36문항. **바꾼 건 검색 범위 하나뿐이다.**

### 최종 가설 판정

| 가설 | 전체 코퍼스 | 문서 한정 |
|---|---|---|
| H1 dense가 표에서 약하다 | 기각 (9/10 적중) | 기각 유지 |
| H2 BM25가 구멍을 메운다 | 거의 기각 | **성립** — 단독 0.532로 dense와 대등 |
| **H3 합치면 순위가 오른다** | 기각 (+0.002) | **성립 (+0.073)** |

BM25가 dense를 **대체**하는 게 아니라, 둘이 **서로 다른 걸 보기 때문에** 합쳤을 때 이득이 난다.
전체 코퍼스에서는 BM25가 너무 약해(0.349 vs 0.577) 합쳐도 끌어올릴 힘이 없었던 것.

---

## 7.5 🔴 프로덕션 코드가 거꾸로 켜져 있다

```python
# src/query/retrieve.py:36
use_bm25 = config.RETRIEVAL_USE_BM25 and doc_id is None
#                                        ↑ 문서 지정되면 BM25를 끈다
```

주석의 근거: *"후보가 한 문서로 좁혀져 어휘 검색 이득이 사라진다"*

**실측은 정반대다. 좁혀져야 이득이 생긴다.**
BM25가 유일하게 잘 작동하는 조건에서 꺼두고, 안 되는 조건에서만 켜도록 돼 있다.

→ **`and doc_id is None` 조건을 뒤집는 것이 이 실험의 실질적 산출물.**

## 7.9 남은 한계 (결론 쓰기 전에 확인할 것)

| # | 한계 | 왜 중요한가 |
|---|---|---|
| 1 | `doc_id`를 **골든셋 정답 문서**로 줬다 | 라우터가 100% 정확하다는 가정. 실전 기대값 = 이득 × 라우터 정확도 |
| 2 | 승격 기준 2번(`기존 hit@5 = 1.0` 유지) 미확인 | 두 조건 다 만족해야 승격 |
| 3 | 손으로 짠 예비 측정 | 정식 러너 `run_rerank_experiments.py`로 재현 필요 |
| 4 | 36문항 표본 | 어휘형은 8문항뿐 |

## 8. 부산물 — 진짜 문제는 따로 있다

기존 28문항의 **dense MRR이 0.527**이다. 정답이 상위 20에 아예 없는 경우가 곳곳에 보인다.

- 봉화군 통합연계 — 정답 6개 중 하나가 15등
- GIS 데이터품질 — 20위권 밖
- 도시계획위원회 발주기관 — dense가 2개 다 놓침

**`hit@5 = 1.000 포화`는 문서 단위 얘기였다. 청크 단위로는 절반 수준이다.**
개선 여지가 큰 지점이고, **BM25로는 안 된다**는 게 이번 실험의 결론.

## 10. 이번에 배운 것 (재발 방지)

**측정 편의를 위해 실전 조건을 바꾸면 그 실험은 실전에 대해 아무 말도 못 한다.**

`doc_id` 필터를 끈 이유가 "지표가 포화돼 변별력이 없어서"였다. 포화는 그 조건에서 검색이
잘 된다는 신호지 조건을 버리라는 뜻이 아니다. 포화를 피하려면 **더 어려운 문항**이나
**더 민감한 지표**를 써야 한다. 조건을 바꾸면 안 된다.

그리고 "승격 기준을 측정 전에 확정한다"는 규칙을 지키느라 **조건 설정 자체는 검토하지 않았다.**
기준을 고정하는 것과 조건을 검증하는 것은 별개다.
