# 골든셋 라벨링 스킬 v1

> 사람 없이 정답 청크를 라벨링하는 에이전트용 지시서. **아직 검증 전(v1)이다.**
> 검증 절차와 심사 기준은 [[골든셋 200문항 확장 계획]], 이 규칙들이 나온 근거는 [[검색 실험 골든셋 40문항]].

규칙 R1~R8은 전부 **사람이 40문항을 라벨링하다 실제로 틀린 지점**에서 뽑은 것이다.
심사위원 3인이 전원 통과를 줄 때까지 라운드마다 개정된다.

---

## 네가 하는 일

질문 하나마다 **후보 청크 30~40개**와 **기준답변**이 주어진다.
후보 중에서 **기준답변의 근거가 되는 청크만** 골라 `chunk_id` 목록으로 낸다.

근거가 하나도 없으면 **빈 목록**을 낸다. 이건 실패가 아니라 정답일 수 있다.

## 판단의 기준선

> **이 청크만 읽고 기준답변을 쓸 수 있는가?**

쓸 수 있으면 정답. 없으면 오답. "관련은 있다"는 정답이 아니다.

## 절차

### 1단계 — 기준답변에서 검증할 사실을 뽑는다

기준답변을 읽고 **확인해야 할 사실 조각**을 나열한다. 이게 채점표가 된다.

```
기준답변: "사업기간은 계약일로부터 3개월이며, 안정화기간 1개월이 포함된다."
    → 사실 ①  사업기간 = 계약일로부터 3개월
    → 사실 ②  안정화기간 1개월 포함
```

### 2단계 — 후보를 훑어 사실을 담은 청크를 표시한다

각 사실마다 그것을 담은 청크 번호를 적는다. 사실 하나가 여러 청크에 있을 수 있고,
청크 하나가 여러 사실을 담을 수 있다.

### 3단계 — 최소 집합을 고른다

모든 사실을 덮는 **가장 작은 청크 조합**을 고른다.
같은 사실을 담은 청크가 둘이면 **더 완전한 쪽 하나만** 고른다.

### 4단계 — 아래 체크리스트를 전부 통과시킨다

## 반드시 지킬 규칙

### R1. 다른 문서의 청크는 절대 고르지 않는다

후보에는 **다른 사업의 청크가 섞여 있다.** 검색에 문서 필터가 없기 때문이다.

각 후보의 `doc_id`가 `target_doc_id`와 **정확히 같은지** 확인하고, 다르면 내용이 아무리
그럴듯해도 버린다. 이건 예외 없다.

> 사람이 라벨링했을 때 이 오류가 3건 나왔다. 화면에 문서명이 없어서다. 너는 `doc_id`가
> 보이므로 변명의 여지가 없다.

### R2. 정답 개수를 채우려 하지 마라

"2개쯤 있어야 할 것 같다"는 생각으로 애매한 청크를 추가하지 마라.
**근거가 되는 청크가 1개면 1개, 0개면 0개다.**

골든셋에 틀린 정답이 들어가면 이후 모든 실험이 오염된다.
빠뜨린 정답 하나보다 **잘못 넣은 정답 하나가 3배 해롭다.**

### R3. 표기가 달라도 같은 값이면 정답이다

문서와 기준답변이 **다른 표기법**을 쓰는 일이 흔하다. 숫자를 정규화해서 비교하라.

| 기준답변 | 문서 표기 | 판정 |
|---|---|---|
| `40,000,000원` | `40,000천원` | **같음 — 정답** |
| `3.8억원` | `380,000,000원` | 같음 |
| `210일` | `7개월` | 다름 — 근거 부족 |

단위(천원·백만원·억원)를 원 단위로 환산한 뒤 비교한다.

### R4. 글자가 깨져 있어도 내용으로 판단하라

hwp 추출 오류로 청크 머리에 이런 문자가 붙어 있는 경우가 있다.

```
楴䵴楴䵴4. 제안요청 내용
 3) 사업금액 : 40,000천원(부가세 포함)
```

`楴` `䵴` `䛄` `䱴` `䖴` 같은 한자 비슷한 문자는 **파싱 쓰레기**다. 무시하고 나머지를 읽어라.
이것 때문에 사람이 정답을 놓친 사례가 있다.

### R5. 표가 깨져 보여도 내용이 있으면 정답이다

마크다운 표가 파이프와 빈 칸투성이라 읽기 어려워도, **답이 그 안에 있으면 정답이다.**
서식이 아니라 내용으로 판단하라.

```
|  |  |  |
| --- | --- | --- |
|  | 소형 쉘터형 : 50대 |  |      ← 읽기 나쁘지만 정답임
```

### R6. 정답이 인접 청크로 쪼개졌으면 둘 다 골라라

500자 경계가 표 중간을 자르는 일이 잦다. `::0059`와 `::0060`처럼 **번호가 연속인 청크**가
하나의 표에서 갈라져 나온 것이면, 기준답변의 사실이 양쪽에 나뉘어 있는지 확인하라.

```
::0059  | 요구사항 고유번호 | ECR-002 |  ← 번호는 여기
::0060  세부내용 … 소형 쉘터형 : 50대 …   ← 내용은 여기
```

**둘 다 필요하면 둘 다** 고른다. 다만 한쪽만으로 기준답변이 나오면 한쪽만 고른다(R2).

### R7. 거의 똑같은 청크가 여럿이면 식별자로 가려라

같은 양식의 표가 여러 벌 있는 문서에서는, 잘린 뒤 조각들이 **글자가 거의 같아진다.**

```
후보 25  냉각 FAN(최소 2개이상) … 서지보호기 2P 40kA …   ← 어느 타입인지 안 적혀 있음
후보 26  냉각 FAN(최소 2개이상) … 서지보호기 2P 40kA …
후보 27  냉각 FAN(최소 2개이상) … 서지보호기 2P 40kA …
```

이럴 때는 **`섹션` 필드와 `chunk_id` 순번**을 보고, 앞 조각(식별자를 담은 청크)이 후보에
있는지 확인하라. 앞 조각이 있으면 그것으로 어느 타입인지 특정한다.

특정이 **불가능하면 추측하지 말고 고르지 마라.** 넷 중 하나를 찍는 것은 R2 위반이다.

### R8. 기준답변에 없는 내용이 담겼다고 배제하지는 마라

청크는 대개 기준답변보다 길다. 기준답변의 사실을 **담고 있으면** 정답이고,
그 외에 다른 내용이 더 있는 것은 문제가 아니다.

## 유형별 추가 지침

| 유형 | 지침 |
|---|---|
| `단일세부` | 기본 절차 그대로 |
| `후속` | `선행_턴`의 질문 맥락을 이어 읽는다. 대명사("그 사업")는 선행 턴이 가리키는 대상으로 치환한 뒤 판단 |
| `직답` | 금액·마감일·기관은 `data_list.csv` 메타에서 오는 경우가 많다. **본문에 그 값이 없으면 빈 목록**이 정답이다 |
| `탐색비교` | `대상_doc_id`가 여러 개다. **문서마다 근거를 따로** 고르고 합친다. R1은 "목록에 있는 문서면 허용"으로 완화된다 |
| `모른다` | 근거가 없어야 정상이다. 빈 목록이 기대값. 그럴듯한 청크를 찾아 넣지 마라 |
| `반문` | 대상 문서 자체가 없다. 항상 빈 목록 |

## 출력 형식

문항마다 JSON 한 줄(JSONL):

```json
{"qid":"기존:af85ee75","gold_chunk_ids":["문서::0005"],"facts":["사업기간=계약일로부터 3개월","안정화기간 1개월 포함"],"reason":"후보 12번이 사업기간과 안정화기간을 모두 담고 있어 단독으로 기준답변을 재구성할 수 있다","confidence":"높음"}
```

| 필드 | 내용 |
|---|---|
| `qid` | 입력 그대로 |
| `gold_chunk_ids` | 고른 청크의 `chunk_id`. **후보에 있는 것만.** 없으면 `[]` |
| `facts` | 1단계에서 뽑은 사실 조각 |
| `reason` | 왜 이 조합인가. 빈 목록이면 왜 근거가 없는지 |
| `confidence` | `높음` / `보통` / `낮음` — 애매하면 솔직히 낮음 |

## 스스로 점검할 것

제출 전에 문항마다 확인한다.

- [ ] 고른 청크의 `doc_id`가 전부 `target_doc_id`와 같은가 (R1)
- [ ] 고른 청크만 읽고 기준답변을 쓸 수 있는가
- [ ] 하나를 빼도 기준답변이 나오는 청크가 섞여 있지 않은가 (R2)
- [ ] `chunk_id`를 지어내지 않았는가 — 전부 후보 목록에 있는가
- [ ] 빈 목록으로 낸 문항은, 정말 후보 전체를 다 읽고 없다고 판단한 것인가
