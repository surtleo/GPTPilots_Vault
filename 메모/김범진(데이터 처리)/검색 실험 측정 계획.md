# 검색 실험 측정 계획

라벨링 감사([[검색 실험 골든셋 40문항]])에서 나온 진단을 반영한 측정 설계.
배경 [[검색 실험 구도]] · 구조도 [[검색 품질 개선 (BM25·리랭커)]]

## 왜 변형을 늘리는가

원안은 BM25·리랭커 on/off 2×2였다. 그런데 라벨링 실패 4건을 실측해보니 **원안으로는 답이 안 나오는 질문**이 두 개 생겼다.

| 실측 | 원안이 답 못 하는 질문 |
|---|---|
| 전체 질문 160위 → 핵심어만 2위 (4건 모두 1~4위) | BM25가 나쁜 건가, **우리가 질문을 잘못 넣은 건가**? |
| 정답이 dense 23·35·94위에 있는데 top-20에서 잘림 | 알고리즘 문제인가, **후보 깊이 설정 문제**인가? |

이 둘을 분리하지 않으면 결과를 보고도 "무엇을 고쳐야 하는지"를 말할 수 없다.

## 변형 목록

| 변형 | BM25 | 리랭커 | 후보 K | 쿼리 | 성격 |
|---|---|---|---|---|---|
| **A_dense** | ✗ | ✗ | 20 | 원문 | 베이스라인 |
| **B_hybrid** | ✓ | ✗ | 20 | 원문 | 사전등록 |
| **C_rerank** | ✗ | ✓ | 20 | 원문 | 사전등록 |
| **D_hybrid_rerank** | ✓ | ✓ | 20 | 원문 | 사전등록 |
| **B′_kw** | ✓ | ✗ | 20 | **핵심어** | 탐색 |
| **E_deep** | ✗ | ✓ | **40** | 원문 | 탐색 |
| **F_all** | ✓ | ✓ | **40** | **핵심어** | 탐색 |

- **핵심어 쿼리** = BM25에 넣기 전 질문에서 저IDF 토큰을 걸러낸다. dense 쿼리는 원문 그대로 둔다(임베딩은 문맥이 있어야 함).
- 후보 K는 `RERANK_CANDIDATE_K`. 최종 반환은 모든 변형이 top-5로 동일.

### 사전등록 vs 탐색 — 구분해서 보고할 것

A~D는 **결과를 보기 전에 승격 기준까지 정해둔** 변형이다. B′·E·F는 라벨링 진단을 본 **뒤에** 추가했다.
따라서 **승격 판정은 A~D로만** 하고, B′·E·F는 "다음에 뭘 고칠지"를 정하는 참고 자료로 쓴다.
이 구분을 흐리면 결과를 보고 기준을 만든 셈이 되어 실험이 무의미해진다.

## 측정 대상

- **문항 35개** (전체 40 − 검색 미검출 4 − 검색 대상 아님 1)
- 정답 청크 72개, 문항당 평균 2.1개
- 인덱스 `data/chroma_v2` (30,002청크, 표 헤더 승격 반영본)

## 지표

| 지표 | 역할 |
|---|---|
| **MRR@10** | 주 지표. 첫 정답이 몇 등인가 |
| **nDCG@10** | 정답이 여러 개일 때 위쪽에 몰렸나 (정답 2개 이상 문항이 22개) |
| **Recall@5** | 실제 생성에 넘어가는 top-5의 실질 품질 |
| hit@5 | 회귀 감시용. 문서 단위 적중이 안 깨지는지만 확인 |

**보고는 3분할**: 전체 35 / 기존 26 / 어휘형 9. 어휘형만 좋아지고 기존이 나빠지는 건 개선이 아니라 트레이드오프이고, 합치면 그게 숨는다.

## 승격 기준 (변경 없음 — 원안 그대로)

> A 대비 **전체 MRR@10 +0.05 이상** AND **기존 문항 hit@5 = 1.0 유지** → 프로덕션 반영(플래그 ON).
> 미달 시 미채택으로 기록하고 코드는 OFF로 유지.
> 여러 변형이 통과하고 차이가 0.02 이내면 더 단순한 쪽 (A < B,C < D).

## 실행 순서

### 1단계 — GPU 없이 지금 (로컬 CPU)

`A` · `B` · `B′` 는 리랭커가 없어 CPU로 돈다. **BM25의 순수 효과와 쿼리 처리의 효과를 먼저 확인**한다.

판단 갈림길:
- `B′ ≫ B` → 문제는 BM25가 아니라 **쿼리 처리**였다. 알고리즘 교체(BGE-M3 등) 불필요
- `B′ ≈ B ≈ A` → BM25 자체가 이 코퍼스에서 힘을 못 쓴다. 대안 검토 대상

### 2단계 — GPU 확보 후 (VM L4)

`C` · `D` · `E` · `F`. 리랭커 1,600~3,200회 추론.

**선결 과제**: VM 디스크가 96G 중 1.7G만 남아 리랭커 모델(2.2GB)을 못 받는다. 디스크 확보가 먼저다.
차선책은 맥 CPU 측정(20~40분). MPS는 쓰지 않는다 — 수치가 VM과 갈리면 비교가 무너진다.

### 3단계 — 결과 해석

| 관측 | 해석 | 다음 행동 |
|---|---|---|
| E ≫ C | 병목은 알고리즘이 아니라 **후보 깊이** | `RERANK_CANDIDATE_K` 상향 (설정 한 줄) |
| B′ ≫ B | 병목은 **쿼리 처리** | 저IDF 필터를 프로덕션에 반영 |
| F ≈ D | 추가 조치의 효과 없음 | 원안 판정대로 진행 |
| 전부 A와 비슷 | 순위 문제가 아님 | **인제스트(표 처리)로 투자 전환** |

## 필요한 코드 작업

| 작업 | 내용 | 규모 |
|---|---|---|
| 핵심어 쿼리 필터 | 코퍼스 df 기반으로 저IDF 토큰 제거. `hybrid.py`에 함수 추가 + 테스트 | 소 |
| 변형 스윕 확장 | `run_rerank_experiments.py`의 `VARIANTS`에 후보 K·쿼리 모드 필드 추가 | 소 |
| 결과 3분할 집계 | 이미 있음 (전체/기존/어휘형) | — |

플래그 기본값은 계속 OFF. 측정 스크립트가 변형별로 토글할 뿐 프로덕션 동작은 안 바뀐다.

## 비용

**OpenAI 호출 0건.** 임베딩(로컬 e5)·BM25·리랭커 전부 로컬 모델이라 팀 키 $20 한도와 무관하다.

## 보류 — spec 이탈 안건

`spec.md`/ADR-006이 임베딩을 `multilingual-e5-small`로 고정하고 있다. BGE-M3(dense+sparse+multi-vector 통합)로 교체하면 e5와 BM25를 한 모델로 대체할 수 있고 한국어 성능도 낫지만:

- 30,002청크 재인덱싱 + **라벨 전량 재생성** 필요
- 모델 2.2GB (VM 디스크 문제와 동일)
- 임베딩·sparse·인덱스가 한꺼번에 바뀌어 **무엇 때문에 좋아졌는지 구분 불가**

→ **1단계 결과를 보고 결정한다.** `B′`가 잘 나오면 굳이 바꿀 이유가 없다.
