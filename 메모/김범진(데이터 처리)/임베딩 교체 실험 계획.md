# 임베딩 교체 실험 계획

> 검색의 **기본 엔진**을 바꿀지 판정한다. 리랭커 실험([[검색 실험 결과 (164문항)]])의 후속.
> 개념이 낯설면 → [[개념 색인]] · 특히 [[임베딩]] · [[Dense 검색]]

---

## 0. 세 줄 요약

1. 지금 임베딩(`e5-small`)은 **일부러 작은 걸 골랐고**, 그 약점을 BM25로 메우기로 했었다. **그 BM25가 방금 실패했다.** → §2
2. 리랭커를 채택하면서 **임베딩이 할 일이 바뀌었다.** 순위를 잘 매기는 게 아니라 **정답을 후보 20개 안에 넣는 것**이 임무다. 그래서 주 지표도 바뀐다. → §5
3. 가장 큰 함정은 성능이 아니라 **정답지다.** 지금 정답지는 e5-small이 뽑은 후보에서 만들어져서, 새 모델에 구조적으로 불리하다. → §7

# 1부 · 왜 바꾸려 하나

## 1. 지금 무엇을 쓰고 있나

| | |
|---|---|
| 모델 | `intfloat/multilingual-e5-small` |
| 크기 | 118M 파라미터 · 384차원 |
| 입력 한도 | 512토큰 |
| 프리픽스 | 문서 `passage: ` / 질문 `query: ` **필수** |
| 근거 | `docs/ADR.md` ADR-006 (2026-07-15) |

**작은 걸 고른 건 의도였다.** ADR-006의 이유는 이랬다.

> OpenAI 임베딩 대신 로컬 실행 → $20 한도를 생성·평가에 온전히 배분.
> 재임베딩이 무료라 ablation에 유리. e5-small은 CPU로도 충분.

## 2. 그때 적어둔 약점, 그리고 그 보완책이 실패했다

ADR-006은 트레이드오프를 이렇게 적어놨다.

> 대형 임베딩 모델 대비 **한국어 고유명사·표 검색 품질 한계**
> → 메타데이터 필터·프리픽스 주입·**(백로그) BM25 하이브리드로 보완**

세 보완책 중 앞의 둘은 이미 들어가 있다. 그리고 **세 번째가 방금 기각됐다.**

164문항 실측에서 [[BM25]]는 문서 한정 −0.031, 전체 −0.036으로 양쪽 모두 손해였다
([[검색 실험 결과 (164문항)]] §3).

> **즉, ADR-006이 "이걸로 메우겠다"고 적어둔 보완책이 사라졌다.**
> 약점을 그대로 안고 갈지, 임베딩 자체를 키울지 다시 정해야 하는 시점이다.

이건 `spec.md` §9가 원래 요구한 항목이기도 하다 — *"임베딩 모델 E5-small vs 대안 1개 비교표"*.
Plans 6.1에서 한 번 했지만 **`hit@5`가 1.000으로 포화돼 변별이 안 됐다**([[지표 포화]]).
지금은 순위 지표와 164문항 정답지가 있으니 제대로 다시 잰다.

## 3. 리랭커 채택으로 임베딩의 임무가 바뀌었다

이게 이번 실험 설계의 출발점이다.

```
[예전]  질문 → 임베딩이 20개 찾고 순위도 매김 → 상위 5개 → LLM
                 └── 임베딩이 "찾기"와 "줄세우기"를 다 함

[지금]  질문 → 임베딩이 20개 찾음 → 리랭커가 다시 줄세움 → 상위 5개 → LLM
                 └── 찾기만          └── 줄세우기는 여기가 담당
```

**리랭커는 후보 밖의 것을 데려올 수 없다.** 20개 안에 정답이 없으면 끝이다.

그러니 임베딩을 바꿔서 얻을 수 있는 것은 두 가지인데, 값어치가 다르다.

| 얻는 것 | 리랭커가 대신해주나 | 값어치 |
|---|---|---|
| 정답을 20개 안에 **넣는** 능력 | ❌ 못 함 | **크다** |
| 20개 안에서 정답을 **위로 올리는** 능력 | ✅ 이미 함 | 작다 |

> **예상**: 새 임베딩이 단독 [[MRR]]은 크게 올려도, 리랭커를 켠 종단 성적은 거의 안 오를 수 있다.
> 올린 순위를 리랭커가 어차피 다시 매기기 때문이다. 이건 실패가 아니라 **예상된 결과**이고,
> 그래서 §5처럼 두 지표를 나눠 본다.

# 2부 · 무엇과 비교하나

## 4. 후보 5종

무작정 큰 모델을 넣는 게 아니라, **한 번에 하나씩만 다르게** 해서 무엇이 효과의 원인인지 알 수 있게 짰다.

| # | 모델 | 크기 | 차원 | 프리픽스 | 이 줄이 알려주는 것 |
|---|---|---|---|---|---|
| **E0** | `intfloat/multilingual-e5-small` | 118M | 384 | `query:`/`passage:` | **기준선 (현행)** |
| E1 | `intfloat/multilingual-e5-base` | 278M | 768 | 같음 | **크기만** 키우면 얼마나 오르나 |
| E2 | `BAAI/bge-m3` | 568M | 1024 | 없음 | **계열을 바꾸면** 어떤가 |
| E3 | `nlpai-lab/KURE-v1` | 568M | 1024 | 없음 | E2에 **한국어 튜닝**을 더하면 |
| E4 | `skt/A.X-Encoder-base` | 확인 필요 | 확인 필요 | 확인 필요 | 팀 리서치 후보 |

**대조 구조**: E0→E1은 크기만, E0→E2는 계열만, E2→E3은 한국어 튜닝만 다르다.
E1이 오르는데 E2가 안 오르면 "그냥 크면 된다"는 뜻이고, E3만 오르면 "한국어 튜닝이 관건"이라는 뜻이다.

### E4는 착수 전에 확인이 필요하다

`skt/A.X-Encoder-base`는 팀원이 조사한 후보다([[A.X Encoder base]]).
다만 **이름이 "Encoder"라는 점이 걸린다.** 확인할 것:

- 검색용으로 **파인튜닝된** 모델인가, 아니면 일반 인코더인가
- 일반 인코더를 그대로 쓰면 검색 성능이 낮게 나오는 게 정상이라, 그걸 "이 모델이 나쁘다"로 읽으면 **팀원 제안을 잘못 기각**하게 된다
- `sentence-transformers`로 바로 로드되나 / 풀링 방식은 무엇인가

**확인 전에는 측정하지 않는다.** 조건을 못 맞춘 채 재면 안 재느니만 못하다.

## 5. 무엇으로 재나 — 지표를 둘로 나눈다

§3의 이유로, **하나의 숫자로 판정하지 않는다.**

| 지표 | 무엇을 보나 | 역할 |
|---|---|---|
| **Recall@20** | 정답이 후보 20개 안에 들어왔나 | **진단** — 임베딩 고유의 실력 |
| **종단 MRR@10** (리랭커 ON) | 사용자가 실제로 받는 순위 | **판정** — 채택 여부는 이걸로 |
| 단독 MRR@10 (리랭커 OFF) | 리랭커 없을 때의 순위 | 참고 |

**판정은 종단 성적으로 한다.** 그게 실제로 돌아가는 구성이기 때문이다.
1차 실험에서 프로덕션에 없는 경로를 재서 결론이 뒤집혔던 교훈([[검색 실험 계획 (164문항)]] §15)을 그대로 적용한다.

**Recall@20은 왜 보나**: 종단 성적이 안 올랐을 때 그 이유를 구분하기 위해서다.

| Recall@20 | 종단 MRR | 해석 |
|---|---|---|
| 올랐다 | 올랐다 | 새 모델이 정답을 더 데려왔고 그게 성적으로 이어졌다 → **채택** |
| 올랐다 | 안 올랐다 | 더 데려왔지만 리랭커가 그걸 위로 못 올렸다 → **리랭커 쪽 문제** |
| 안 올랐다 | 안 올랐다 | 임베딩을 키워도 못 찾는 문항이다 → **청킹·질의 쪽 문제** |

# 3부 · 함정

## 6. 정답지가 지금 임베딩 편이다 ★ 이번 실험의 최대 위험

**정답지를 어떻게 만들었는지** 돌이켜 보면 문제가 보인다.

```
164문항 정답지 만든 과정:
  질문 → e5-small로 후보 뽑기 ∪ BM25로 후보 뽑기 → 사람이 그중에서 정답 고르기
          └──────────── 이 풀 안에 없던 청크는 애초에 후보에 못 올랐다 ────────────┘
```

그래서 이런 일이 생긴다.

> 새 모델이 **진짜 정답 청크**를 찾아왔는데,
> 그게 e5-small 후보 풀에 없었어서 라벨이 안 붙어 있고,
> 채점기는 그걸 **오답으로 센다.**

**새 모델은 잘할수록 손해를 보고, 기준선은 항상 유리하다.** 이걸 안 다루면 실험 자체가 무의미하다.

> 이 문제는 이미 한 번 목격했다 — RFID 문항에서 `::0024`가 정답인데
> 후보 풀에 `::0023`과 `::0025`만 있어 라벨이 안 붙은 사례([[골든셋]]).

### 어떻게 다루나 — 전부 라벨링하지 않고 상·하한으로 먼저 본다

라벨이 없는 청크를 전부 사람이 읽으면 모델당 수백 건이다. 대신 **두 번 채점한다.**

| | 라벨 없는 청크를 어떻게 세나 | 누구에게 유리 |
|---|---|---|
| **하한** (비관) | 전부 **오답** 취급 | 새 모델에 불리 |
| **상한** (낙관) | 전부 **정답** 취급 | 새 모델에 유리 |

그리고 이렇게 판단한다.

```
하한에서도 새 모델이 이긴다          → 라벨링 없이 채택 확정 (더 볼 것 없음)
상한에서도 새 모델이 진다            → 라벨링 없이 기각 확정 (더 볼 것 없음)
하한은 지고 상한은 이긴다 (구간이 걸침) → 이때만 라벨링한다
```

**라벨링이 필요해져도 전부 하지 않는다.** 판정을 뒤집을 수 있는 것만 읽으면 된다 —
*새 모델의 상위 10위 안에 있으면서, 이미 있는 정답보다 위에 있고, 라벨이 없는 청크*.
경험상 문항당 0~2건이라 감당 가능한 양이다.

**라벨링은 내(Claude)가 원문을 직접 읽고 한다.** 팀 OpenAI API는 쓰지 않는다
(`CLAUDE.md` CRITICAL — 골든셋 작업은 호출이 광범위해 $20 한도를 빠르게 소진).

## 7. 통제해야 할 것 — 하나라도 놓치면 실험이 무효

### 7-1. 프리픽스를 모델마다 다르게 줘야 한다 ⚠️ 제일 위험

E5 계열은 `passage: ` / `query: `를 **반드시** 붙여야 하고, bge-m3·KURE는 **붙이면 안 된다.**
틀려도 **에러가 안 나고 성능만 조용히 떨어진다**(`spec.md` §190이 경고하는 그 실패 모드).

여기에 함정이 하나 더 있다. 우리 코드의 프리픽스는 이렇게 생겼다.

```python
# src/index/chunk.py:58
return f"{E5_PASSAGE_PREFIX}[{label}]\n"   # → "passage: [섹션명]\n"
```

**`passage: ` 뒤에 섹션 이름이 같이 붙어 있다.** 그러니 프리픽스를 통째로 떼면
섹션 정보까지 날아가서, 새 모델만 정보를 덜 받게 된다.

> **규칙**: E5 계열은 `passage: [섹션명]\n` 그대로, 나머지는 `[섹션명]\n`만 남긴다.
> 모델별 설정으로 분리하고, 각 인덱스 첫 청크의 실제 입력 문자열을 눈으로 확인한다.

### 7-2. 청킹은 절대 건드리지 않는다

`chunk_id`는 `doc_id::0001` 형태로 **몇 번째 청크인지**로 만들어진다([[청크와 chunk_id]]).
청킹이 조금이라도 달라지면 번호가 밀리고, **164문항 정답지 전체가 다른 청크를 가리키게 된다.**

bge-m3는 8192토큰까지 받으니 "청크를 키우면 더 좋지 않나" 싶지만, **그건 다른 실험이다.**
같이 바꾸면 무엇이 효과의 원인인지 알 수 없다.

> **검증 게이트**: 새 인덱스를 만든 직후, chunk_id 집합이 현행 `chroma_v2`와
> **완전히 일치**하는지 확인한다. 하나라도 다르면 그 자리에서 중단한다.
> (청킹 코드가 그사이 바뀌었을 수 있다 — 이건 조용히 어긋나는 종류의 사고다.)

### 7-3. 나머지 고정 항목

| 항목 | 값 |
|---|---|
| 질문 | 164문항 동일 |
| 검색 범위 | 문서 한정 (프로덕션 경로) |
| 후보 수 | 20 |
| 정규화 | `normalize_embeddings=True` 전 모델 공통 |
| 리랭커 | `BAAI/bge-reranker-v2-m3` 동일 |

# 4부 · 실행

## 8. 자원 제약 — VM 디스크가 부족하다

| | |
|---|---|
| VM 여유 | **7.3GB** (96GB 중 89GB 사용, 93%) |
| 필요 추정 | 모델 가중치 4종 ~8GB + 인덱스 4종 ~3GB = **11GB** |

**그대로는 안 들어간다.** 그래서 **한 모델씩 처리하고 지운다.**

```
모델 받기 → 인덱싱 → 후보 캐시 저장(작음) → 인덱스·가중치 삭제 → 다음 모델
```

후보 캐시(chunk_id + 거리)만 남기면 모델당 수 MB다.
[[검색 실험 결과 (164문항)]] §10에서 만든 캐시 방식을 그대로 재사용한다 —
캐시만 있으면 리랭커 채점과 상·하한 계산을 인덱스 없이 다시 할 수 있다.

## 9. 순서

| 단계 | 작업 | 어디서 | 비고 |
|---|---|---|---|
| 1 | E4(A.X-Encoder) 성격 확인 (§4) | 로컬 | 검색용 모델 맞나 |
| 2 | 모델별 프리픽스 설정 분리 (§7-1) | 코드 | **눈으로 검증** |
| 3 | E1 인덱싱 → chunk_id 게이트 (§7-2) | VM | 어긋나면 중단 |
| 4 | E1 후보 캐시 → 인덱스 삭제 | VM | |
| 5 | E2·E3·E4 반복 | VM | 한 번에 하나씩 |
| 6 | 상·하한 채점 (§6) | 로컬 | 라벨링 필요 여부 판정 |
| 7 | (필요 시) 추가 라벨링 | 로컬 | Claude 직접, 팀 API 금지 |
| 8 | 리랭커 종단 채점 | VM | |
| 9 | 승격 판정 (§10) | | |

**1·2번을 건너뛰지 않는다.** 둘 다 "틀려도 에러가 안 나는" 종류라 사후에 발견하기 어렵다.

## 10. 언제 채택하나 — 측정 전에 확정한다

기준선은 **E0 + 리랭커** (현행 프로덕션 예정 구성, 종단 MRR@10 = 0.7443).

| 조건 | 값 | 왜 이 값인가 |
|---|---|---|
| **주 기준** | 종단 MRR@10 차이의 **95% 신뢰구간 하한 > 0** | 아래 참조 |
| **최소 폭** | 점추정 **+0.03 이상** | 재인덱싱 한 번이면 되고 질의 시간 증가는 리랭커(270ms) 옆에서 무시할 수준이라, "비용을 넘는가"보다 "노이즈가 아닌가"가 관건 |
| **회귀 금지** | 어떤 유형도 −0.03 이하로 떨어지지 않을 것 | 평균이 오르면서 한 유형이 망가지는 걸 막는다 (BM25가 정확히 그랬다) |

### 신뢰구간을 쓰는 이유

**지난번에 이것 때문에 틀렸다.** 36문항에서 +0.073이 나와 "확정"이라고 적었는데,
164문항에서 −0.031로 부호가 뒤집혔다([[검색 실험 결과 (164문항)]] §5).

문항별 차이를 재표본추출(paired bootstrap)해서 **차이가 0을 넘는다고 말할 수 있는지**를 본다.
"평균이 올랐다"만으로는 또 같은 실수를 한다.

> 여러 모델이 통과하면 **작은 쪽**을 고른다. E1(278M)과 E3(568M)이 비슷하면 E1이다.

# 5부 · 예상되는 결과와 리스크

## 11. 미리 적어두는 예상

**결과를 보고 말을 바꾸지 않기 위해** 먼저 적는다.

1. **Recall@20은 오를 것이다.** 큰 모델이 한국어 고유명사·표를 더 잘 잡는다는 게 ADR-006이 인정한 약점이다.
2. **종단 MRR은 그보다 덜 오를 것이다.** §3의 이유 — 순위 개선분은 리랭커가 이미 먹었다.
3. **탐색비교·후속 유형은 거의 안 오를 것이다.** 리랭커도 이 둘은 못 올렸다(+0.034 / +0.005). 여러 문서를 걸치는 문제라 임베딩 교체로 풀릴 성질이 아니다.

**2번이 맞으면 채택 기준을 못 넘을 가능성이 실제로 있다.** 그건 실패가 아니라
"리랭커가 이미 그 몫을 하고 있다"는 유용한 결론이다.
