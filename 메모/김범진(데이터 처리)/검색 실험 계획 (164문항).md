### 모수 — 200이 아니라 164다

골든셋은 200문항이지만 **MRR 채점이 성립하는 건 164문항**이다. 숫자를 섞어 쓰지 않는다.

| 수 | 무엇 | 용도 |
|---|---|---|
| **200** | 골든셋 전체 (VM `v3_20260729`) | 데이터셋 크기 |
| **164** | **이 실험의 모수** — 정답 청크가 있는 문항 | **MRR·nDCG·Recall 채점** |
| 30 | 모른다 15 + 반문 15 | **거짓양성 검사** (§6-3) — MRR 대상 아님 |

# 1부 · 무엇을 왜 재는가

## 1. 배경 — 예비 실험에서 확정된 것

40문항 예비 실험([[검색 개선]] 2부)에서 결론이 두 번 뒤집히며 **세 가지가 확정**됐다.
본 실험은 이 위에서 시작한다.

| # | 확정 사실 | 근거 |
|---|---|---|
| 1 | **BM25는 검색 범위를 문서로 좁혔을 때만 효과가 있다** | 전체 코퍼스 +0.002 / 문서 한정 **+0.073** |
| 2 | **프로덕션 코드에서 BM25는 죽은 코드다** | `retrieve.py:36`의 `and doc_id is None`. 라우터는 `doc_id` 없이 `retrieval`에 도달하지 않음 → 조건이 **항상 거짓** |
| 3 | **표만 검색하는 방식은 역효과** | 정답 청크의 상당수가 표가 아님. 어휘형에서도 0.701 → 0.593 |

### 왜 BM25는 좁혀야만 되나 (메커니즘)

질문이 **"〈사업명 10토큰〉에서 〈핵심어 1~2토큰〉은?"** 형식이라, BM25 합산 점수에서
사업명을 반복하는 개요·표지 청크가 정답을 이긴다. 실측 — 네팔 `ISO 4373` 정답이 59등,
1등은 같은 문서의 `## 1. 과업개요`.

사업명 토큰은 **문서를 좁히는 데는 필수**(제거하면 0.126으로 붕괴)지만
**문서 안에서 청크를 고르는 데는 방해**다. 두 역할이 충돌한다.
문서를 외부에서 좁혀주면 첫 역할이 불필요해지고 충돌이 풀린다.

### 남은 미해결 — 청크 단위 검색이 약하다

기존 문항 dense MRR **0.527**. `hit@5 = 1.000 포화`는 **문서 단위** 얘기였고,
**청크 단위로는 절반 수준**이다. 하이브리드로도 0.650까지밖에 못 올린다.
**본 실험의 진짜 목표는 이 구간을 얼마나 올릴 수 있느냐다.**

## 2. 가설

| # | 가설 | 검증 방법 |
|---|---|---|
| **H1** | 문서 한정 하이브리드가 dense 단독보다 낫다 | 40문항에서 +0.073. **164문항에서 재현되는가** |
| **H2** | 이득이 유형마다 다르다 | 유형별 Δ 분리. 표·고유번호가 많은 유형에서 클 것 |
| **H3** | 리랭커가 하이브리드보다 낫다 | dense가 상위 20에 정답을 갖고도 순위를 못 매기는 게 주 병목이므로 |
| **H4** | 하이브리드 + 리랭커가 최선이다 | 상호작용 확인. 둘이 같은 걸 고치면 이득이 안 겹칠 수 있음 |

## 3. 베이스라인

> **베이스라인은 언제나 "지금 프로덕션이 실제로 하는 것"이다.** 절대 점수는 의미 없다.

| 항목 | 현행 |
|---|---|
| 검색 | **dense 단독** (`multilingual-e5-small`, `query:`/`passage:` 프리픽스) |
| 인덱스 | Chroma `chunks` — 30,002청크 / 99문서 / 표 63.3% |
| 범위 | **항상 문서 한정** — 라우터가 `doc_id`를 확정한 뒤에만 검색 진입 |
| top-k | `RETRIEVAL_TOP_K = 5` (후보 폭 `RERANK_CANDIDATE_K = 20`) |
| BM25 | `RETRIEVAL_USE_BM25 = False` (게다가 켜도 동작 안 함 — §1-2) |
| 리랭커 | `RETRIEVAL_USE_RERANKER = False` |

# 2부 · 평가셋

## 4. 200문항의 실제 구성

**200문항이 전부 검색 채점 대상이 아니다.** 유형마다 성격이 다르다.

**정본은 VM `v3_20260729`다** (로컬 작업본보다 최신). 실측 기준:

| 유형 | 문항 | 빈 정답 | 정답 청크 | **채점** | 성격 |
|---|---|---|---|---|---|
| 단일세부 | 90 | 0 | 171 | **90** | 한 문서 안의 특정 사실 |
| 탐색비교 | 25 | 0 | 58 | **25** | **문서 2개 비교** (25/25 다중문서) |
| 후속 | 30 | 1 | 49 | **29** | **선행_턴 있는 대화형** |
| 직답 | 25 | 5 | 32 | **20** | 짧은 사실 (금액·기간·번호) |
| 모른다 | 15 | 15 | 0 | ✗ | 정답 청크 **없는 게 정답** |
| 반문 | 15 | 15 | 0 | ✗ | 라우터가 되물어야 함 |
| **계** | **200** | **36** | **310** | **164** | |

- **모른다·반문 30문항**은 빈 정답이 **설계상 정상**이다. MRR 대상이 아니지만
  **거짓양성 검사**로 쓴다 (§6-3)
- **직답 5건 + 후속 1건 = 6건**만이 "정답이 있어야 하는데 없는" 케이스.
  라우터 `direct_meta`가 CSV로 답하는 문항이면 정상 제외, 아니면 라벨 결함 → §7-5에서 판정

> ⚠️ **40문항 때의 교훈**: 빈 정답 중 일부는 "정답이 없는 것"이 아니라
> **"후보 풀에 안 들어온 것"**이었다(4건 중 2건). 위 6건은 전수 원문 대조로 확인하고 시작한다.

## 5. 유형별 특수 처리 — 실험 코드가 반드시 구현할 것

### 탐색비교 (25문항) — 문서 2개

`target_doc_id`가 **리스트(2개)**다. 25문항 전부 2개 문서.

```
검색 = 문서A 한정 top-k  ∪  문서B 한정 top-k  → 융합 → 최종 순위
```

문서별로 따로 뽑아야 한다. 한쪽 문서가 후보를 독식하면 비교 자체가 불가능하다.
(후보 풀도 이 방식으로 만들어졌다 — 문항당 후보 66~68개)

### 후속 (29문항) — 선행_턴

`선행_턴`에 이전 질문이 배열로 들어 있고, `query`는 **선행 질문 + 후속 질문이 합쳐진 문자열**이다.

```json
"선행_턴": ["한영대학교 트랙운영 학사정보시스템 고도화 사업의 사업기간은 어떻게 되나요?"],
"query":   "한영대학교 ... 사업기간은 어떻게 되나요? 그 사업의 안정화기간은 얼마나 포함되나요?"
```

**실험은 `query`를 그대로 쓴다.** 실전 라우터는 `active_doc_id`로 문서를 유지하는데,
검색 성능만 재는 실험에서는 문서가 이미 확정된 상태이므로 등가다.
단 **이 결정을 결과에 명시**한다 — 라우터의 후속 처리 정확도는 별도 문제다.

### 직답 (20문항)

일부는 라우터가 `direct_meta`로 처리해 **검색을 안 탄다**(`data_list.csv`에서 직답).
검색 실험 대상은 **CSV 결측으로 retrieval 폴백되는 것**뿐이다.
→ 라벨에 정답 청크가 있는 20문항만 채점하므로 자동으로 걸러진다.

## 6. 지표

### 6-1. 주 지표 — MRR@10

첫 정답 청크가 **몇 등**인가. 1등=1.0, 2등=0.5, 5등=0.2, 10위 밖=0.

실전에서 상위 5개만 LLM에 넘긴다. **20등의 정답은 없는 것과 같다.**

### 6-2. 보조

| 지표 | 용도 |
|---|---|
| nDCG@10 | 정답이 여러 개일 때 위쪽 쏠림 (탐색비교는 문항당 정답 2.3개 평균) |
| Recall@5 | 상위 5개에 정답이 몇 개 들어왔나 |
| doc_hit@5 | 탐색비교 전용 — **두 문서가 모두** 상위에 들어왔나 |

### 6-3. 모른다·반문 30문항 — 거짓양성 검사

MRR로는 못 재지만 **버리지 않는다.** 검색이 근거 없는 청크를 자신 있게 가져오면
생성 단계에서 환각이 된다.

> **측정**: 상위 5개 청크의 최고 유사도 점수 분포. 정답 있는 문항과 비교해
> **분리도**가 유지되는지 본다. BM25·리랭커가 이 분리를 무너뜨리면 감점.

### ⚠️ 포화 지표 주의

| 지표 | 상태 |
|---|---|
| `hit@5` (**문서 단위**) | **1.000 포화** — 쓰지 마라 |
| `hit@5` (**청크 단위**) | 포화 아님 (dense MRR 0.527) |

**포화됐다고 조건을 바꾸지 마라.** 포화는 그 조건에서 잘 되고 있다는 신호다.
변별력이 필요하면 **더 어려운 문항**이나 **더 민감한 지표**를 쓴다.
— 40문항 실험이 이걸 어겨서(`doc_id` 필터 해제) 틀렸다.

## 7. 선결 조건 — 라벨 신뢰도

> **이게 끝나기 전에는 실험을 시작하지 않는다.**

VM `v3_20260729`에 200문항 라벨이 올라와 있지만, 이 라벨은
**합격선을 못 넘은 스킬**로 만들어졌다. 라벨러 스킬 r8 실측:

| 기준 | 필요 | r8 | |
|---|---|---|---|
| 재현율 | ≥0.90 | 0.836 | ❌ |
| 정밀도 | ≥0.80 | 0.772 | ❌ |
| 완전+포함 | ≥0.70 | 0.725 | ✅ |
| 거짓판정 | 0 | 0 | ✅ |

그래서 **독립 검증자**를 붙였고, 실제로 50문항 검증에서 **8건(16%) 수정**이 나왔다.

| # | 선결 작업 | 현황 |
|---|---|---|
| 1 | rest130 검증 완료 | **50/130** — 80문항 남음 |
| 2 | pilot40 검증 | 미착수 |
| 3 | `held_for_review` 18건 사람 확인 | **사용자 몫** |
| 4 | `known_defects` 4건 처리 방침 | 이미지 안에만 있는 정답 등 → **제외 확정** |
| 5 | **빈 정답 6건 원문 대조** (직답 5 · 후속 1) | 40문항 때 4건 중 2건이 "후보 누락"이었음 |
| 6 | 검증 반영 후 **VM v4 업로드** | v3는 검증 전 스냅샷 |

> **라벨 오류율 16%가 남은 채로 실험하면, 방식 간 차이(+0.07)보다 노이즈가 크다.**

# 3부 · 실험 설계

## 8. 조건 — 하나뿐이다

| 축 | 값 | 이유 |
|---|---|---|
| 검색 범위 | **문서 한정만** | 프로덕션에 다른 경로가 없음 (§1-2) |
| 문서 지정 | **골든셋 `target_doc_id` 주입** | 검색 성능만 분리해 측정 |

> **전체 코퍼스 조건은 측정하지 않는다.** 프로덕션에 존재하지 않는 경로다.
> 40문항 실험이 이 조건을 재느라 무의미한 결론을 냈다.

**라우터 정확도로 할인하지 않는다.** 라우터가 문서를 틀리면 dense도 하이브리드도
똑같이 실패하므로, **방식 간 차이는 라우터와 무관**하다.
(라우터 정확도는 "검색 전체가 쓸모 있나"의 문제로, 별도 실험 대상)

## 9. 비교 변형

| 변형 | 구성 | 묻는 것 |
|---|---|---|
| **A_dense** | 현행 | 베이스라인 |
| **B_hybrid** | dense + BM25 (RRF) | 어휘 신호가 보태지는가 (H1) |
| **C_rerank** | dense + 크로스인코더 | 순위 재배열이 더 나은가 (H3) |
| **D_hybrid_rerank** | 둘 다 | 이득이 겹치는가 (H4) |

**RRF**: 두 검색기의 점수는 척도가 달라 못 섞으므로 **등수만** 쓴다.
`점수 = Σ 1/(60 + 등수)`. 가중치 튜닝이 필요 없다는 게 RRF를 고른 이유.

**리랭커**: `BAAI/bge-reranker-v2-m3` (568M). GPU 필요 → **VM L4에서 실행**.

## 11. 승격 기준

> **측정 전에 확정한다. 결과를 보고 바꾸지 않는다.**

| # | 기준 |
|---|---|
| 1 | A_dense 대비 **MRR@10 +0.05 이상** |
| 2 | **어느 유형에서도 −0.02 이상 나빠지지 않을 것** (회귀 금지) |
| 3 | 모른다·반문 30문항의 **분리도가 유지될 것** (거짓양성 악화 금지) |
| 4 | 조건이 **실전과 동일**할 것 (문서 한정) |

- 하나라도 미달이면 **미채택**으로 기록하고 플래그는 OFF로 남긴다
- 여러 변형이 통과하고 차이가 0.02 이내면 **더 단순한 쪽** (A < B,C < D)
- **채택 시 선결**: `retrieve.py:36`의 `and doc_id is None` 제거 + **동시성 락**
  (Plans 6.7 — `ask()`가 동기 함수라 FastAPI 스레드풀에서 BM25 인덱스·리랭커 중복 로드 → L4 OOM 위험)

## 12. 실행 환경

> ### 🔴 `CHROMA_DIR_OVERRIDE`로 인덱스를 명시하지 않으면 결과가 전부 틀린다.

`chunk_id`가 위치 기반(`doc_id::순번`)이라 인덱스가 다르면 **같은 id에 다른 본문**이 들어간다.
**id는 100% 매칭돼서 에러 없이 조용히 돌아간다.**

## 15. 교훈 (40문항 실험에서)

> **측정 편의를 위해 실전 조건을 바꾸면, 그 실험은 실전에 대해 아무 말도 못 한다.**

`doc_id` 필터를 끈 이유가 *"지표가 포화돼 변별력이 없어서"*였다.
그 결과 **프로덕션에 존재하지도 않는 경로**를 측정하고 "BM25 기각"이라고 결론냈다.

**"승격 기준을 측정 전에 확정한다"는 규칙을 지키느라 조건 설정 자체는 검토하지 않았다.**
기준을 고정하는 것과 조건을 검증하는 것은 별개다. 전자만 지키면 *엄격하게 잘못된 답*이 나온다.
