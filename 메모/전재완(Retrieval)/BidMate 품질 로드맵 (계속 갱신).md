- **우선순위**: ① 정확성·신뢰성 버그(잘못된 답, 거짓 결과) → ② 안정성(멈춤·크래시·
  레이스컨디션) → ③ 비용 낭비 → ④ UX 거칠음 → ⑤ 새 기능

  **시각적 버그(레이아웃·애니메이션)는 회원님이 가끔 봐주셔야 발견됨.**

### 라운드 2 (2026-07-30) — feat/ux-v6-workspace 머지 직후

팀원이 `feat/ux-v6-workspace`를 머지하면서 라우터 기반 화면(`/chat`·`/profile`·
`/recommendations`)이 사라지고 **4단 상시 워크스페이스**(NavSidebar|DocsPanel|
Viewer|ChatPanel)로 구조가 바뀜. 제가 이번 세션에 만든 상태 레이어(추천 캐시·
활성 문서·프로필)는 그대로 살아 확장됐고, 채팅은 `chat-sessions-context`가
`chat-flows.tsx`(새 파일, 프로토타입의 flowReco·flowCompare·flowSummary·flowReady를
실제 엔드포인트에 연결)로 한 단계 더 커짐. 이 새 흐름 레이어를 코드 정독으로 검토.

**발견 1 — 추천 대조 진행 카드가 세션 전환 중 엉뚱한 대화로 샘 [신뢰성·안정성]**

새 "최근 대화" 사이드바로 대화를 여러 개 넘나들 수 있게 됐는데, `chat-flows.tsx`의
`pushLocal`/`patchCard`는 항상 **"지금 보고 있는 세션"**(`chat-sessions-context`의
`currentId`)에만 쓰도록 되어 있었다. 맞춤 공고 대조(`runReco`)는 1~2분 걸리는데
(주석에 이미 명시돼 있던 사실), 그 사이 사용자가 사이드바에서 다른 대화로
넘어가면:
- 진행 카드("적합도 높은 공고 선별 중…")는 원래 세션 A에 남아 있는데, `patchCard`가
  대상을 `currentId`(이제 세션 B)로 찾아서 A의 카드를 찾지 못해 **조용히 무시**
  (no-op) → 세션 A는 "대조하는 중…" 스피너로 **영원히 멈춘 채** localStorage에
  저장됨(새로고침해도 안 풀림 — 라운드 1 미해결 항목 7과 겹치는 지점).
- 대조가 끝나면 `pushLocal`이 완료/실패 메시지를 이번엔 **세션 B**(사용자가
  실제로 보고 있는, 이 흐름과 무관한 대화)에 끼워 넣는다 — 맥락 없는 "참가자격을
  대조해 담아뒀어요" 메시지가 엉뚱한 대화에 뜬다.
- 코드 정독만으로 발견(브라우저 없이 재현 불가한 종류의 버그라 정적 분석이 유일한
  검증 수단이었음) — `chat-sessions-context.tsx`의 `patchCard`/`pushLocal` 구현이
  `s.id === currentId`로만 필터링하는 걸 확인해 확정.

→ **수정**: `chat-sessions-context`에 `currentIdRef`(state를 동기 미러링하는 ref)와
`peekCurrentId()`를 추가하고, `pushLocal`/`patchCard`가 선택적 `sessionId`를 받게
확장. `chat-flows.tsx`의 `runReco`가 흐름 시작 시점에 `peekCurrentId()`로 세션을
고정해서(`recoCardRef`가 `{id, sessionId}` 쌍을 들고 있음) 이후 모든 패치·메시지가
그 세션으로 향하도록 함 — `sessionId`를 명시한 쓰기는 화면도 그쪽으로 튕기지 않음
(다른 대화를 보던 중 갑자기 화면이 바뀌는 것도 같이 막음). `tsc -b`·`lint`·
`format:check`·`build` 전부 통과 확인. 브랜치 `fix/session-scoped-background-flows`
(GPTPilots_Webs), 커밋 `a5fbe1b`, PR 대기 중.

**같은 유형이지만 아직 안 고친 자리** — `runSummary`(핵심 정리, `/ask` 1회)·
`runReady`/`judge`(입찰 준비 점검, `/eligibility` 1회)·`answerAsk`(확인 질문 답변
후 재판정)도 원리상 같은 버그가 있다. 다만 이쪽은 네트워크 호출이 보통 수 초
내로 끝나 사용자가 그 사이 대화를 옮길 확률이 낮아 우선순위를 낮춰 다음 라운드로
미룸. 고칠 때는 이번에 추가한 `sessionId` 파라미터를 그대로 넘기면 된다.

**테스트했으나 문제 없었던 것**
- `workspace-context.tsx`의 탭 열기/닫기·`addFile`(같은 id로 재생성 시 교체)
  로직 — 정상
- `docKey`/`genKey`/`parseKey` 왕복 — 정상
- `api.ts`의 doc_id 인코딩(`encodeURIComponent`) — 라우터 제거 후에도 여전히

  기존 "useParams 이중 디코딩" 경고가 가리키던 위험은 이번 개편으로 오히려
  사라짐(라우터가 없으니 react-router 디코딩도 없음)

### 라운드 3 (2026-07-30) — 아직 안 본 새 컴포넌트 계속 검토

docs-panel.tsx, viewer/*(doc-viewer·viewer.tsx), chat/cite.tsx, chat/chat-panel.tsx를
코드 정독. 이번에도 진짜 버그 두 개 발견·수정.

**발견 1 — 인용 각주가 엉뚱한 위치를 하이라이트할 수 있음 [신뢰성]**

`chat/cite.tsx`의 `CiteChip`이 `openCite(docId, quote, section)`을 호출할 때
`openCite(docId, section, section)`처럼 **section을 quote 자리에도 그대로
넘기고** 있었다. citations[]엔 실제 인용 발췌문이 없어(NDA 정책상 청크 원문
미제공, `src/api/core.py`) 섹션명("제출서류" 등)만 있는데, 그 섹션명 문자열을
`doc-viewer.tsx`의 `FullText`가 원문 전체에서 `markdown.indexOf()`로 검색해
하이라이트·자동스크롤 위치로 썼다. 섹션명이 목차 등 다른 곳에 우연히 있으면
근거와 무관한 위치를 확신 있게 보여주는 셈 — `doc-viewer.tsx`가 이미 지키고
있던 "못 찾으면 하이라이트 없이 원문만 보여준다(억지로 근사매칭하지 않는다)"는
원칙을, 애초에 quote 자리에 진짜 발췌문이 아닌 값을 넣어서 무력화하고 있었다.
→ quote를 `null`로 바로잡고, "인용 누르면 원문 펼침" 동작 조건도 quote 유무가
아니라 인용 자체의 유무로 바꿔서 기존 UX는 유지. 브랜치
`fix/cite-highlight-wrong-target`, 커밋 `f585ecf`.

**발견 2 — 채팅 "정리" 명령이 실제로 친 문장을 버림 [정확성]**

`chat-panel.tsx`의 `submit()`에서 `runReco(text)`·`runCompare(text)`·
`runReady(text)`는 사용자가 실제로 입력한 문장을 그대로 넘기는데,
`runSummary()`만 인자 없이 호출해서 "계약 조건 좀 정리해줘"처럼 구체적으로
물어봐도 기본값("핵심 정리해줘")으로 뭉개지고, 화면 말풍선에도 사용자가 안 친
문장이 남았다. 나머지 세 흐름과 동일하게 `text`를 넘기도록 수정. 브랜치
`fix/summary-flow-drops-user-text`, 커밋 `c006d66`.

**곁들여 발견 — 키워드 기반 흐름 라우팅 자체의 한계 [정의 필요, 안 고침]**

`submit()`은 문장에 "맞춤/추천"·"비교"·"준비/점검"·"정리"가 들어 있으면
무조건 해당 흐름(추천 재검색·비교표·준비점검·핵심정리)으로 보내고 일반
`/ask`로는 안 간다. "이 두 공고 비교하면 어느 쪽이 유리해?"처럼 구체적인
질문도 전부 정형화된 흐름으로 가로채여진다 — 틀린 답은 아니지만 사용자가
실제로 물은 뉘앙스를 반영 못 한다. 정규식을 어떻게 좁힐지는 제품 판단이
필요해 이번엔 안 건드림. 근거: `chat-panel.tsx` `submit()`.

**테스트했으나 문제 없었던 것**

## 이미 알려진 미해결 항목 (이전 세션에서 발견, 아직 미착수)

우선순위 순서:

1. **[신뢰성] 치명적 단일 요건의 즉시 탈락 처리 안 됨**
   지금 verdict는 미충족 **개수**로만 갈림(0/1~3/4+). 대기업 참여 제한처럼
   개수와 무관하게 그 자체로 탈락인 요건이 있는데, 구분 없이 개수 기준에
   섞여 있음 — "확인필요"로 잘못 표시될 수 있음. 요건에 "치명도" 플래그
   필요. 근거: [[참가자격 매칭 — 기능 설계]] §9-1.

2. **[정의 필요] "협상에 의한 계약체결 방식" 참가자격 포함 여부**
   한국전기안전공사 문서에서 발견된 항목 — 참가자격(누가 참여 가능한가)이
   아니라 계약방식 정보인데, 팀원은 참가자격 범주에 넣고 싶어함. 팀 합의
   필요, 제가 임의로 결정하면 안 되는 영역. 근거:
   [[참가자격 매칭 — 추출 정확도 디버깅]].

3. **[기능 한계] 대화가 활성 문서 A 하나만 근거로 삼음**
   활성 문서를 B·C까지 담아도, `/ask`가 `doc_id` 하나만 받아서 대화는 A
   기준으로만 답함. "두 공고 차이가 뭐야?" 같은 질문에 진짜 두 문서를
   근거로 답하려면 백엔드 `/ask` 계약을 `doc_id` 리스트로 확장해야 함.

4. **[UX] 문서 비교 화면에 차이 자동 하이라이트 없음**
   활성 문서 2개 이상을 나란히 볼 때 다른 조항을 자동으로 표시해주는 기능
   없음. LLM 추가 호출이 필요해 보류 중.

5. **[환경] GPU 공유 자원 경합**
   공유 VM이라 팀원이 GPU를 많이 쓰면 백엔드(임베딩 모델)가 아예 못 뜸.
   코드로 해결 불가 — 팀 차원의 GPU 사용 시간 조율 또는 임베딩 CPU 폴백
   고려 필요.

6. **[검증 안 됨] 후보 8건 vs 15건 공정 비교**
   같은 프로필로 K=8, K=15를 각각 돌려서 실제 소요시간·정확도 차이를
   측정한 적 없음(매번 다른 프로필로 테스트해서 비교가 불공정했음). 근거:
   [[공고 추천 — 로딩 개선(캐시·스트리밍·후보수)]].

7. **[정리] 대화 히스토리는 localStorage뿐, 기기 간 동기화 안 됨**
   서버 저장이 아니라서 다른 브라우저·컴퓨터에서는 히스토리가 안 보임.
   여러 사람이 같이 쓸 계획이면 서버 쪽 저장으로 옮겨야 함. 근거:
   [[대화 히스토리 — 세션 목록·삭제]].

  파라미터를 적용해 세션 전환 중 결과가 새는 걸 마저 막기(우선순위 낮음)

  여러 건 체크했을 때 나머지는 조용히 무시되는지, 사용자에게 안내가 있는지 확인
- `send()`도 `currentIdRef` 기반으로 통일할지 검토(지금은 클로저 `currentId`를
  써서 라운드 2와 같은 유형의 잠재 위험이 이론상 남아 있으나, 호출 패턴상
  아직 실제 트리거 경로는 못 찾음)
- `chat-panel.tsx`의 키워드 라우팅("맞춤/추천"·"비교"·"준비/점검"·"정리")을
  좁힐지 — 일반 질문이 우연히 그 단어를 포함하면 정형화된 흐름으로 가로채임
  (라운드 3에서 발견, 제품 판단 필요라 보류)
- `active-docs-context`의 `add()` 반환값이 클로저 상태 기준이라 이론상 스테일
  가능(라운드 3에서 발견, 현재는 트리거 경로 없음) — `doc-picker.tsx` 외에
  `add()`를 쓰는 자리가 새로 생기면 재검토
