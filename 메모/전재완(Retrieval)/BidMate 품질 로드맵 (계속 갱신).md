- **우선순위**: ① 정확성·신뢰성 버그(잘못된 답, 거짓 결과) → ② 안정성(멈춤·크래시·
  레이스컨디션) → ③ 비용 낭비 → ④ UX 거칠음 → ⑤ 새 기능

  **시각적 버그(레이아웃·애니메이션)는 회원님이 가끔 봐주셔야 발견됨.**

### 라운드 2 (2026-07-30) — feat/ux-v6-workspace 머지 직후

팀원이 `feat/ux-v6-workspace`를 머지하면서 라우터 기반 화면(`/chat`·`/profile`·

Viewer|ChatPanel)로 구조가 바뀜. 제가 이번 세션에 만든 상태 레이어(추천 캐시·

`chat-flows.tsx`(새 파일, 프로토타입의 flowReco·flowCompare·flowSummary·flowReady를
실제 엔드포인트에 연결)로 한 단계 더 커짐. 이 새 흐름 레이어를 코드 정독으로 검토.

**발견 1 — 추천 대조 진행 카드가 세션 전환 중 엉뚱한 대화로 샘 [신뢰성·안정성]**

새 "최근 대화" 사이드바로 대화를 여러 개 넘나들 수 있게 됐는데, `chat-flows.tsx`의
`pushLocal`/`patchCard`는 항상 **"지금 보고 있는 세션"**(`chat-sessions-context`의
`currentId`)에만 쓰도록 되어 있었다. 맞춤 공고 대조(`runReco`)는 1~2분 걸리는데
(주석에 이미 명시돼 있던 사실), 그 사이 사용자가 사이드바에서 다른 대화로
넘어가면:
- 진행 카드("적합도 높은 공고 선별 중…")는 원래 세션 A에 남아 있는데, `patchCard`가
  대상을 `currentId`(이제 세션 B)로 찾아서 A의 카드를 찾지 못해 **조용히 무시**
  (no-op) → 세션 A는 "대조하는 중…" 스피너로 **영원히 멈춘 채** localStorage에
  저장됨(새로고침해도 안 풀림 — 라운드 1 미해결 항목 7과 겹치는 지점).
- 대조가 끝나면 `pushLocal`이 완료/실패 메시지를 이번엔 **세션 B**(사용자가
  실제로 보고 있는, 이 흐름과 무관한 대화)에 끼워 넣는다 — 맥락 없는 "참가자격을
  대조해 담아뒀어요" 메시지가 엉뚱한 대화에 뜬다.
- 코드 정독만으로 발견(브라우저 없이 재현 불가한 종류의 버그라 정적 분석이 유일한
  검증 수단이었음) — `chat-sessions-context.tsx`의 `patchCard`/`pushLocal` 구현이
  `s.id === currentId`로만 필터링하는 걸 확인해 확정.

→ **수정**: `chat-sessions-context`에 `currentIdRef`(state를 동기 미러링하는 ref)와
`peekCurrentId()`를 추가하고, `pushLocal`/`patchCard`가 선택적 `sessionId`를 받게
확장. `chat-flows.tsx`의 `runReco`가 흐름 시작 시점에 `peekCurrentId()`로 세션을
고정해서(`recoCardRef`가 `{id, sessionId}` 쌍을 들고 있음) 이후 모든 패치·메시지가
그 세션으로 향하도록 함 — `sessionId`를 명시한 쓰기는 화면도 그쪽으로 튕기지 않음
(다른 대화를 보던 중 갑자기 화면이 바뀌는 것도 같이 막음). `tsc -b`·`lint`·
`format:check`·`build` 전부 통과 확인. 브랜치 `fix/session-scoped-background-flows`
(GPTPilots_Webs), 커밋 `a5fbe1b`, PR 대기 중.

**같은 유형이지만 아직 안 고친 자리** — `runSummary`(핵심 정리, `/ask` 1회)·
`runReady`/`judge`(입찰 준비 점검, `/eligibility` 1회)·`answerAsk`(확인 질문 답변
후 재판정)도 원리상 같은 버그가 있다. 다만 이쪽은 네트워크 호출이 보통 수 초

미룸. 고칠 때는 이번에 추가한 `sessionId` 파라미터를 그대로 넘기면 된다.

**테스트했으나 문제 없었던 것**

### 라운드 5 (2026-07-30) — 백엔드 curl 엣지케이스 + 다크모드 대비 코드 리뷰

**발견 1 — `/recommendations/stream`이 클라이언트가 사라져도 LLM 매칭을 계속 돎
[비용낭비, 코드 미수정]**

`recommend_progress()`의 배치 매칭 루프가 `ThreadPoolExecutor`로 돌아가는
**동기(sync) 제너레이터**인데, 어디에도 "요청이 아직 살아있나?"를 확인하는
코드가 없음(`is_disconnected` 계열 호출 전무 — grep으로 확인). Starlette가 sync
제너레이터를 스레드풀에서 돌리는데, 파이썬 스레드는 강제로 멈출 수 없어서 —
사용자가 브라우저를 닫거나 터널 연결이 끊겨도(하트비트로 이미 확인된 실제
시나리오) **서버는 그 사실을 모른 채 나머지 배치 매칭을 실제로 다 돌리고 실제
OpenAI 비용을 계속 씀.** 실측은 안 함(실제로 재현하려면 진짜 매칭 LLM 호출
비용이 들어서, 공유 예산 고려해 코드 정독으로만 확인하고 라이브 테스트는 보류).
고치려면 `request.is_disconnected()`를 스트림 루프 중간에 주기적으로 확인해서
끊겼으면 남은 future를 취소하는 로직이 필요한데, sync 제너레이터 안에서 async
메서드를 호출해야 해서 구조를 좀 바꿔야 함 — 실제로 살려서 확인하려면 비용이
드니 진행 방식을 먼저 상의할 것.

**발견 2 — 라이트모드 배지 색이 WCAG 대비 기준 미달 [UX, 코드 미수정]**

`index.css`의 색상 토큰으로 실제 명도대비를 계산해봄(WCAG 공식 그대로 계산,
추측 아님):
- 라이트모드 "적격" 뱃지(success 글자/success-soft 배경): **2.89:1**
- 라이트모드 "확인필요" 뱃지(warning): **2.81:1**
- 라이트모드 "미달" 뱃지(danger): **4.01:1**
- (참고: 일반 텍스트 WCAG AA 기준은 4.5:1, 큰 텍스트도 3:1 — 뱃지 글자는
  10.5px라 "큰 텍스트" 기준도 안 됨)
- 다크모드는 전부 4.23~6.72:1로 훨씬 양호함(danger만 4.5 턱걸이 미달).

색 자체를 바꾸는 건 브랜드 색상 판단이 들어가는 영역이라(예전에 "우리 원래
배경 있잖아" 피드백처럼 임의로 색을 바꾸면 안 된다는 원칙과 같은 결) 코드는
안 건드리고 수치만 정확히 재서 보고함 — 뱃지 배경 투명도를 낮추거나 글자색을
더 진하게 하는 식으로 고칠 수 있어 보이는데, 어느 쪽을 원하시는지 확인 필요.

**테스트했으나 문제 없었던 것**
- `GET /rfps`에 SQL인젝션류 문자열(`' OR '1'='1`, `"; DROP TABLE x; --`) — 200,
  빈 결과. SQL DB가 아니라 임베딩·JSON 카드 기반이라 애초에 인젝션 경로 없음.
- `limit=-1`·`limit=999999`·`offset=-5`·`limit=abc` — 전부 422, Pydantic
  타입 검증이 이미 잘 막고 있음.

**곁들여 발견 — `GET /rfps`의 `q`도 사실상 길이 무제한(우선순위 낮음)**
5만자 검색어를 보내면 400이 뜨긴 하는데, 앱 코드가 막은 게 아니라 uvicorn의
HTTP 파서가 "Invalid HTTP request received"로 거부하는 것(대략 4천~8천자
사이에서 걸림, 실측). `q`는 LLM을 안 타서(정적 열람, 비용 0) 라운드 1같은
비용 낭비는 없지만, 그 사이 애매한 길이(수천 자)는 완전히 무방비고 걸렸을 때
에러 메시지도 "Invalid HTTP request received"로 사용자에게 불친절함 — 낮은
우선순위로 남김.

## 이미 알려진 미해결 항목 (이전 세션에서 발견, 아직 미착수)

우선순위 순서:

1. **[신뢰성] 치명적 단일 요건의 즉시 탈락 처리 안 됨 — 실제 데이터로 규모 확인함**
   지금 verdict는 미충족 **개수**로만 갈림(0/1~3/4+). 대기업 참여 제한처럼
   개수와 무관하게 그 자체로 탈락인 요건이 있는데, 구분 없이 개수 기준에
   섞여 있음 — "확인필요"로 잘못 표시될 수 있음. 근거: [[참가자격 매칭 — 기능 설계]] §9-1.

   **2026-07-30 추가 — 프로필/체크리스트 설계 토론 중 데이터로 검증(GPTPilots_work,
   코드 미수정, 사용자와 토론만 진행):** 이미 캐시된 98개 문서·1,703개 참가자격
   요건으로 실측함.
   - "~할 수 없음/제한/박탈/실격" 같은 **예외 없는 탈락형 문구**가 전체 요건의
     10%(171건). 그중 68%(115건)는 지금 체크리스트 어디로도 안 걸림.
   - 특히 "상호출자제한기업집단(대기업 계열사) 참여 제한"이 **98개 문서 중
     67%(66건)**에 있음 — 지금 체크리스트에 있는 항목 5개 중 3개보다도 자주
     나오는데 물어볼 칸 자체가 없음.
   - 체크리스트를 늘리는 것보다 **이 로직(치명도 구분)을 먼저 고치는 게 순서상
     맞다** — 지금 상태에서 체크리스트만 늘리면, 사용자가 정직하게 "대기업
     계열사예요"라고 답할수록 오히려 "확인필요"로 순화되는 사고가 더 자주
     터짐(체크리스트가 없을 땐 사용자가 자기소개에 우연히 안 적어야만 발생하는
     드문 사고였는데, 체크리스트가 생기면 매번 정직하게 답하니 상시 발생 사고가 됨).

2. **[신뢰성] 보유 자격 체크리스트 5개의 실제 커버리지가 낮음 — 데이터로 확인,
   아직 미착수(토론만 진행)**
   같은 1,703개 요건 기준, 현재 체크리스트 5개 키워드로 걸리는 문장은 **26%뿐**.
   반대로 체크리스트에 없는 "공동수급/컨소시엄 조건"(85% 문서에 등장)·
   "하도급 제한"(81%)은 지금 체크리스트에 있는 항목 대부분보다 흔한데 빠져
   있고, 반대로 가장 드문 현재 항목("중소기업 확인서", 21%)은 들어가 있음 —
   처음 5개를 고를 때 표본이 부족했던 것으로 보임. 실제 예시(축산물이력관리
   시스템 공고, 요건 10개 중 체크리스트로 답되는 건 4개뿐)로 화면에 뜬
   "확인 7건"이 왜 나오는지 확인함. 항목 1과 순서 있음(1을 먼저 고칠 것).

3. **[UX] "확인 질문" 되묻기가 그 문서의 실제 불명 항목과 무관함**
   `chat-flows.tsx`의 `runReady`가 판정 후 되묻는 질문은 그 문서에서 실제로
   불명확했던 항목이 아니라, **항상 고정된 체크리스트 5개 중 안 체크한 것**만
   보여줌. 항목 2가 고쳐지기 전에도 이 자체는 독립적으로 고칠 수 있는 불일치임
   — 문서의 실제 unmet/unclear 항목을 되물어야 함.

4. **[정의 필요] "협상에 의한 계약체결 방식" 참가자격 포함 여부**
   한국전기안전공사 문서에서 발견된 항목 — 참가자격(누가 참여 가능한가)이
   아니라 계약방식 정보인데, 팀원은 참가자격 범주에 넣고 싶어함. 팀 합의
   필요, 제가 임의로 결정하면 안 되는 영역. 근거:
   [[참가자격 매칭 — 추출 정확도 디버깅]].

5. **[기능 한계] 대화가 활성 문서 A 하나만 근거로 삼음**
   활성 문서를 B·C까지 담아도, `/ask`가 `doc_id` 하나만 받아서 대화는 A
   기준으로만 답함. "두 공고 차이가 뭐야?" 같은 질문에 진짜 두 문서를
   근거로 답하려면 백엔드 `/ask` 계약을 `doc_id` 리스트로 확장해야 함.

6. **[UX] 문서 비교 화면에 차이 자동 하이라이트 없음**
   활성 문서 2개 이상을 나란히 볼 때 다른 조항을 자동으로 표시해주는 기능
   없음. LLM 추가 호출이 필요해 보류 중.

7. **[환경] GPU 공유 자원 경합**
   공유 VM이라 팀원이 GPU를 많이 쓰면 백엔드(임베딩 모델)가 아예 못 뜸.
   코드로 해결 불가 — 팀 차원의 GPU 사용 시간 조율 또는 임베딩 CPU 폴백
   고려 필요.

8. **[검증 안 됨] 후보 8건 vs 15건 공정 비교**
   같은 프로필로 K=8, K=15를 각각 돌려서 실제 소요시간·정확도 차이를
   측정한 적 없음(매번 다른 프로필로 테스트해서 비교가 불공정했음). 근거:
   [[공고 추천 — 로딩 개선(캐시·스트리밍·후보수)]].

9. **[정리] 대화 히스토리는 localStorage뿐, 기기 간 동기화 안 됨**
   서버 저장이 아니라서 다른 브라우저·컴퓨터에서는 히스토리가 안 보임.
   여러 사람이 같이 쓸 계획이면 서버 쪽 저장으로 옮겨야 함. 근거:
   [[대화 히스토리 — 세션 목록·삭제]].
